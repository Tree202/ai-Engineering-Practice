一、四种方法:四道网

先认识四个工具。它们不是「四选一」,而是按时间轴排开的四道网——分别拦截不同时刻发生的不同问题。

把它们放到时间轴上

最容易看漏的一点 表格里「时间点」这一行,标的是「它什么时候救你」,不是「你什么时候操作它」。 前三个方法这两件事重合,唯独 git 是分开的:你必须在动手前就铺好,它却要到出事后才兑现价值。

第一个必须理解的概念:为什么不能直接 pip install macOS 自带的那个 python3 是系统在用的。你往它里面装包,可能污染系统环境,而且不同项目需要不同版本的库,迟早打架。

Python 和 JavaScript 的一个重要差别 JS 项目有 package.json,里面的 "scripts" 段定义了 npm test 这种统一入口。 Python 没有这个东西——没有一条放之四海皆准的「跑测试」命令。你得直接敲工具名:

.venv/bin/python -m pytest  ·  .venv/bin/python -m mypy  ·  .venv/bin/python -m ruff check .

所以别人教程里的 pnpm test,在 Python 世界对应的就是上面这几条。记住它们,后面全流程都在用。

第 3 步:一个 pyproject.toml 配好三个工具

在项目根目录建 pyproject.toml。这一个文件同时是 pytest、mypy、ruff 三者的配置文件:

[project]
name = "myshop"
version = "0.1.0"
requires-python = ">=3.9"
dependencies = []            # 主代码只用标准库,不装任何第三方包

# ---------------- pytest:跑测试 ----------------
[tool.pytest.ini_options]
testpaths = ["tests"]        # 只去 tests/ 里找测试,别扫整个项目
pythonpath = ["."]           # ← 这一行是新手救命稻草,见下面的红框
addopts = "-v"               # 每条测试单独打一行,看得更清楚
python_files = ["test_*.py"]
python_functions = ["test_*"]

# ---------------- mypy:静态类型检查 ----------------
[tool.mypy]
python_version = "3.9"
files = ["myshop", "tests"]
strict = true                # 严格模式:所有函数都必须写类型标注

# ---------------- ruff:规范 + 常见 bug ----------------
[tool.ruff]
target-version = "py39"
line-length = 100

[tool.ruff.lint]
# E=风格  F=真错误(未使用变量等)  I=import 排序  B=常见 bug 陷阱
select = ["E", "F", "I", "B"]
99% 的初学者会卡在这里:ModuleNotFoundError 你写了 from myshop.price import format_price,一跑 pytest 就报:

ModuleNotFoundError: No module named 'myshop'

原因:pytest 是从 tests/ 目录里跑的,项目根目录不在 Python 的搜索路径里,所以它找不到 myshop 这个包。

教科书答案是 pip install -e .(把项目装成一个包),但对新手太重。 本教程的答案就是上面那一行 pythonpath = ["."](pytest 7+ 支持)——零安装、一行解决。

另外 myshop/ 目录里要有一个 __init__.py(哪怕是空文件),它是「这个文件夹是一个 Python 包」的标志。

第 4 步:关于 Python 3.9 的两个提醒

3.9 能不能用?能,但要注意两点 ① 新语法不能用。str | None 这种写法是 3.10+ 才有的,3.9 上运行会报错,要写成 Optional[str]。 本教程的所有代码都是 3.9 兼容的,你可以直接抄。

② ruff 的 UP 规则会和 3.9 打架。如果你在 select 里加了 "UP"(升级建议), ruff 会催你把 Dict[str, Any] 改成 dict[str, Any],但那在 3.9 运行时会炸。 所以上面的配置只选了 ["E","F","I","B"],3.9 上零冲突。

想升级到新版 Python 的话,你装了 Homebrew,一条命令的事:brew install python@3.13。但不升级也完全能走完本教程。

第 5 步:五个你一定会撞上的概念

这五个东西,后面每一页都在用。不先讲清楚,你会以为是自己抄错了。

概念 1:venv 和 activate —— 为什么命令前面老是 .venv/bin/

比喻:每个项目自己的一整套厨具 系统 Python 是公共厨房那口锅,几个项目抢着用,版本互相打架。 venv 是这道菜专用的锅碗瓢盆,全放在项目里的 .venv/ 文件夹。 不要了就把整个文件夹删掉,不影响任何人。

有两种用法,效果一样:

用法怎么写特点
激活(activate) source .venv/bin/activate
之后直接 pytest		 命令短,但只在当前这个终端窗口有效,关掉就没了
写全路径 .venv/bin/python -m pytest 命令长,但在任何地方都一定对
为什么本教程和 CLAUDE.md 里都用全路径写法 Claude Code 在 Bash 里跑命令,不会继承你终端的 activate 状态。

你在终端 activate 了,自己敲 pytest 好好的;但你让 AI 跑 pytest, 它那边可能根本没激活,于是报 command not found,或者用了系统 Python 跑出一堆诡异错误。

所以对 AI 下命令时,永远写 .venv/bin/python -m pytest 这种全路径形式。

两个最常见的报错和诊断方法:

现象原因
装完了却 command not found: pytest没 activate,或者装到了别的 Python 里
明明装了却 ModuleNotFoundError: pytest装到了另一个解释器里

一条命令诊断(两个路径都应该在 .venv/bin/ 下面):

which python; which pytest

概念 2:pytest 怎么找到你的测试

「AI 明明写了测试,跑出来却是 0 passed」——原因几乎总是这四条规则之一没满足:

规则必须是违反了会怎样
文件名test_*.py 或 *_test.py整个文件被无视
函数名以 test_ 开头这个函数被无视
测试类名以 Test 开头整个类被无视
测试类不能有 __init__—⚠️ 静默跳过,只给一条很容易被忽略的 warning
最后一条是 AI 协作里的真陷阱 AI 时不时会生成带 __init__ 方法的测试类(它以为要初始化)。 pytest 会一声不吭地跳过整个类,你看到「测试通过」,其实一条都没跑。

防呆办法:跑完看一眼收集到几条(collected N items), 数字对不上就说明有东西被吞了。

概念 3:__init__.py 到底要不要建

位置要不要理由
myshop/(源码包) 要 它是「这个文件夹是一个 Python 包」的标志,import myshop.price 才成立。可以是空文件
tests/ 默认不要 只有当两个子目录里出现同名测试文件、pytest 报 import file mismatch 时,才加一个空的

概念 4:conftest.py —— pytest 自动加载的工具箱

三句话讲完:

  1. 它是 pytest 自动加载、不需要 import 的一个文件,作用范围是「它所在的目录及所有子目录」
  2. 放在项目根目录时有个重要副作用:让根目录进入 Python 的搜索路径,于是 from price import ... 能用了
  3. 共享的 fixture(见下)就放这儿
它和 pythonpath = ["."] 是同一个问题的两种解法 都是为了解决 ModuleNotFoundError。实测对比:
有 conftest.py,跑 pytest✅ 正常
删掉 conftest.py,跑 pytest❌ ModuleNotFoundError
删掉 conftest.py,跑 python -m pytest✅ 正常

给初学者的判定规则:只要你的测试里出现 from <你自己的模块> import ..., 就必须三选一——① 配 pythonpath = ["."],② 用 python -m pytest,③ 放个 conftest.py。 三个都不做 = 一定报错。

顺带记住这个退出码 ModuleNotFoundError 导致的失败,pytest 的退出码是 2(Interrupted: N errors during collection), 不是 5。5 是「一条测试都没收集到」。搞混了会对着错误的方向查半天。

概念 5:fixture —— 写在参数位置上的「自动准备工作」

比喻:手术前的护士 你(测试函数)只需要在参数里点个名说要 tmp_path, 护士就在你动手之前把干净的器械台准备好(建好临时目录); 你做完之后她负责收拾(自动清理)。 这些你一行代码都不用写,你只是喊了个名字。

规则很简单:参数名 = fixture 名。pytest 按名字找到它、调用它、把返回值塞进你的参数里。

def test_订单真的落盘了(tmp_path):     # ← 只是写了个参数名
    数据库 = str(tmp_path / "test.db")  # ← tmp_path 已经是一个准备好的临时目录了
    ...

三个你会经常见到的内置 fixture:

名字干什么为什么重要
tmp_path 给每条测试一个全新的空临时目录,跑完自动删 这就是几条测试各写各的数据库、互不污染的原因
monkeypatch 临时改模块变量 / 环境变量,测试结束自动改回来 用它把 order.DB_PATH 指向临时库,不碰真实数据
capsys 抓住 print 的输出 测「有没有打印正确的提示」时用
自己写 fixture:yield 之前是准备,之后是收尾 
@pytest.fixture()
def 服务器(tmp_path, monkeypatch):
    monkeypatch.setattr(order, "DB_PATH", str(tmp_path / "api.db"))
    服务 = api.make_server(port=0)      # ← 准备:启动服务器
    线程 = threading.Thread(target=服务.serve_forever, daemon=True)
    线程.start()

    yield f"http://127.0.0.1:{服务.server_port}"   # ← 把地址交给测试用

    服务.shutdown()                     # ← 收尾:不管测试成功失败都会执行
    服务.server_close()

最底层:price.py —— 一个纯函数

"""价格模块:全项目最「纯」的一块。

纯 = 只做计算。不读数据库、不发网络请求、不看时间、不改全局变量。
同样的输入永远得到同样的输出 —— 这种函数是单元测试最好啃的骨头。
"""


def format_price(cents: int) -> str:
    """把「分」换算成人类看的价格字符串。

    1234 -> "¥12.34"
    """
    if cents < 0:
        raise ValueError("价格不能为负数")
    # divmod(1234, 100) 一次返回 (12, 34):12 块、34 分
    yuan, fen = divmod(cents, 100)
    # :02d 表示不足两位就在前面补 0,所以 5 分会变成 "05"
    return f"¥{yuan}.{fen:02d}"

中间层:order.py —— 跨模块 + 写数据库

完整代码见第二册,这里只看最关键的那几行——它演示了什么叫「集成」:

from myshop.price import format_price      # ← 依赖了另一个模块

def create_order(item: str, unit_cents: int, qty: int, db_path=None) -> Order:
    # ---- 1. 先把所有校验做完 ----
    if qty <= 0:
        raise ValueError("数量必须大于 0")
    if unit_cents < 0:
        raise ValueError("单价不能为负数")

    total_cents = unit_cents * qty

    # ---- 2. 再把所有可能抛异常的计算做完 ----
    # format_price 对负数会 raise。放在写库前面调用,
    # 保证「要么整单成功,要么库里什么都没有」。
    total_text = format_price(total_cents)     # ← 这一行就是「跨模块协作」

    # ---- 3. 最后才动数据库 ----
    init_db(path)
    with closing(sqlite3.connect(path)) as conn:       # ← 真的写进数据库
        cur = conn.execute(
            "INSERT INTO orders (item, qty, total_cents) VALUES (?, ?, ?)",
            (item, qty, total_cents),
        )
        order_id = cur.lastrowid or 0
        conn.commit()

    return {"id": order_id, "total_cents": total_cents, "total_text": total_text}
注意这里的顺序 —— 它本身就是一课 所有可能抛异常的事情,必须发生在 INSERT 之前。

如果把 format_price 挪到写库之后调用(这是很自然的写法,因为它只是"拼个显示文案"), 那么单价为负时就会先把订单写进数据库,然后才抛异常——库里留下一条不该存在的脏数据。

这个 bug 有多隐蔽?mypy 完全看不出来,而且如果你没写那条测试,全量 pytest 也抓不到。 实测证据见下一节。
记住这个 format_price 它是全项目最小、最不起眼的一个函数,但它被两个上层模块引用着。 第 步骤 5 那场事故的主角就是它——一个函数的爆炸半径,和它的代码行数成反比。

同一个项目,把三层分开跑,计时:

层级条数实测耗时倍数为什么慢
⓪ ruff— 0.02 秒— 不运行代码,只扫一遍文本
⓪ mypy— 0.27 秒— 不运行代码,推导全项目的类型
① 单元测试5 条 0.00 秒1× 快到测不出来。只调一个纯函数,什么外部东西都不碰
② 集成测试5 条 0.02 秒— 要真的建 sqlite 数据库、写入、再读出来
③ 接口测试7 条 3.64 秒≈180×
(对比集成层)		 每条都要真的启动一个 HTTP 服务器再关掉
④ E2E— 10 秒+ / 条1000×+ 要开真浏览器,还要等页面加载、动画播完
这组数字比任何说教都有力 集成层 0.02 秒 vs 接口层 3.64 秒,差约 180 倍。 而单元测试那 5 条快到 pytest 都测不出耗时,直接显示 0.00s。

这就是为什么金字塔下宽上窄:底层便宜到可以「每改一行就跑一次」,顶层贵到「整个任务只跑一次」。 也是为什么步骤 3 只跑底下两层——如果每步都跑接口测试,你一天做 20 步就要白等一分多钟, 而如果每步都跑 E2E,那就是几个小时。

Bug问题后果

四、步骤 0 · 建安全网 git 小步提交

0

做什么:

git init
git checkout -b feat/add-discount
git status

逐字拆解

部分含义
git版本控制工具。把它想成游戏的存档系统
init给这个项目装上存档系统(只需要做一次)
checkout切换到某条分支
-b--branch 的缩写:新建一条分支并立刻切过去。不加 -b 就是切到已存在的分支
feat/add-discount分支名。feat/ 是社区约定的前缀(feature,新功能),后面写实际功能名
status看当前进度面板:哪些改了、哪些勾选了、哪些是 git 不认识的新文件
为什么非要新开一条分支 让 main 保持绝对干净。AI 在新分支上怎么折腾都行,最坏情况是切回 main 把这条分支整个删掉,main 一行都没动过。

这一步把爆炸半径从「整个项目」缩到了「这条分支」。

更安全的新写法:git switch -c feat/add-discount(git 2.23+)。 老的 checkout 身兼两职(切分支 / 恢复文件),容易误操作;新版拆成了 switch(切分支)和 restore(恢复文件)。两者都行。

「干净」具体长什么样

  git status 的五种状态(实测)
$ git status

nothing to commit, working tree clean     ← 这就是「干净」

─────────── 简短版 git status -s 的对照 ───────────
$ git status -s
(完全没有输出 —— 没输出就是好消息,不是命令卡住了)

?? ai_notes.py     ← ?? = git 完全不认识的新文件(最危险的一类)
 M app.py          ← 改了,但没 add(注意 M 前面那个空格!)
M  README.md       ← 改了,已经 add 了
MM both.py         ← 两种都有:add 过之后又改了
A  new.py          ← 新文件,已 add
-s 输出的关键:左右两列 左列 = 暂存区(add 过的),右列 = 工作区(还没 add 的)。 M 前面那个空格特别容易被忽略,而它恰恰是关键——M  和  M 是完全不同的两种状态。

为什么 git status 必须干净:一条隐藏的因果链

如果 status 不干净,先处理掉再开工:要么提交(git commit),要么先收进抽屉(git stash)。

Python 项目必写的 .gitignore

Python 会自动生成大量垃圾文件。不写 .gitignore 的话,它们会全部进入 git,让你的 git diff 全是噪音——又一次让步骤 4 失效。

# ---- Python 垃圾 ----
__pycache__/
*.py[cod]
.pytest_cache/
.mypy_cache/
.ruff_cache/

# ---- 虚拟环境(几千个文件、几十 MB)----
.venv/
venv/

# ---- 密钥,千万别提交 ----
.env

# ---- 数据库文件 ----
*.db

# ---- macOS ----
.DS_Store
.gitignore 最大的陷阱:它管不了「已经被提交过」的文件 如果你先提交了 __pycache__,之后再写 .gitignore,git 会继续跟踪它们。要清掉得:

git rm -r --cached __pycache__ 然后 git commit

--cached 这个词千万别漏!不加它就是把磁盘上的文件真删了。对 .env 这种文件漏加就是灾难。

正确顺序永远是:先写 .gitignore,再开始 add/commit。

存下第一个档

git add -A
git commit -m "chore: 初始化项目骨架"
步骤 0 完成的标志 git status 显示 working tree clean,并且 git log --oneline 至少有一条记录。
现在,不管 AI 接下来做什么,你都有一个可以回去的点。

六、步骤 3 · 做第一步 + 自测 检测

3

这一步里其实有两件独立的事

先把这句话拆开

半句在管什么
「实施方案第 1 步」管做多少(分量控制)
「改完跑 pytest 和 mypy,修到干净」管做完怎么验收(质量控制)
一个关键的时间差:指令下发 ≠ 验证执行 很多人看到这句话会以为「还没写代码就要测试了?」。不是的。这一步的执行顺序是先改代码 → 再跑测试。

但验收标准要在派活的时候就一起给出,原因是:
  • 事前给:它带着「最后要过测试」这个约束去写代码,写的时候就在朝这个标准靠。
  • 事后追加:它已经进入「我做完了」的状态,你再让它跑测试,它的动机就变成了用最小改动让红变绿——这正是作弊的温床。

为什么只做「第一步」,不一口气做完

后果说明
diff 大到你读不动一步 50 行你会认真看,五步 500 行你只会拉到底说「看着还行」。步骤 4 就这样悄悄失效了
错误会叠加第 1 步的数据结构设计错了,后面四步全建在这个错误上。第 5 步才发现 = 前四步全废
回退粒度太粗五步做完才发现问题,只能整个推翻。分步提交才能精确回到「第 2 步做完」
上下文越长越容易漂连续工作五步,后面它会开始忘掉你最初的约束。每步停一下相当于重新对焦
「一步」应该多大? 判断标准只有一个:这一步做完,是不是能独立验证、独立提交?
✅ 好的一步
  • 「给 price.py 加一个 apply_discount 函数并写单测」
  • 「给 orders 表加 discount_cents 字段」
❌ 不好的一步
  • 「把整个价格体系重构一遍」
  • 「做优惠券功能」
新手期宁可切得太碎。碎了最多多几轮对话,大了是你彻底失去控制。

① 改测试作弊 改断言值、加 @pytest.mark.skip、注释掉、把该测的 mock 掉、包个空 try/except 改动文件列表里出现 tests/*.py —— 一眼就能看见
② 范围蔓延 你让它改 A,它顺手「优化」了 B、重命名了 C、删了一段它认为没用的代码 出现了你没要求改的文件
③ 写了但没接上 新建了函数但没有任何地方调用;加了配置项但没读取 只有新增、没有对应的调用点改动
这三类的共同点 它们都躲在「测试通过」和「做对了」之间的那条缝里。 测试全绿完全不代表这三件事没发生。git diff 是唯一能看进这条缝的工具。

反直觉但重要:测试越绿,越要看 diff —— 因为绿色会让你放松,而绿色恰恰不覆盖这三类。
为什么说漏掉这一步「最危险」 漏掉步骤 0(git),你丢的是安全网,但那是一次性的、看得见的损失。

漏掉步骤 4,你丢的是对自己代码库的所有权——这是个缓慢的、看不见的过程。 几个月后你面对一个自己完全看不懂的项目,而它已经在跑生产了。 前四种方法都可以外包给工具,只有这一步不能。

兜底 · git 回退三件套

rewind 兜不住,或者已经 commit 过了,就得用 git。这里有本教程最重要的一个坑。

🔥 reset --hard 删不掉 AI 新建的文件 AI 一顿操作新建了 5 个实验文件,你跑 git reset --hard,然后发现那 5 个文件原封不动地躺在目录里。 你以为「回退失败了」。

不是失败,是 reset 只管 git「认识」的文件。那些从没 git add 过的新文件(status 里显示 ??), git 压根不知道它们存在,自然也不会删。
  完整实测:AI 改了 2 个文件 + 新建 3 个文件 1 个目录
$ git status -s
 M report.py
 M src/mod.py
?? experiment_final_FINAL.py
?? experiment_v1.py
?? experiment_v2.py
?? tmp_output/

$ git reset --hard HEAD
HEAD is now at 622dcb3 docs: 用 -am 一步提交

$ ls
experiment_final_FINAL.py  experiment_v1.py  experiment_v2.py  report.py  src  tmp_output
↑↑↑ 已跟踪文件的改动没了(对),但 AI 新建的 4 个东西一个都没删!

$ git clean -fdn        ← -n 是预演,只说要删什么,不真删
Would remove experiment_final_FINAL.py
Would remove experiment_v1.py
Would remove experiment_v2.py
Would remove tmp_output/

$ git clean -fd         ← 确认无误,真删
Removing experiment_final_FINAL.py
Removing experiment_v1.py
Removing experiment_v2.py
Removing tmp_output/

$ ls
report.py  src
$ git status -s
(空 = 彻底回到 AI 动手之前)
标准四步,背下来
  1. git status —— 先看清 AI 到底动了什么
  2. git reset --hard HEAD —— 抹掉对已跟踪文件的所有改动
  3. git clean -fdn —— 预演:看看还剩哪些新文件要删
  4. git clean -fd —— 确认无误再真删

口诀:先 reset 后 clean;clean 先 n 后 f。
clean 的三个坑 ① 不加 -d 会漏掉新建的文件夹。git clean -n 只列文件,不列目录,你会以为清干净了其实没有。

② -x 是核弹级选项,别乱加。git clean -fdx 会把 .gitignore 忽略的东西一起删光—— 实测直接蒸发了一个 9MB、569 个文件的 .venv,.env 里的密钥也会没。没有明确理由绝不要加 x。

③ 删掉的东西不进回收站、不进 git、reflog 也救不回。所以必须先 -fdn 预演。 预演清单里如果有你想留的(比如 AI 生成的一份不错的文档),先复制出来或者 git add 保住。
一个反直觉的细节 新文件add 过和没 add 过,命运完全不同:

git reset --hard 会把已经 add 过的新文件连文件本身一起删掉(实测直接从磁盘消失), 但对没 add 过的新文件束手无策。

所以「AI 新建的文件」到底会不会被 reset 干掉,取决于它有没有被 add 过。这就是为什么两步都要做。

三档的选择规则

损伤程度用哪档成本
结果对,细节不满意5b 直接说零回退
这一轮跑偏了5c Esc Esc / /rewind退会话,副作用不退
好几轮都烂了 / rewind 兜不住git reset --hard + clean -fd退到上一个提交

往下一档才换工具,不要一上来就 rewind。粒度正好对应对比表「防的是」那一行:实现有 bug → 刚才那几轮 → 任何时候的任何问题。

E2E 在这里才第一次跑

① 跑真正的全套

E2E 为什么只在这里跑一次 E2E 天生 flaky(同样的代码有时绿有时红:网络抖动、动画没播完、元素还没渲染出来)。

人看到偶发失败的反应是:「这个老抽风,重跑一下。」
AI 看到的反应是:「红了,一定是我刚才改坏的,我来修。」

于是它开始修一个根本不存在的 bug,而且会越来越粗暴:加 time.sleep(3)、加重试、放宽断言、直接 skip。 最糟的是它「成功」了——红变绿,汇报「已修复」,但绿是因为它塞了个 3 秒等待。

所以 E2E 绝不进每步循环。详见 第二册。

跑 E2E 时的提示词要堵死它的四条歪路:

跑一次 pytest tests/e2e/。

如果有失败:
- 先原样重跑一遍,确认是偶发还是稳定复现
- 不许用 sleep / 重试 / 放宽断言 / skip 的方式让它变绿
- 稳定复现的话告诉我是哪条、错在哪一步,先别动手改

② 通读完整 diff

!git diff main...HEAD

这是从分支起点到现在的全部改动。这一遍要看的是「整体」:有没有互相矛盾的设计、有没有该删没删的临时代码、命名是否一致。

③ 让它自己再审一遍

/review
/review 是什么 /review 是 /code-review 的别名,两者完全相同。它审查当前分支的改动,找逻辑错误、安全问题、可简化的地方。

常用变体:
  • /code-review --fix —— 审完直接把问题改掉
  • /security-review —— 专门查安全问题的独立命令
注意顺序:先你看,再让它看 不要用 /review 代替步骤 ②。 它审的是「代码质量」,你审的是「这是不是我要的东西」——后者它永远不知道。

而且如果你先看它的 review 报告再看 diff,你的判断会被它的结论锚定。先形成自己的看法。

  3. 局部检查回答「我写对了吗」,全量回答「我弄坏了谁」。后者只有跑全量才知道,而它只要 0.03 秒。

十二、进阶:把流程固化下来

上面这套流程,每次都手打提示词很累。有三种办法把它固化。

① CLAUDE.md —— 每次对话自动加载的项目说明

在项目根目录建一个 CLAUDE.md,里面写项目的规矩。每次开新对话它都会自动读到,不用你再说一遍。

# myshop 项目说明

## 环境
- Python 3.9,虚拟环境在 .venv/
- 所有命令都要用 .venv/bin/python -m xxx 的形式

## 每次改完代码必须跑
    .venv/bin/python -m mypy
    .venv/bin/python -m pytest

## 硬性约束
- 不许改动 tests/ 下的任何文件,除非我明确要求
- 不许用 skip / 注释掉 / 放宽断言的方式让测试变绿
- 测试本身有问题就停下来告诉我
- 每次只做一步,做完停下等我检查
- 报告结果时贴命令的真实输出,不要只说"通过了"
放在哪影响范围
~/.claude/CLAUDE.md用户级,影响你所有项目
./CLAUDE.md项目级,团队共享(会进 git)
./CLAUDE.local.md本地私密,不进版本控制

不想手写的话,在项目里跑 /init,它会自动生成一份初始版本。

② 自定义 slash command —— 把重复指令变成一个词

建一个文件 .claude/skills/check/SKILL.md:

# 检查代码

按顺序跑这三条,任何一条失败就停下来报告:

1. .venv/bin/python -m ruff check .
2. .venv/bin/python -m mypy
3. .venv/bin/python -m pytest

把每条的真实输出贴出来。不许改测试文件。

之后在对话里打 /check 就等于把上面整段话说了一遍。

③ Hooks —— 让检查变成强制的

这是最硬的一档 前两种都还是「指令」,AI 理论上可以不照做。Hooks 是在 Claude Code 的固定生命周期点执行 shell 命令—— 不依赖模型判断,是确定性的。

比如配置成「每次编辑了 .py 文件之后,自动跑一次 mypy」。这样「让它自测」就从你要记得说 变成了系统强制执行。

配置写在 .claude/settings.json 里。具体的事件名和字段格式各版本略有差异, 建议先查一下你这个版本的 hooks 文档再配,别照抄网上的旧写法。
给你的建议顺序 先手打几轮,把流程跑熟 → 觉得某句话每次都要说 → 写进 CLAUDE.md → 某组命令总是一起跑 → 做成 /check → 某个检查绝对不能漏 → 上 hook。

不要一上来就配一堆自动化。你得先知道自己需要什么,才知道该固化什么。
