一、测试到底是什么

一句话回答 测试是真实的、可执行的代码文件。不是自然语言,不是文档,也不是让 AI「在心里过一遍」。

一个测试长什么样

假设你有这么一个函数(这是我们示例项目 myshop 里真实的代码):

# 文件:myshop/price.py

def format_price(cents: int) -> str:
    """把「分」换算成人类看的价格字符串。1234 -> "¥12.34" """
    if cents < 0:
        raise ValueError("价格不能为负数")
    yuan, fen = divmod(cents, 100)     # divmod(1234,100) -> (12, 34)
    return f"¥{yuan}.{fen:02d}"        # :02d = 不足两位前面补 0

它的测试是另一个真实存在的文件:

# 文件:tests/test_price.py

import pytest
from myshop.price import format_price


def test_普通价格() -> None:
    assert format_price(1234) == "¥12.34"


def test_零元是边界值() -> None:
    # 0 很容易被漏掉,专门写一条
    assert format_price(0) == "¥0.00"


def test_不足一角要在前面补零() -> None:
    # 5 分不能显示成 "¥0.5",必须是 "¥0.05"
    assert format_price(5) == "¥0.05"


def test_整数元不能丢掉小数位() -> None:
    assert format_price(10000) == "¥100.00"


def test_负数要报错() -> None:
    # 「该报错的时候有没有报错」也是行为的一部分,同样要测
    with pytest.raises(ValueError):
        format_price(-1)

逐行解剖

部分是什么
test_price.py 文件名里的 test_ 是硬规则。pytest 启动时会自动扫描全项目,把符合命名的文件找出来执行
from myshop.price import ... 把要测的那个函数真的引进来
def test_普通价格() 一条测试用例。函数名必须以 test_ 开头,后面可以用中文
assert A == B 断言 —— 整个测试的心脏。意思是「我期望 A 等于 B」,不等就判定失败
pytest.raises(ValueError) 断言「这里应该抛异常」。没抛反而算失败

跑起来是什么样

pytest 最贴心的地方 它会自动对比字符串,用 - 和 + 标出差在哪,还用 ? 那一行精确指出位置。 你完全不需要自己去猜哪里不一样。

「几百上千条」是怎么来的

看上面的例子:一个 5 行的小函数就有 5 条测试用例。一条用例 ≈ 一个具体场景(正常值、边界值、异常值)。

项目状态测试数量
你刚建的新项目0 条
写了两个月的小项目几十条
一个成熟的开源库几百到几千条
大型商业项目上万条
关键认知 这些不是谁在某一天一口气准备出来的,是几个月几年里一条一条累积的。 每加一个功能加几条,每修一个 bug 加一条。

你现在没有测试,不代表你用不了这套流程——跟着流程走,测试会自己长出来。

二、三种容易混淆的「测试」

形态谁执行 能否重复可靠性
① 自动化测试代码文件机器,秒级 ✅ 无限次高,客观
② 手动测试人的操作你,鼠标键盘 ❌ 每次靠人中,会漏
③ 自然语言验收标准一段话AI 自己判断 ⚠️ 结论可能不同低,主观

pytest 跑的只有 ①。

③ 确实存在也有用,但它不叫测试。比如你写:

改完自己检查一下:登录失败时应该显示错误提示,不应该跳转。

这是验收标准,AI 会去读代码判断「嗯,看起来是这样」。问题在于:

  • 它是在读自己刚写的代码,倾向于确认自己是对的(自我美化)
  • 结论是「我觉得应该没问题」,不是「我执行了,结果是 X」
  • 同一份代码问两次可能给两个答案
① 和 ③ 的本质区别:证据来自谁 ① 的证据来自 pytest 和 mypy —— 它们不会撒谎,也不会给 AI 面子。
③ 的证据来自模型自己的判断 —— 那正是你要防的东西。

三、先纠正一个分类错误

很多人会问:「这是白盒测试?单元测试?接口测试?系统测试?」——这个问法本身混了两个正交的维度:

维度分类回答的问题
视角白盒 / 灰盒 / 黑盒写测试的人知不知道内部实现
层级单元 → 集成 → 接口 → 系统 / E2E一次测试覆盖多大范围

任何一个测试同时具有这两个属性。比如「单元测试」通常是白盒的,「E2E」通常是黑盒的。

另外两组词的真实关系 接口测试是集成测试的一种(包含关系): 
集成测试(大概念:测多个模块凑在一起对不对)
   └── 接口测试(其中一类:专门从 HTTP API 这个入口测)
系统测试和 E2E 基本是同一件事的两种叫法,只是来自不同年代:
系统测试传统软件工程教材;教科书、考证、传统行业、测试岗在用
E2E 测试Web 开发圈;互联网公司、前端、现代技术文档在用

为什么 typecheck 对 AI 协作特别有用

它是「改了 A 忘了改 B」的天敌 AI 改了一个函数的签名(比如加了个参数),可能只改了它注意到的几个调用点。

mypy 会把它漏掉的全部一次性揪出来,精确到文件和行号。人工找一定会漏。

致命盲区:签名不变、行为变了

def format_price(cents: int) -> str:   # 改前:返回 "¥0.00"
def format_price(cents: int) -> str:   # 改后:返回 "免费"
                                        # ↑ 签名一个字符都没变
对 mypy 来说,"¥0.00" 和 "免费" 完全等价 它们都是 str 这个类型的合法居民。mypy 没有任何理由报警。

这不是配置问题,调再严的 strict 模式也抓不到——这是类型系统结构性的盲区。

「mypy 全绿」给人的安全感,和它实际提供的安全性,差得非常远。
两个比喻,选你喜欢的记 比喻一:mypy 检查插头的形状对不对(两脚还是三脚), pytest 检查通上电以后灯亮不亮。形状对了,灯照样可能不亮。

比喻二:杯子里的水被换成了醋。杯子还是杯子(类型对),但你喝下去会知道不对(行为错)。

一个 AI 协作专属的坑

mypy 默认不检查「没写类型标注」的函数体 AI 生成的测试函数经常忘了写 -> None, 于是 mypy 对整个测试文件视而不见,你却以为「类型检查过了」。

解决:配置里开 check_untyped_defs = true,或者命令加 --check-untyped-defs。

六、第 ① 层 · 单元 / 组件测试

①
单元测试 —— 金字塔的主力
5 条实测 0.01 秒
✅ 这一层测什么 一个纯函数的输入输出,包括正常值和边界值(0、进位、非法输入)。
❌ 这一层不测什么 不碰数据库、不碰 HTTP、不启动服务。 如果一个「单元测试」需要连数据库,那它其实已经是集成测试了。

什么叫「纯」

纯 = 只做计算。不读数据库、不发网络请求、不看时间、不改全局变量。
同样的输入永远得到同样的输出 —— 这种函数是单元测试最好啃的骨头。

完整代码见 第一节。这一层的关键是边界值:

边界类型例子为什么容易出错
零format_price(0)0 是最常被漏掉的值,也是最常出问题的
进位 / 补位format_price(5) → ¥0.05格式化的经典 bug 温床
整数边界format_price(10000) → ¥100.00小数位容易被吞掉
非法输入format_price(-1) 应抛异常「该报错时有没有报错」也是行为
给初学者的写测试口诀 一个函数至少写四条:一条正常的、一条零、一条最大或最小的、一条非法的。
这四条能挡掉大部分低级 bug。

七、第 ② 层 · 集成 / 接口测试

②
集成测试 —— 测「拼起来」还对不对
4 条实测 0.02 秒
✅ 测什么 多个模块拼在一起还对不对 —— order 调用 price 有没有接错、 数据有没有真的写进数据库、换个连接还能不能读回来。
❌ 不测什么 不重复测 format_price 的每个边界(那是第 ① 层的活,重复测是浪费)。 不走 HTTP,直接调 Python 函数。

真实代码

# 文件:tests/test_order.py
from pathlib import Path
import pytest
from myshop.order import create_order, get_order


def test_下单会把总价算对并且带上价格文案(tmp_path: Path) -> None:
    数据库 = str(tmp_path / "test.db")

    订单 = create_order("咖啡", unit_cents=1250, qty=2, db_path=数据库)

    assert 订单["total_cents"] == 2500
    # ↓↓↓ 这一行证明 order 真的调用了 price,而不是自己乱拼字符串
    assert 订单["total_text"] == "¥25.00"


def test_订单真的落盘了_换个连接还读得到(tmp_path: Path) -> None:
    数据库 = str(tmp_path / "test.db")

    订单 = create_order("键盘", unit_cents=39900, qty=1, db_path=数据库)
    # get_order 会重新 connect 一次数据库,读到说明数据不是只存在内存里
    读回来 = get_order(订单["id"], db_path=数据库)

    assert 读回来["item"] == "键盘"
    assert 读回来["total_text"] == "¥399.00"


def test_下两单会拿到两个不同的订单号(tmp_path: Path) -> None:
    数据库 = str(tmp_path / "test.db")

    第一单 = create_order("茶", unit_cents=800, qty=1, db_path=数据库)
    第二单 = create_order("茶", unit_cents=800, qty=1, db_path=数据库)

    # 自增主键有没有正常工作,是数据库层面的行为,只能靠集成测试发现
    assert 第一单["id"] != 第二单["id"]
两个「怎么断言才算数」的关键技巧 ① 怎么证明「真的跨模块了」?
只 assert total_cents == 2500 是不够的——那只证明乘法对了。 必须 assert total_text == "¥25.00",这条断言一旦挂,就说明两个模块之间接错了。

② 怎么证明「真的落盘了」?
同一个连接里 INSERT 完再 SELECT,即使没 commit 也能读到,证明不了落盘。 必须像 get_order 那样重新连接一次数据库,读到才算真的写进文件了。

这是集成测试和单元测试最本质的区别。
试试看:故意把它弄坏 把 order.py 里 format_price(total_cents) 那一行删掉, 看 assert 订单["total_text"] == "¥25.00" 这条变红。 亲眼看到测试抓住一个真实的错误,比读十页文档管用。
②
接口测试 —— 从 HTTP 打进去
5 条实测 2.60 秒 · 比单元测试慢 260 倍
✅ 测什么 真的启动一个 HTTP 服务器,真的发请求进去,检查状态码(201/400/404)、 Content-Type、返回的 JSON 结构。也就是「契约」。
❌ 不测什么 不测浏览器、不测页面长什么样(那是第 ③ 层)。 也不再重复测价格进位这种细节。 
# 文件:tests/test_api.py

@pytest.fixture()
def 服务器(tmp_path, monkeypatch):
    """启动一个真的 HTTP 服务器,测完自动关掉。"""
    # 让接口层写到临时数据库,别碰真实的 myshop.db
    monkeypatch.setattr(order, "DB_PATH", str(tmp_path / "api.db"))

    服务 = api.make_server(port=0)   # ← 0 = 让系统分配空闲端口,避免端口冲突
    线程 = threading.Thread(target=服务.serve_forever, daemon=True)
    线程.start()

    yield f"http://127.0.0.1:{服务.server_port}"

    # yield 之后是收尾,不管测试成功失败都会执行
    服务.shutdown()
    服务.server_close()


def test_下单接口返回_201_和订单内容(服务器: str) -> None:
    状态码, 数据 = 发请求(
        f"{服务器}/orders", "POST",
        {"item": "咖啡", "unit_cents": 1250, "qty": 2},
    )

    assert 状态码 == 201            # 201 Created:新建资源成功
    assert 数据["total_text"] == "¥25.00"


def test_查不存在的订单要返回_404(服务器: str) -> None:
    状态码, 数据 = 发请求(f"{服务器}/orders/99999", "GET")

    assert 状态码 == 404
    assert "不存在" in 数据["error"]
三个实用技巧 ① port=0 让系统随机挑端口。 写死 8000 的话,你本地开着开发服务器时测试就跑不了。

② urllib 把 4xx 当异常抛。 测 400/404 时,urlopen 遇到非 2xx 会 raise HTTPError 而不是返回响应, 必须 except urllib.error.HTTPError 接住才能断言状态码。 新手在这里常以为「接口挂了」。(requests 库不会这样)

③ 中文乱码。json.dumps 默认会把中文转义, 必须写 ensure_ascii=False,Content-Type 也要带 charset=utf-8。
为什么它慢 260 倍?答案出人意料 实测:5 条接口测试 2.60 秒,而 5 条单元测试只要 0.01 秒。

慢的不是 HTTP 本身,而是每条测试都要启动和关闭一个服务器—— server.shutdown() 的默认轮询间隔就是 0.5 秒,乘以 5 条 fixture。

这个数字比任何说教都能解释「为什么金字塔上窄下宽」。

八、第 ③ 层 · E2E / 系统测试

③
E2E —— 像真人一样用一遍
End-to-End:从用户这一端,到数据库那一端

它和单元测试的区别(最直观的对比)

单元测试:直接调函数 
from myshop.price import format_price

assert format_price(1234) == "¥12.34"
E2E:开真浏览器,像人一样操作 
page.goto("http://127.0.0.1:8000")
page.get_by_role("link", name="咖啡").click()
page.get_by_label("数量").fill("2")
page.get_by_role("button", name="去结算").click()

看那段代码,每一行就是一个人的动作。这就是 E2E 的本质:用程序模拟一个真人在用你的产品。

完整的 Python 写法

# 文件:tests/e2e/test_checkout_e2e.py

import pytest

# importorskip:导入不到就跳过整个文件,而不是让测试报红
pytest.importorskip(
    "playwright.sync_api",
    reason="E2E 需要:pip install pytest-playwright && playwright install chromium",
)

from playwright.sync_api import Page, expect   # noqa: E402

首页 = "http://127.0.0.1:8000"


def test_用户可以从首页一路下单成功(page: Page) -> None:
    page.goto(首页)

    # 按「用户看得见的东西」定位,而不是按 CSS class ——
    # class 改个名测试就挂了,按钮上的字改了才是真的改了功能
    page.get_by_role("link", name="咖啡").click()
    page.get_by_label("数量").fill("2")
    page.get_by_role("button", name="加入购物车").click()
    page.get_by_role("button", name="去结算").click()

    # expect(...) 会自动重试等待,不需要自己写 sleep
    expect(page.get_by_test_id("order-total")).to_have_text("¥25.00")
    expect(page.get_by_text("下单成功")).to_be_visible()
两个值得学的写法 ① importorskip。没装 playwright 的人跑测试时, 输出是干净的 1 skipped 而不是一屏 ImportError。 这样别人复制你的项目也不会看到一片红。

② 用 get_by_role / get_by_label 而不是 CSS 选择器。 按「用户看得见的东西」定位。CSS class 改个名测试就挂,但按钮上的字改了才是真的改了功能。

它的独特价值

它是唯一能回答「用户真的能用吗」的测试 一个非常常见的场景:
单元测试 100% 全绿 ✅,但用户打开页面,点登录按钮没反应。

为什么?因为每个零件单独测都是对的,但装起来接错线了—— 前端调的接口地址写错了一个字母。单元测试测不到这个,因为它压根不发真实请求。
E2E 就是抓这类「零件都对、组装错了」的问题。

它的代价

代价说明
慢要启动整个应用 + 启动浏览器。一个用例几秒到几十秒,一套跑十几分钟很正常
脆你改个按钮的 class 名,测试就挂了
难定位红了只告诉你「登录流程失败」,到底是前端、接口还是数据库的问题?得自己查
flaky见下一节 —— 这是对 AI 协作最致命的一条

九、flaky:为什么 E2E 对 AI 特别危险

flaky 是什么

flaky 英文原意是「薄片状的、容易剥落的」,引申义是「靠不住的、反复无常的」。中文一般直接说 flaky,或译作「不稳定测试」「偶发失败」。

精确定义 代码一个字没改、环境一模一样,反复跑同一个测试,有时绿有时红。
跑十次,七次过、三次挂。你什么都没做,再跑一次又过了。

为什么这件事很严重

因为它打破了测试最基本的契约:

红色 = 有 bug

一旦这个契约破了,红色的含义变成了「可能有 bug,也可能没有,你自己猜」。测试套件就此失去了作为判据的资格——这比没有测试更糟,因为它会消耗你的信任和注意力,却不给你确定的答案。

团队里最终会出现那句致命的话 「哦这个测试老是这样,重跑一下就好了。」

然后有一天,一个真的 bug 被这句话打发掉了。

E2E 为什么特别容易 flaky

原因具体表现
时序竞态测试点按钮时,按钮还没渲染出来 / 数据还在加载。机器比人快得多——人会自然地等页面加载完再点,机器不会
网络抖动真实 HTTP 请求,偶尔慢 100 毫秒就超时
测试互相污染测试 A 往数据库塞了条数据,测试 B 查询时读到了,断言的数量对不上
并行顺序不定多个测试并发跑,每次执行顺序不同
外部依赖第三方 API 挂了、跨零点导致日期变了、时区、随机数
动画过渡元素正在移动中,点击落到了空处

单元测试也可能 flaky(比如依赖当前时间或随机数),但概率低一个数量级——因为它不涉及网络、渲染、真实时序这些不确定因素。

致命之处:人和 AI 的反应完全不同

最糟的情况是它「成功」了 红变绿了,它汇报「已修复」。但绿是因为它加了个 3 秒等待或者删了断言,不是因为解决了问题。

这个只有你看 diff 才能发现。

怎么应对

#做法说明
1结构上:E2E 不进每步循环归到流程的步骤 7,整个任务跑一次
2先建立基线在干净代码上先跑一遍。本来就有 2 个红的,记下来是哪 2 个
3红了先重跑一次再判断重跑绿了 = flaky,忽略;重跑还红 = 真 bug,处理
4在提示词里堵死它的乱修路径见下
 
跑一次 pytest tests/e2e/。

如果有失败:
- 先原样重跑一遍,确认是偶发还是稳定复现
- 不许用 sleep / waitForTimeout / 重试 / 放宽断言 / skip 的方式让它变绿
- 稳定复现的话告诉我是哪条、错在哪一步,先别动手改

第二条尤其重要——它把 AI 最容易走的四条歪路一次性封掉了。

十、局部 vs 全量:同一批测试跑两次

这不是两种测试,是同一批测试跑了两次,区别只在于「跑几个」
步骤 3 · 局部步骤 5a · 全量
跑什么只跑和刚改的东西相关的全部都跑
命令pytest tests/test_price.pypytest(不带任何参数)
回答什么我这块改对了吗?我有没有弄坏别人?
检查半径你手指碰过的文件整个仓库
一个比喻:换水管 改一个被到处引用的底层函数,像换水管的一节管子。

你在自家水槽下面拧上、放水、不漏,于是宣布搞定 —— 这是步骤 3。
楼下邻居的天花板,是第二天才开始滴水的 —— 这是没跑步骤 5a 的代价。

步骤 5a 就是整栋楼一起放水。它只要 0.03 秒。

完整的事故复盘(含真实的红字输出)在 第一册 · 步骤 5a。

三条可以直接用的规则
  1. 改底层 = 必跑全量。判断标准:这个函数被别的文件 import 了吗?被 import 得越多,局部检查越不可信。 工具函数、格式化、序列化、常量、配置——全是重灾区。
  2. 「我顺手改了对应的测试」是危险信号,不是安心信号。 改一个断言意味着你确认了行为变更,而行为变更就一定有波及面。
  3. 别把 mypy 的绿灯当测试的替代品。类型检查只保证「接得上」,不保证「算得对」。

十一、AI 在每一层能做多少

把「做测试」拆成四个动作分别评估,因为 AI 在这四个动作上的能力差异极大:

层级写测试跑 判断结果修代码综合
⓪ typecheck/lint —★★★★★ ★★★★★★★★★★ 可全权代理
① 单元/组件 ★★★★☆★★★★★ ★★★★★★★★★☆ 断言必须人审
② 集成/接口 ★★★☆☆★★★☆☆ ★★★★☆★★★☆☆ 卡在业务知识
③ E2E/系统 ★★☆☆☆★★★☆☆ ★★☆☆☆★☆☆☆☆ 最弱,修时最危险

逐层说明

层级AI 能做的你必须保留的
⓪ typecheck 配置、执行、修错。类型错误是它修得最准的一类——报错精确到行号+原因 只决定严格程度(strict 开不开),一次性决策
① 单元测试 写用例、执行、修错。给一个函数能生成覆盖正常/边界/异常的一整套 审断言的期望值 —— 最关键的一道人工闸门
② 集成/接口 写代码、执行 提供业务规则和测试数据 —— 哪些字段必填、正确的业务流程顺序,这些不在代码里
③ E2E 只能当打字员(配合浏览器工具写选择器) 决定测哪几条流程、判断红色是真是假、禁止它自己修

十二、防作弊:AI 写测试的根本陷阱

陷阱:它照着「实现」写测试,不是照着「应该做什么」写

如果你的实现里有 bug,它会把 bug 固化成「预期行为」 它读代码看到 return None,就写 assert result is None。 测试全绿,bug 永久保存。

这背后是一个更本质的问题:

测试的价值,来自它是一份「独立于实现的第二真相来源」。
当实现和测试都出自同一个模型、同一份上下文时,这份独立性就消失了。
做法效果
先写实现,再让 AI 补测试⚠️ 会固化 bug,必须人审断言
先让 AI 写测试(你审),再写实现✅ 独立性保住了,这是 TDD 的思路
你自己写死期望值,让 AI 补充边界用例✅ 很实用的折中

五种典型作弊,按隐蔽程度排

作弊方式长什么样怎么发现
改断言assert x == 8 改成 == 9diff 里出现 tests/*.py
skip 掉加 @pytest.mark.skip同上,或看输出里的 skipped 数量
注释掉整个测试块被注释读 diff
吞异常给报错处包个空 try/except读 diff
假声称根本没跑,直接说「测试通过了」要求它贴真实输出

一条揪出「测试被动过」的命令

git diff --staged --name-only | grep -E '^tests/|_test\.py$'

有输出 = 测试文件被改过了,停下来仔细看。

怎么确认 AI 写的测试真的会失败

变异测试的手工版 —— 一个非常值钱的动作 AI 写的测试有相当比例是「永远通过」的(断言写空、把实现原样抄进断言)。

让 Claude 先故意把源码改坏一行,确认那条测试变红,再改回来。

一条从来不会红的测试,等于没有这条测试。

提示词:

你刚写的这 4 条测试,我要确认它们真的有效。

请依次做:
1. 故意把 format_price 里的补零逻辑去掉,跑测试,贴出变红的输出
2. 改回去,跑测试,贴出全绿的输出

如果有哪条测试在代码被改坏时依然是绿的,说明那条测试没用,告诉我。

两种垃圾测试,一眼识别

def test_works():
    assert True                    # ❌ 什么都没测,永远绿


def test_format_price():
    format_price(1234)             # ❌ 只验证"没崩",没检查结果对不对
审断言的唯一标准 这条测试里,有没有一个写死的期望值?
没有的话,它基本没在测东西。

十三、项目一条测试都没有怎么办

这是新手项目的常态。不要因此放弃验证——退而求其次,能用哪层用哪层:

层级手段需要你写测试吗
1️⃣typecheck 通过(mypy)❌ 不需要,配好就一直有
2️⃣lint 通过(ruff check .)❌ 不需要
3️⃣实跑一遍(启动服务真访问一次)❌ 不需要
4️⃣让它先补测试⚠️ 见上一节的警告
5️⃣人眼读 diff + 小步提交❌ 永远的兜底
即使零测试,1️⃣ + 3️⃣ + 5️⃣ 依然能挡掉大部分问题 别觉得「没测试所以这套流程用不了」。这时候步骤 3 的提示词变成: 
实施方案第 1 步。改完跑:
  .venv/bin/python -m mypy
  .venv/bin/python -m ruff check .
然后启动服务自己访问一下,确认没报错。

从零开始长出测试的正确姿势

不要一上来就让 AI「给整个项目补全测试」 你会得到几百行没人看得懂、也没人信得过的测试。
正确做法:跟着流程慢慢长 这一步改哪个模块,就顺手给那个模块补两三条测试。 每次两三条,你都能看完。跑几十轮之后,你的测试套件是真实长出来的,而且每一条你都过过目。

特殊情况:接手一个没有测试的老项目,又必须动它。 这时先用 Plan 模式,让 Claude 为你不打算改的核心函数补一批 「刻画现状」的测试(characterization test)——不管现在的行为对不对,先把它固定下来。 先织网,再动刀。
