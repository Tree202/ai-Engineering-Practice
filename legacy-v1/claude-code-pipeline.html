二、核心概念:为什么同一层要跑两遍

先回答那个问题:Jenkins 前还是后? 答案是「都要」。但同一条命令在两个地方跑,目的完全不同。
本地跑(Jenkins 前)CI 跑(Jenkins 里)
目的快速反馈质量门禁(Quality Gate)
给谁看你自己团队 / 主干
范围局部(只跑改动相关的)全量
能否绕过✅ 能(--no-verify)❌ 不能
环境你的机器(每个人都不一样)统一的干净容器
失败代价你自己再改一次PR 变红,合不进去

两个理由,缺一不可

理由 1:本地可以被绕过 git commit --no-verify 一秒钟就绕过所有本地钩子。

赶时间的时候人人都会这么干,包括你。CI 不行——它跑在你控制不了的机器上。
理由 2:「在我机器上是好的」 你本地 Python 3.11、同事 3.9、生产 3.10;你装了某个包、CI 没装; 你的 .env 里有个配置别人没有。

CI 是唯一的权威裁判。
本地跑是为了「快」,CI 跑是为了「不可绕过」。
同一条命令,两种角色。
一个和 Claude Code 直接相关的推论 第一册那套七步流程,覆盖的全是「Jenkins 之前」的部分。 它的目标是:让你 push 上去的代码,在进 Jenkins 之前就已经是绿的。

CI 是最后一道保险,不是你的调试工具。 用 CI 当调试工具(推上去看看红不红,红了再改再推)是最慢最贵的开发方式—— 一个来回 10 分钟,而本地一个来回 3 秒。

pre-commit 长什么样

建一个 .pre-commit-config.yaml:

repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.16.3
    hooks:
      - id: ruff
        args: [--fix]
      - id: ruff-format

  - repo: https://github.com/pre-commit/mirrors-mypy
    rev: v1.19.1
    hooks:
      - id: mypy
pre-commit install

装完之后,每次 git commit 它都会自动跑一遍,不过关就不让你提交。

本地为主,云端兜底 理想状态是它在你手指离开键盘之前就报错了——PyCharm 会直接把那行标红。

这一层是「测试左移」做得最彻底的一层。左移的意思就是:把问题尽量往开发的早期推,越早发现越便宜。 理论上它根本轮不到 Jenkins。

如果它只能在云端跑,那它就失去了 90% 的意义——你不可能改一行代码就等 CI 跑 5 分钟。
维度 5 · Jenkins 前还是后

两边都跑,分工明确:

本地(Jenkins 前)Jenkins 里
范围局部 — pytest tests/test_price.py全量 — pytest
覆盖率一般不跑(会变慢)✅ 必出报告 + 卡门槛
目的我改的这块对不对我弄坏了谁 + 覆盖率够不够
覆盖率门禁是什么 「测试覆盖率低于 80% 就让 PR 变红」这类规则,通常只在 Jenkins 里做。

因为本地跑覆盖率会慢一截(要插桩统计),不值得每次都跑。命令长这样: 
.venv/bin/python -m pytest --cov=myshop --cov-fail-under=80

五、第 ② 层 · 集成 / 接口测试

②
集成 / 接口测试
⚠️ 这里是分界线,归属最模糊
维度 1 · 谁做
类型谁写放在哪用什么
集成测试
代码内跨模块 + 连数据库		 开发 和源码同一个仓库 pytest
接口测试 · 开发版 后端开发 同一个仓库 pytest + httpx
接口测试 · 测试岗版 测试工程师 独立的测试项目 Postman / Apifox / JMeter
国内互联网公司的典型分工 后端开发写单元测试 + 集成测试(在代码库里);测试工程师写接口自动化(在独立项目里)。

两边在接口层重叠,这是常态,不是浪费—— 开发关心「代码逻辑对不对」,测试关心「接口契约有没有被破坏」。视角不同,抓的问题也不同。

运维 / SRE 在这一层的角色:🔶 负责提供测试环境和依赖服务(数据库、消息队列、缓存)。

维度 4 · 本地还是云端
这一层开始出现「本地跑不动」的情况 原因:它需要数据库、消息队列、第三方服务。三种现实:
依赖复杂度做法
简单(如 sqlite)✅ 本地能跑,和单元测试一样方便(我们的 myshop 就是这种)
中等(PostgreSQL、Redis)🔶 用 Docker Compose 或 testcontainers 让本地也能跑
复杂(一堆微服务、第三方支付)❌ 本地跑不了,只能靠 CI

这是 CI 相对本地优势最大的一层——CI 环境可以随手拉起十个容器,你的笔记本不行。

六、第 ③ 层 · E2E / 系统测试

③
E2E / 系统测试
参与角色最多的一层,唯一有运维参与的一层
维度 1 · 谁做
角色参与程度
测试工程师 / SDET✅ 传统主力。写 Playwright / Selenium 脚本
前端开发✅ 现代团队里越来越多,写自己模块的关键路径
后端开发🔶 小公司没测试岗时全包

手工测试✅ 探索性测试也在这一层
运维 / SRE✅ 上线后的拨测 / 合成监控
这是唯一一层运维会真正参与的 他们不写 CI 里的 E2E,但会在生产环境挂一个每 5 分钟跑一次的 「登录 + 下单」脚本,挂了就报警。

这个东西叫 合成监控(synthetic monitoring) 或 拨测—— 本质上就是生产环境版的 E2E。
维度 2 · 用什么工具
场景工具
Web 自动化Playwright(现在主流)、Selenium(老牌)、Cypress(JS 生态)
Python 绑定pytest-playwright、Selenium Python bindings
移动端Appium
云端设备农场 BrowserStack、Sauce Labs、LambdaTest —— 跑各种浏览器/设备组合,你自己没那么多机器
录制生成playwright codegen —— 你点一遍,它自动生成代码
AI 🔻 最弱。它看不见页面,选择器只能猜。 带浏览器工具的 AI 能读 DOM 后再写,好一些,但不知道哪几条是关键流程——那是产品知识
CIJenkins + 浏览器环境(headless 或专门的 Docker 镜像)
给初学者的一个省力技巧 playwright codegen http://localhost:8000 会打开一个浏览器, 你手动点一遍流程,它同步生成对应的 Python 代码。

比让 AI 猜选择器靠谱得多——生成出来再让 Claude 帮你整理成规范的测试。

维度 4 · 本地还是云端
几乎纯云端 本地跑 E2E 很痛苦:要起整个应用栈(前端 + 后端 + 数据库)+ 浏览器。

开发本地通常只在写或调试某一条用例时跑,不会跑全量。
维度 5 · Jenkins 前还是后
这一层永远不会出现在 Jenkins 之前 它太慢、太脆,而且需要一个部署好的完整环境——你的笔记本上没有。
为什么 E2E 绝不能进开发循环:回顾 flaky E2E 天生不稳定(同样代码有时绿有时红)。人看到偶发失败会说「重跑一下」; AI 会认定「一定是我改坏的」,然后去修一个不存在的 bug, 并且很可能用 sleep / 放宽断言的方式「修好」它。

八、一个真实的 Jenkinsfile

把上面所有东西落到一个文件里,你就全串起来了:

pipeline {
  agent any
  stages {

    // ===== 第 ⓪ 层:最快最便宜,第一道关 =====
    stage('Lint & Typecheck') {
      steps {
        sh '.venv/bin/python -m ruff check .'
        sh '.venv/bin/python -m mypy'
      }
    }

    // ===== 第 ① 层:快,第二道关 =====
    stage('Unit Tests') {
      steps {
        sh '.venv/bin/python -m pytest tests/test_price.py --cov=myshop --cov-fail-under=80'
      }
    }

    // ===== 第 ② 层:需要起容器,较慢 =====
    stage('Integration Tests') {
      steps {
        sh 'docker compose up -d postgres redis'
        sh '.venv/bin/python -m pytest tests/test_order.py tests/test_api.py'
      }
      post {
        always { sh 'docker compose down' }     // 不管成败都清理容器
      }
    }

    stage('Build & Deploy to Staging') {
      steps { sh './deploy.sh staging' }
    }

    // ===== 部署之后才能跑的:接口回归 =====
    stage('API Regression') {
      steps { sh 'newman run postman/api-collection.json --env-var host=staging' }
    }

    // ===== 第 ③ 层:最慢,最后一道 =====
    stage('E2E') {
      steps {
        sh '.venv/bin/python -m pytest tests/e2e/ --base-url=https://staging.example.com'
      }
    }
  }
}
看这个文件要注意三件事
  1. 顺序 = 从便宜到贵。fail fast,前面挂了后面不跑
  2. API Regression 和 E2E 在 Deploy 之后——它们打的是已经跑起来的服务
  3. 前三个 stage 你在本地也跑过。CI 不是替你跑,是不允许你不跑
没有 Jenkins 怎么办? 用 GitHub Actions —— 免费,配置就是仓库里一个 YAML 文件,五分钟能跑起来。 最小版本: 
name: CI
on: [push, pull_request]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '3.11' }
      - run: pip install pytest mypy ruff
      - run: ruff check .
      - run: mypy
      - run: pytest

九、行业趋势:测试岗在消失吗

不是消失,是转型。你需要知道这个背景,因为它决定了你要不要学写测试。

变化说明
微软取消了纯测试岗 十几年前就改成了 SDET(Software Engineer in Test)—— 本质是写测试代码的工程师,要求和开发一样的编码能力
谷歌走过类似的路径 测试角色深度融进工程团队
国内大厂 仍有测试岗,但招聘要求普遍写着「具备自动化测试能力」「熟悉 Python/Java」。 纯手工点点点的岗位在快速萎缩
创业公司 / 小团队 常常根本没有测试岗,四层全归开发
现在的主流理念 「质量是全员责任」+「测试左移」(shift left,把验证尽量往开发早期推)。

对你的直接含义:如果你是个人开发者或小团队,这四层全是你的活。

这恰恰是那套 Claude Code 流程的价值所在——它让一个人扛起原本要几个岗位分担的质量工作。

十、给你的实操建议

如果你是个人开发 / 小团队

层级建议怎么做
⓪ typecheck/lint 一定要有 零成本,配一次永久受益。pyproject.toml 里几行搞定
① 单元测试 一定要有 跟着流程一条条长出来,不要一次性补
② 集成测试 🔶 挑核心的 只写核心链路的几条(下单、支付这类)
③ E2E 🔶 只写 1~3 条 只写最值钱的路径:能不能登录、能不能付钱
优先级排序,按投入产出比
  1. typecheck + lint —— 一小时配置,永久受益
  2. git 小步提交 —— 零成本,只要纪律
  3. 单元测试 —— 跟着改动慢慢长
  4. GitHub Actions —— 五分钟配一个,从此本地不绕过
  5. 其他的,等你真的需要了再说

如果你在中大型公司

四层全有,分工按上面的表。你作为开发要关心的是 ⓪ 和 ①(必须自己写、自己跑),② 一半,③ 基本不用你操心—— 但你要知道它存在,因为你的改动挂在 E2E 上时,是你去修。

最后一句

把 Claude Code 的七步流程放回这张大图里 它覆盖的全是「Jenkins 之前」那一段(关卡 ①②③④)。

目标只有一个:让你 push 上去的代码,在进 Jenkins 之前就已经是绿的。

CI 是保险,不是调试工具。用 CI 当调试工具的人,每个来回要等 10 分钟; 走完七步流程再 push 的人,每个来回 3 秒。
