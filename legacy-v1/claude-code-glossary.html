二、git 命令速查

先记住三个比喻,后面全部好懂 git 仓库 = 游戏的存档系统(commit = 存档,回退 = 读档)
暂存区 = 超市结账传送带(改文件 = 从货架拿东西;add = 放上传送带;commit = 收银员打单)
未跟踪文件 ?? = 没贴条码的商品(git 只对贴过条码的东西负责)
建立与查看
命令做什么
git init给项目装上存档系统(只做一次)
git checkout -b feat/xxx新建分支并切过去。-b = 新建
git switch -c feat/xxx同上,新写法,更安全(git 2.23+)
git status看进度面板。啰嗦但有指引,新手用这个
git status -s两个字母的简短版。没输出 = 干净,不是卡住了
git log --oneline看存档列表
git log --oneline --stat每次提交改了哪些文件、加删几行

git status -s 的两列怎么读

M  README.md    ← 左列 = 暂存区:改了,已 add
 M app.py       ← 右列 = 工作区:改了,没 add(注意 M 前面那个空格!)
MM both.py      ← 两种都有:add 过之后又改了
A  new.py       ← 新文件,已 add
?? ai_notes.py  ← git 完全不认识的新文件(最危险的一类)
M 前面那个空格特别容易被忽略,而它恰恰是关键 M (已暂存)和  M(未暂存)是完全不同的两种状态。
看改动
命令看的是什么
git diff还没 add 的改动
git diff --staged已经 add、待提交的改动(--cached 同义)
git diff HEAD两种全看(最全,流程步骤 4 推荐用这条)
git diff --stat只看每个文件加删几行
git diff --staged --name-only只列改动的文件名
git diff main...HEAD从分支起点到现在的全部改动(步骤 7 总审用)

diff 怎么读

--- a/app.py         ← a = 改之前
+++ b/app.py         ← b = 改之后
@@ -1 +1,4 @@        ← 改动发生在第 1 行起
-print("hello")      ← 减号 = 被删掉的旧内容
+def greet(name):    ← 加号 = 新加的内容
头号坑:git add 之后 git diff 变空白 新手会以为改动丢了。其实是跑到暂存区去了,要用 git diff --staged 看。

另外:未跟踪的新文件不会出现在 git diff 里(git 还不认识它)。 所以步骤 4 应该先 git status 再 git diff。

输出很长时会进入分页模式(底部显示冒号),按 q 退出,不是死机。
提交
命令做什么
git add -A暂存全部改动(含新文件)
git add 文件名只暂存某个文件
git commit -m "说明"存档并起名
git restore --staged .取消暂存,但保留你写的内容
提交信息的判断标准 一次提交要能用一句话讲清楚。讲不清就说明该拆成两次。

❌ 更新 / 修改 / fix bug —— 三天后自己也看不懂

三、git 回退三件套(最危险的一节)

🔥 全篇最重要的一条:reset --hard 删不掉 AI 新建的文件 AI 一顿操作新建了 5 个实验文件,你跑 git reset --hard, 然后发现那 5 个文件原封不动躺在目录里,你以为「回退失败了」。

不是失败。reset 只管 git「认识」的文件——那些从没 add 过的新文件(??), git 压根不知道它们存在。
手段✅ 能回退❌ 管不了
git restore .
git checkout -- .		 已跟踪文件的未暂存改动 已 add 的改动;AI 新建的未跟踪文件
git reset --hard HEAD 已跟踪文件的所有改动(含已暂存) 未跟踪文件照样纹丝不动
git clean -fd 未跟踪的新文件和新目录 —(但先用 -fdn 预演!)
一次干净的回退 = 两步,缺一不可
  1. git status —— 先看清 AI 到底动了什么
  2. git reset --hard HEAD —— 抹掉老文件的改动
  3. git clean -fdn —— 预演,看看还剩哪些新文件要删
  4. git clean -fd —— 确认无误再真删

口诀:先 reset 后 clean;clean 先 n 后 f。

clean 的参数

命令行为
git clean -fdn安全 预演,只打印会删什么,不真删
git clean -fd真删。-f=force,-d=连新目录一起
git clean -fdx☢️ 核弹级 连 .gitignore 忽略的一起删
clean 的三个坑(全部实测过) ① 不加 -d 会漏掉新建的文件夹。 git clean -n 只列文件,不列目录,你会以为清干净了其实没有。

② -x 绝不要乱加。实测:git clean -fdx 直接蒸发了一个 9MB、569 个文件的 .venv,.env 里的密钥也会没。

③ 删掉的东西不进回收站、不进 git、reflog 也救不回,永久消失。 所以必须先 -fdn 预演。
一个反直觉的细节 新文件 add 过和没 add 过,命运完全不同:

git reset --hard 会把已经 add 过的新文件连文件本身一起删掉(实测直接从磁盘消失), 但对没 add 过的新文件束手无策。

回到某一次旧提交的三种方式

方式命令特点
只是去看看 git checkout 哈希 历史一点不改。会提示 detached HEAD(听着吓人,其实就是「你现在站在一次提交上」)。
回来:git switch -
真的退回去 git reset --hard 哈希 危险 后面的提交从分支上消失。
后悔药:git reflog 能找回来
最安全 git revert 哈希 历史不改,只追加一个「反做」的提交。团队协作时用这个

四、git 新手报错速查

报错原因 / 解法
fatal: not a git repository 当前目录没有 git 仓库 → git init,或者你 cd 错地方了
fatal: clean.requireForce ... refusing to clean 忘了加 -f → 用 git clean -fdn 先预演
nothing to commit, working tree clean 不是报错,是「干净」的意思 —— 好消息
Please tell me who you are 第一次用 git,没配名字 →
git config --global user.name "你的名字"
git config --global user.email "你的邮箱"
error: pathspec 'xxx' did not match 分支名或文件名写错了 → git branch 看有哪些分支
You are in 'detached HEAD' state 不是报错。你 checkout 到了一个提交而不是分支 → git switch - 回去
终端卡在一个冒号 : 不动 进了分页器 → 按 q
突然进了个奇怪的编辑器,退不出来 是 vim。按 Esc,再输入 :wq 回车

# ---- 虚拟环境(几千个文件、几十 MB)----

.gitignore 管不了「已经被提交过」的文件 如果你先提交了 __pycache__,之后再写 .gitignore,git 会继续跟踪它们。清理: 
git rm -r --cached __pycache__
git commit -m "chore: 把 __pycache__ 从版本库里移除"
--cached 千万别漏!不加它就是把磁盘上的文件真删了。对 .env 漏加就是灾难。

正确顺序永远是:先写 .gitignore,再开始 add/commit。

五、Python 命令速查

Python 没有 package.json 的 scripts JS 有 npm test 这个统一入口,Python 没有等价物。 后果是:AI 每次自测跑的命令都可能不一样(pytest / python -m pytest / .venv/bin/pytest)。

解法:CLAUDE.md 就是 Python 项目缺失的那个 scripts。把命令写死在里面(见第八节)。
环境
命令做什么
python3 -m venv .venv建虚拟环境
source .venv/bin/activate激活(只在当前终端窗口有效)
.venv/bin/python -m pip install pytest mypy ruff装三个工具
which python; which pytest诊断:两个都该在 .venv/bin/ 下
对 AI 下命令时永远写全路径 Claude Code 在 Bash 里跑命令,不继承你终端的 activate 状态。 你 activate 了自己敲 pytest 好好的,让 AI 跑就可能 command not found。

所以永远写 .venv/bin/python -m pytest 这种形式。
pytest
命令做什么
python -m pytest全量(步骤 5a 用)
python -m pytest tests/test_price.py只跑一个文件(步骤 3 用)
python -m pytest tests/test_price.py::test_零元是边界值只跑一条
python -m pytest -k "价格"按关键字过滤
python -m pytest -q安静模式,输出少
python -m pytest -v详细模式,每条单独一行
python -m pytest -x第一个失败就停
python -m pytest -rs显示被 skip 的原因
python -m pytest --durations=5找出最慢的 5 条
python -m pytest --cov=myshop出覆盖率报告(需 pytest-cov)
mypy / ruff
命令做什么
python -m mypy类型检查(按 pyproject 配置的范围)
python -m mypy --check-untyped-defs myshop tests推荐:连没写类型标注的函数体也检查
python -m ruff check .规范检查
python -m ruff check . --fix能自动修的直接修掉
python -m ruff format .格式化代码
mypy 的一个 AI 协作专属坑 mypy 默认不检查「没写类型标注」的函数体。 AI 生成的测试函数经常忘写 -> None,于是 mypy 对整个测试文件视而不见, 你却以为「类型检查过了」。

解法:配置里开 check_untyped_defs = true。

pyproject.toml 最小可用配置

[tool.pytest.ini_options]
testpaths = ["tests"]
pythonpath = ["."]           # ← 救命稻草,解决 ModuleNotFoundError
addopts = "-v --strict-markers"

[tool.mypy]
python_version = "3.9"
files = ["myshop", "tests"]
strict = true
check_untyped_defs = true

[tool.ruff]
target-version = "py39"
line-length = 100

[tool.ruff.lint]
select = ["E", "F", "I", "B"]   # 注意:3.9 上别加 "UP",会打架

六、Python / pytest 报错速查

现象原因 / 解法
ModuleNotFoundError: No module named 'myshop' 头号劝退坑。项目根目录不在搜索路径里。三选一: ① pyproject 配 pythonpath = ["."] ② 用 python -m pytest 而不是 pytest ③ 根目录放一个 conftest.py
退出码是 2,不是 5
collected 0 items / 退出码 5 一条测试都没找到。检查:文件名是不是 test_*.py、函数名是不是 test_ 开头
写了测试类却一条都没跑,只有个 warning 测试类里有 __init__ 方法 → pytest 静默跳过整个类。 AI 时不时会生成这种。删掉 __init__
command not found: pytest 没 activate,或装到了别的 Python。用全路径 .venv/bin/python -m pytest
import file mismatch 两个子目录里有同名测试文件 → 给 tests/ 各子目录加空的 __init__.py
接口测试报「端口已被占用」 写死端口了 → 用 make_server(port=0) 让系统随机分配
测 404 时说「接口挂了」 urllib 把 4xx 当异常抛 → 要 except urllib.error.HTTPError 接住
JSON 里中文变成 咖啡 json.dumps 默认转义 → 加 ensure_ascii=False
ruff 催你把 Dict[str,Any] 改成 dict[str,Any] 你选了 UP 规则但用的是 Python 3.9 → 从 select 里去掉 "UP"

八、CLAUDE.md 模板

放在项目根目录,每次开新对话自动加载。它同时扮演两个角色: Python 缺失的那个 scripts,以及规矩的存放处。

# myshop 项目说明

## 环境
- Python 3.9,虚拟环境在 .venv/
- 所有命令都用 .venv/bin/python -m xxx 的形式
- 不要用系统 python,不要 pip install 到全局

## 本项目的命令(请严格使用,不要自己发明)
- 全量测试:  .venv/bin/python -m pytest -q
- 单文件测试:.venv/bin/python -m pytest tests/test_price.py -q
- 类型检查:  .venv/bin/python -m mypy --check-untyped-defs myshop tests
- 规范检查:  .venv/bin/python -m ruff check .
- E2E(只在最后跑):.venv/bin/python -m pytest tests/e2e/

## 硬性约束
- 修 bug / 改行为时,不要修改现有测试的断言。
  如果你认为某条断言本身写错了,停下来告诉我原因,由我决定。
- 不许用 skip / 注释掉 / 放宽断言 / 加 sleep 的方式让测试变绿
- 每次只做一步,做完停下等我检查,不要连着做下一步
- 报告结果时贴命令的真实输出,不要只说"通过了"
- 不要改本次任务范围之外的文件

## 提交规范
- 提交信息格式:type: 简短说明(feat / fix / chore / docs / test)
- 一次提交要能用一句话讲清楚
建 CLAUDE.md 的时机:第 0 步,不是「高级技巧」 很多教程把它放在最后当进阶内容。其实它应该在建项目时就有—— 因为它同时解决了「Python 没有统一命令入口」和「每次都要重复说约束」两个问题。

懒得手写就跑 /init 生成初稿,再按上面的模板补。控制在 200 行内。

再进一步:自定义命令和 hooks

手段怎么做强度
CLAUDE.md 项目根目录建文件 指令级 —— AI 理论上可以不照做
自定义 slash command .claude/skills/check/SKILL.md 里写 Markdown 指令,之后打 /check 指令级,但省打字
Hooks .claude/settings.json 配置 强制级 —— 在固定生命周期点执行 shell 命令,不依赖模型判断
Hooks 的代价 可以配成「每次编辑完自动跑检查」,但要注意:它是每次编辑后都跑。 全量测试慢的项目会拖垮体验——建议只挂 mypy 或只跑最快的那一层。

具体的事件名和字段格式各版本略有差异,配之前先查一下你这个版本的 hooks 文档, 别照抄网上的旧写法。
建议的推进顺序 先手打几轮把流程跑熟 → 觉得某句话每次都要说 → 写进 CLAUDE.md → 某组命令总是一起跑 → 做成 /check → 某个检查绝对不能漏 → 上 hook。

不要一上来就配一堆自动化。你得先知道自己需要什么,才知道该固化什么。
