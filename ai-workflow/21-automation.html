固化流程与会话管理

一、为什么要固化

三种「让规矩生效」的方式,可靠性差着数量级
级别方式可靠性失效原因
最弱每次对话里口头说一遍 很低 你会忘;换个会话就没了;说法每次不一样
中写进项目说明文件 中 AI 每次会读到,但遵不遵守靠它自觉
最强挂成钩子 / 云端门禁 高 机器执行,不商量。但只能表达能自动判定的规则

这三级正好对应第 16 页那张八关图的三个位置: 口头 = 什么都不是;说明文件 = 本地提醒;钩子和门禁 = 真拦。

策略:能自动判的往下沉到最强级,判不了的写进说明文件。

二、项目说明文件

项目说明文件CLAUDE.md每次自动读
① 定义

项目根目录下一个叫 CLAUDE.md 的普通文本文件。 每次在这个项目里开始对话时,它的内容会自动被读进上下文,不用你贴。

② 类比

贴在工位上的便签条。

新来的同事不用问你「咖啡机怎么用、代码怎么提交、周会几点」—— 这些事写在墙上,他自己会看。

关键在于:便签条上该写的是「本工位特有的规矩」,不是通用常识。 写「电脑要开机才能用」纯属浪费墙面 —— 这条对应第四节。

③ 位置

它是第 13 页那些工具用法的「持久化版本」。 你在对话里说的话只活一次;写进这个文件的话每次都在。

④ 例子

给 myshop 写一份完整的:

# 文件:<你的项目>/myshop/CLAUDE.md

# myshop

一个用来练习「AI 协作标准流程」的最小 Python 项目。

## 怎么跑

本项目必须用虚拟环境里的 Python,不要用系统的:

```bash
cd <你的项目>/myshop
.venv/bin/python -m ruff check .     # 代码规范
.venv/bin/python -m mypy             # 类型检查
.venv/bin/python -m pytest -m p0 -q  # 只跑 P0 核心用例
.venv/bin/python -m pytest -q        # 全部测试
```

四条命令的顺序不要变:便宜的先跑(fail fast)。

## 目录

- `myshop/price.py` — 纯函数,分转价格字符串。没有任何依赖,最好测
- `myshop/order.py` — 下单,会写 SQLite
- `myshop/api.py`   — HTTP 接口
- `myshop/web.py`   — 网页(最小下单页,E2E 的落点)
- `tests/`          — 单元 / 集成 / 接口
- `tests/e2e/`      — 端到端,没装浏览器驱动时会自动跳过

## 改代码的规矩

1. 修 bug 时只准改源码,不准改测试文件。
   如果你认为测试本身写错了,先停下来告诉我,由我决定。
2. 不准新增跳过标记。需要跳过时先说明理由等我同意。
3. 不准删除已有的测试用例。用例只能增加。
4. 新写的每条测试必须有断言。
5. 不准修改门禁配置(`.github/workflows/`、`pyproject.toml` 里的阈值)。
6. 同一个方法失败两次就停下来问我,不要试第三次。
7. 每做完一步跑一遍测试,然后告诉我你改了哪几个文件。

## 已知的坑

- 系统 Python 是 3.9.6,虚拟环境里也是 3.9.6,
  但云端流水线用 3.12 — 写代码时不要用 3.10+ 才有的语法。
- `tests/e2e/` 下的用例在本地默认跳过,这是预期行为,不用去"修"它。
⑤ 误区

误区 1:「写得越全越好」。反了。 它每次都会占用上下文 —— 写成一本书,等于每次对话都先浪费一大截额度, 而且重点被淹没。目标是一屏能看完。

误区 2:「写了它就一定会遵守」。 不一定。它属于上表的「中」级 —— 是很强的提示,但不是强制。 真要强制,得靠第六节的钩子。

三、三个层级,各放什么

层级该写什么不该写什么
个人层 「回答用中文」「先给方案,我同意了再动手」「不要主动 commit」 任何项目相关的东西 —— 换个项目就错了
项目层 命令、目录、规矩、坑。这一层最重要 你个人的偏好 —— 同事不一定同意
子目录层 只有动这块代码才需要知道的约定 和项目层重复的内容

四、🔄 什么该写、什么不该写

这是写说明文件时最容易犯的错。判据只有一条:

只写「看代码看不出来」的东西。
✓ 该写(代码里看不出来)✗ 不该写(代码里写着呢)
必须用 .venv/bin/python 不能用系统的
—— 这条只存在于你的习惯里		 「本项目用 Python 写」
—— 看文件后缀就知道
为什么这么设计(比如「校验必须在写库之前」)
—— 意图,代码只体现结果		 逐个函数解释它在干什么
—— 读函数更准,而且不会过期
已知的坑(「e2e 跳过是预期的,别去修」)
—— 不写的话它每次都会去"修"		 完整的目录树
—— 它自己会看,而且你会忘了更新
改代码的规矩(第 20 页那七条)
—— 纯约定,代码里没有		 过去修过什么 bug
—— 存档系统的历史记录里有
命令的正确写法和顺序
—— 尤其是那些反直觉的		 通用的语言知识
—— AI 本来就会
🔄 一个反复出现的坑:说明文件会过期 代码改了,说明文件不会自动跟着改。

一份过期的说明文件比没有更糟 —— 它会让 AI 自信地按错误信息行事, 而且你还以为自己已经交代清楚了。

防守办法:少写。写得越少,过期的概率越低。 目录树、函数说明这类「代码一改就过期」的内容,坚决不写。

五、自定义命令:把七步变成一句话

自定义命令custom slash command可复用
① 定义

把一段常用的指令存成一个文件,以后打一个短名字就能调用它。

② 类比

手机上的快捷指令。

「回家模式」= 开灯 + 开空调 + 放音乐。你不用每次说三句话,说一句就行 —— 而且不会漏掉其中一步。

「不会漏」比「省字」重要得多。

③ 位置

放在项目里的 .claude/commands/ 目录下,文件名就是命令名。 这个目录进版本控制,所以全组共用同一套命令。

官方已把「自定义命令」并入「技能(Skills)」 —— .claude/commands/step.md 与 .claude/skills/step/SKILL.md 都会生成 /step,用法一样,旧文件不用动。 新建的推荐用技能写法(能带附属文件与前置数据),入门见姊妹课 知识库第 02 章。

④ 例子

把第 14 页那套七步流程固化成一个命令:

# 文件:<你的项目>/myshop/.claude/commands/step.md

按下面的流程处理我提出的需求,一次只做一步,做完停下来等我确认。

## 流程

1. **先给方案,不要写代码。** 说清楚:改哪几个文件、每个文件改什么、
   为什么这么改、有没有别的方案。
2. 等我说「可以」之后,**只做方案里的第一步**。
3. 做完立刻跑:
   `.venv/bin/python -m ruff check . && .venv/bin/python -m mypy && .venv/bin/python -m pytest -q`
4. 跑完告诉我三件事:改了哪几个文件、测试结果、有没有超出方案范围的改动。
5. 停下来等我确认,再做下一步。

## 红线

- 修 bug 只改源码,不改测试文件。
- 不新增跳过标记,不删测试用例。
- 同一个方法失败两次就停下来问我。

以后你只要打 /step 加上你的需求,这一整套就自动生效了。

⑤ 误区

误区:「命令越多越好」。 三五个就够了。命令多到你记不住名字的时候,你又会回去手打了。

说明文件 vs 自定义命令:什么放哪
项目说明文件自定义命令
什么时候生效每次对话,自动你主动调用时
放什么永远成立的事实
(怎么跑、有什么坑、红线)		 某类任务的操作流程
(七步流程、发版检查单、写测试的套路)
判据「这个我每次都要它知道」「这个我做某类事时才要」
代价每次占用上下文 → 要短不调用就不占 → 可以写长

所以第 20 页那七条红线两边都出现了 —— 短的摘要放说明文件(每次生效), 完整的流程放命令(需要时展开)。这不是重复,是分工。

六、钩子:让规矩强制生效

说明文件和命令都属于「提示」。要真拦住,得用钩子 —— 也就是第 16 页那个机制。

规矩能不能自动判怎么落地
不准改测试文件 能 —— 看改动路径 写个钩子:改动里同时含源码和测试就警告
不准新增跳过 能 —— 数数量 第 18 页的跳过数门禁,云端强制
不准删测试用例 能 —— 比用例总数(弱门禁:防纯删除,防不住删一条补一条空用例的替换) 同上,加一条「用例数不得低于主干」
不准改门禁配置 能 —— 看路径 把配置目录设为受保护路径,改它需额外审批
先给方案再动手 不能 只能写进说明文件 + 用方案模式
失败两次就停 不能 只能靠你自己数(第 20 页盲区三)
这张表就是全书的收束 能自动判的,全部沉到最强级(钩子 / 云端门禁),不要靠嘴说。

不能自动判的那两条,都要你亲自看。 其中「自己看改动」就是第 20 页说的唯一不能外包的那一件; 另一条「失败两次就停」属于第 20 页讲的盲区三 —— 两件事,不是同一件。

它们逃不掉,因为它们要的是判断,而不是执行。

七、会话管理:上下文是有限的

上下文窗口context window有上限
① 定义

AI 一次能「同时看到」的内容总量。你说的话、它的回答、它读过的每个文件、 每条命令的输出 —— 全都占用这个额度。

② 类比

一张办公桌的桌面。

你可以在上面同时摊开十几份文件。但桌子就那么大 —— 再多就得把旧的收进抽屉,而收进去的东西它就不再"一眼看得见"了。

所以:桌上摊的东西越少、越相关,它干活越准。 摊了一堆无关的旧文件,它会被干扰。

③ 位置

它解释了为什么长会话会越聊越差,也解释了为什么第二节说「说明文件要短」。

④ 例子
动作效果什么时候用
清空把桌面全清掉,从零开始 换了一个完全无关的任务时。最常用
压缩把之前的对话浓缩成摘要,留住结论丢掉过程 同一个任务做得很久,快满了,但你还需要前面的结论
新开会话等同于清空,但保留旧会话可以回去看 想留个记录时
⑤ 误区

误区 1:「一个会话从早用到晚最省事」。 恰恰相反。桌面上堆了三个不相关任务的资料, 它会把上午那个任务的假设,带到下午这个任务里来。

误区 2:「清空了它就什么都不知道了」。 不会。项目说明文件会重新读一遍 —— 这正是把关键信息写进文件、而不是留在对话里的理由。

一条实用规则 换任务就清空。

代价几乎为零(说明文件会自动重读),收益是每个任务都从干净桌面开始。

判断标准很简单:如果新任务不需要前面的任何结论,就清空。

八、一次一件事

本页最后一条,也是最容易被忽略的一条工作习惯。

✗ 一次说一堆✓ 一次一件
「帮我把价格格式化修一下,顺便加个折扣功能,再把接口改成返回 JSON, 对了测试也补一下」 「先只做一件事:把 format_price 的货币符号改回 ¥。改完跑测试,告诉我改了哪些文件。」
改动几百行,散在八个文件里 改动几行,一个文件
测试红了,你不知道是哪件事弄红的 红了就是这一件事的问题
看改动要看十分钟,于是你不看了 看改动三十秒 → 第 20 页那一步真的会被执行
撤销只能全撤,好的坏的一起丢 撤销精确到这一件
「一次一件事」为什么能同时救活其它所有防线
防线在「一次一件」下
让它自测红了 → 立刻知道是哪一步弄的
看改动三十秒能看完 → 你真的会去看
撤销只丢掉这一件,不牵连其它
存档每条记录说清一件事 → 以后能查
门禁失败原因单一 → 一眼定位

反过来说:一次做十件事的时候,上面这五条防线会同时退化 —— 不是因为它们失效了,而是因为你不再有精力用它们。

这是全书唯一一条「不需要任何工具、不需要任何配置,今天就能用」的建议。
