静态检查:不运行代码的检查

有一类检查连代码都不运行,却能在一秒内扫完你整个项目。 它极便宜、极快、覆盖 100% 的代码 —— 但它有一个结构性盲区,后面第 8 页会用五次真机实验把这个盲区暴露得干干净净。

一、静态分析:不运行代码的检查

静态分析static analysis最便宜的检查
① 定义

不执行你的程序,只把代码当文本读一遍,从中找出问题。

② 类比

校对 vs 试吃。

一份菜谱交上来,校对员不用进厨房 —— 他看一眼就知道「第 3 步写的『放入烤箱』,但前面根本没提到烤箱」, 或者「配料表里的鸡蛋在步骤里从没用到」。这些错误不需要真做一遍菜就能发现。

而试吃员必须真的把菜做出来,才知道咸淡如何。

静态分析是校对员,测试是试吃员。

③ 位置

它和「测试」是并列且互补的两类检查,不是替代关系:

测试静态分析
运行代码吗✅ 真的执行❌ 完全不运行
覆盖范围只覆盖你写了测试的部分100% 代码
能发现什么逻辑错、算错了类型错、拼写错、没用到的变量
需要人写用例吗✅ 要❌ 不用,配置一次永久生效
速度毫秒到几十分钟秒级

最后一行的「不用写用例」是它性价比无敌的原因 —— 投入一次性,收益永久。

④ 例子

本教程用两个:

工具中文叫法命令
mypy类型检查器.venv/bin/python -m mypy
ruff代码规范检查器.venv/bin/python -m ruff check .
⑤ 误区

误区 1:「静态检查过了 = 代码没问题」。 这是全书要反复拆的最大错觉。第 5 节和第 8 页会用五次实验证明它错得多离谱。

误区 2:「有测试了就不用静态检查」。 反了 —— 静态检查更便宜,应该跑得更勤。它能挡掉的问题,不该浪费测试的时间去发现。

二、类型检查器

类型检查type checking / mypy广而浅
① 定义

检查数据的「种类」对不对 —— 该给数字的地方是不是给了文字,该返回文字的函数是不是返回了数字。

② 类比

检查插头的形状。

两脚插头插不进三孔插座 —— 这个问题不用通电就能看出来,拿眼睛比一比形状就行。

但形状对了,不代表通上电灯就会亮。这句话是本页的核心,请记住它。

③ 位置

它是静态分析的一种。和另一种(代码规范检查)是并列关系,管的东西完全不重叠:

  • 类型检查:数据种类对不对
  • 规范检查:写法规不规矩、有没有低级陷阱
④ 例子

Python 本身不检查类型。你写这样的代码它照跑不误:

def add(a, b):
    return a + b

add("3", 5)      # 运行时才会炸

加上类型标注之后,检查器就能提前发现:

def add(a: int, b: int) -> int:
    return a + b

add("3", 5)      # mypy 直接报错,代码根本不用运行

它骂人长这样(真实输出):

  mypy 真实报错格式
myshop/_demo_bad.py:6: error: Incompatible return value type (got "int", expected "str")  [return-value]
Found 1 error in 1 file (checked 1 source file)
⑤ 误区

🔄 误区 1(经核实修正):报错格式里有列号。 默认没有列号,只有 文件:行号:。要列号得显式加 --show-column-numbers。 另外 message 和 [错误码] 之间是两个空格,不是一个 —— 如果你写脚本解析它,这个细节会咬人。

误区 2:「它能发现所有 bug」。见第 5 节 —— 它有一整类问题永远发现不了。

类型检查对 AI 协作的独特价值 AI 改了一个函数的签名(比如加了个参数),可能只改了它注意到的几个调用点。

类型检查会把它漏掉的全部一次性揪出来,精确到文件和行号。人工找一定会漏。

这一条在第 8 页有反面案例:当改动不涉及签名时,它就完全失效了。

三、代码规范检查器

代码规范检查linting / ruff最快
① 定义

检查写法规不规矩,以及有没有踩到已知的低级陷阱 —— 比如定义了变量却从没用过。

② 类比

作文的错别字和格式检查。

它不管你文章写得好不好,只管:有没有错别字、标点用没用对、段落格式乱不乱。 这些问题不影响「意思」,但会让读的人难受。

而其中「定义了变量却没用过」这类,往往是真 bug 的信号 —— 你本来想用它的,结果打字打错了名字。

③ 位置

和类型检查并列。它通常是所有检查里最快的一个(实测 0.02 秒), 所以在第 16、17 页的流水线里,它总是排第一个跑。

④ 例子

它骂人长这样(真实输出):

  ruff 真实报错
B006 Do not use mutable data structures for argument defaults
  --> myshop/_demo_bad.py:9:32
   |
 9 | def collect(items: List[str] = []) -> None:
   |                                ^^
   |
help: Replace with `None`; initialize within function

F841 Local variable `unused` is assigned to but never used
  --> myshop/_demo_bad.py:10:5

...(另 1 条诊断略)

Found 3 errors.
[*] 1 fixable with the `--fix` option.

注意最后那行 [*] 1 fixable —— 有些问题它能自己改掉:

.venv/bin/python -m ruff check . --fix

import 排序、多余空行这类,一秒钟全部搞定,不用麻烦 AI。

⑤ 误区

🔄 误区(经核实,这条对第 18 页很重要):「可以设置『违规数不超过 N』的阈值」。 不能。实测 ruff 0.16.3 只有布尔式判定:有违规就退出码 1,没违规就 0。 相关开关只有两个:

参数作用
--exit-zero有违规也返回 0(做「软门禁」用)
--exit-non-zero-on-fix改过文件就返回非 0

想要真正的阈值,只能自己数 —— 用 --output-format=json 拿到结构化数据再判定。 第 18 页会讲这个做法。

四、广而浅 vs 窄而深

这是理解「为什么两种检查都要跑」的关键图:

五、致命的结构性盲区

🔥 这是全书最重要的知识点之一 当一个改动「签名不变、行为变了」时,类型检查永远发现不了。

看这个例子

def format_price(cents: int) -> str:   # 改前:返回 "¥0.00"
def format_price(cents: int) -> str:   # 改后:返回 "免费"
                                        # ↑ 签名一个字符都没变
它看到的它的判断
类型检查器 进去一个 int,出来一个 str "¥0.00" 和 "免费" 都是合法的 str → 没问题
测试 期望 "¥0.00",实际 "免费" 不相等 → 失败
一句话概括这个盲区
  • 类型系统管的是:调用方能不能安全地把返回值当字符串用?能。
  • 测试管的是:这个字符串的具体内容是不是业务上正确的那个?不是。

这不是配置问题。把严格程度开到最高也抓不到 —— 这是类型系统结构性的盲区。

为什么不能靠「写得更精确」来解决

理论上类型检查有可能抓到,如果你把签名写成这样:

def format_price(cents: int) -> Literal["¥0.00", "¥12.34", "¥25.00", ...]:  # 荒谬

价格有无穷多种,不可能穷举。所以现实里 -> str 就是唯一合理的写法,而它必然对返回值内容一无所知。

两个比喻,选你喜欢的记

比喻说明
插头与灯 类型检查看插头形状对不对(两脚还是三脚),测试看通上电灯亮不亮。 形状对了,灯照样可能不亮。
杯子与醋 杯子里的水被换成了醋。杯子还是杯子(类型对),但你喝下去会知道不对(行为错)。
这个盲区会被验证五次 第 8 页会在真机上做五次「故意改坏代码」的实验。五次改动全都是「签名不变、行为变了」这一类, 结果是:

两个静态检查工具,五战五败 —— 每一次都报「一切正常」。

那不是巧合,正是这一节讲的结构性原因。

六、一个 AI 协作专属的坑

⚠ 类型检查默认不检查「没写标注」的函数体 AI 生成的测试函数经常忘了写返回类型标注(那个 -> None), 于是类型检查器对整个测试文件视而不见,你却以为「类型检查过了」。

怎么办

第 2 页给的配置里,strict = true 已经处理了这个问题。但要理解是哪个开关在起作用:

配置项它管什么包含在 strict 里吗
check_untyped_defs 「连没写标注的函数体也检查」 ✅ 是
disallow_untyped_defs 「不许有没写标注的函数」 ✅ 是
🔄 经核实修正:是后者在防 AI 漏写 很多人(包括我一开始)以为防「AI 漏写 -> None」靠的是 check_untyped_defs。不准确。

实测:严格模式下,一个没写标注的函数会被 disallow_untyped_defs 直接报成 error: Function is missing a type annotation [no-untyped-def]。

check_untyped_defs 的作用是「函数体里面也查」,是另一件事。

好消息:strict = true 把两个都打开了,所以第 2 页那份配置是够用的。
⚠ 再提醒一次那个静默失效的坑 类型检查器对拼错的配置键名只打一条 Warning,然后照常报成功。

实测把 strict 拼成 strictt: 
pyproject.toml: [mypy]: Unrecognized option: strictt = True
Success: no issues found in 10 source files

严格模式根本没开,报的却是 Success。 这是一个「假绿」—— 而假绿比直接报错危险得多,因为它让你放松警惕。
