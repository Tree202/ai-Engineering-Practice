git 回退:三件套与它们的死角

全书最容易出人命的一页。这里的命令能一秒钟抹掉你几小时的工作,而且没有回收站。 但更常见的问题不是删多了,而是 —— 你以为回退了,其实没有。

🔥 先说本页最重要的一条 最常用的那条回退命令,删不掉 AI 新建的文件。

你跑完它,发现那些文件还原封不动躺在目录里,于是以为「回退失败了」。 不是失败 —— 是它管不着那些文件。

一、先分清「跟踪」与「未跟踪」

不理解这个区分,后面所有命令的行为你都会觉得莫名其妙。

未跟踪文件untracked file核心概念
① 定义

git 从来没见过的文件 —— 你新建了它,但从没 add 过。 在状态里显示为 ??。

② 类比

没贴条码的商品。

超市的库存系统只管贴过条码的东西。有人把一箱自己带来的货放在货架上, 系统里查不到它、盘点盘不着它、退货也退不了它 —— 因为系统压根不知道它存在。

它就一直躺在那儿。

③ 位置

文件在 git 眼里只有两种身份,而这个身份决定了它会被哪条命令影响:

身份怎么变成这样回退命令管得着吗
已跟踪add 过,或已经存档过✅ 管得着
未跟踪 ??新建了但从没 add❌ 大部分管不着
④ 例子

AI 干完活之后典型的状态:

  真实输出
$ git status -s
 M report.py                    ← 已跟踪,改了
 M src/mod.py                   ← 已跟踪,改了
?? experiment_final_FINAL.py    ← 未跟踪,新建的
?? experiment_v1.py             ← 未跟踪
?? experiment_v2.py             ← 未跟踪
?? tmp_output/                  ← 未跟踪的目录

前两行和后四行,需要用完全不同的命令处理。

⑤ 误区

🔄 误区(实测发现的反直觉细节):「新建的文件都是未跟踪的」。 只要 add 过一次就不是了。
而这会导致一个惊人的结果:add 过的新文件,会被回退命令连文件本身一起删掉 (实测直接从磁盘消失);没 add 过的反而活下来。见第四节。

二、回退三件套总览

命令✅ 能回退❌ 管不了
git restore .
老写法 git checkout -- .		 已跟踪文件的未勾选改动 已勾选的改动;未跟踪的新文件
git reset --hard HEAD 已跟踪文件的所有改动(含已勾选) 未跟踪文件照样纹丝不动
git clean -fd 未跟踪的新文件和新目录 —(但先用 -fdn 预演!)

三、第一件:丢弃未勾选的改动

cd <你的项目>/myshop && git restore .

这条命令没有任何输出,静悄悄地把你还没勾选的改动一笔勾销。

  实测:它动了什么、没动什么
现场:app.py 有未勾选改动、README.md 有已勾选改动、还有两个新建的东西
$ git status -s
M  README.md
 M app.py
?? ai_notes.py
?? scratch/

$ git restore .
(无输出)

$ git status -s
M  README.md        ← 已勾选的改动:纹丝不动
?? ai_notes.py      ← 新文件:纹丝不动
?? scratch/         ← 新目录:纹丝不动
(app.py 的改动:已被抹掉)
⚠ 它的三个坑
  1. 对新建的文件完全无效 —— AI 新建的一堆文件一个都不会消失
  2. 救不回来。没存过档的改动被它抹掉就是永久丢失,后悔药也没用。 执行前先 git diff 看一眼你要丢的是什么
  3. 那个点是「当前目录」 —— 在子目录里执行只还原子目录。 记得先回到项目根目录

四、第二件:回到上次存档

cd <你的项目>/myshop && git reset --hard HEAD
部分含义
reset把指针挪回去
--hard连同工作区一起强制拉回(不加它只是取消勾选,内容保留)
HEAD「当前存档指针」,也就是最近一次存档
  真实输出
$ git reset --hard HEAD
HEAD is now at b086c7f feat: greet 支持自定义问候语

$ git status
On branch main
Untracked files:
	ai_notes.py
	scratch/

$ ls
README.md  ai_notes.py  app.py  scratch
(README 和 app.py 的改动都没了,但两个新东西一个没少)
🔥 本教程最关键的一个坑 AI 一顿操作新建了 5 个文件,你跑 git reset --hard, 然后发现那 5 个文件原封不动躺在目录里。

你以为「回退失败了」。不是失败 —— reset 只管 git「认识」的文件。 那些从没 add 过的新文件,git 压根不知道它们存在,自然也不会删。

后果不只是碍眼:下次运行程序时,这些残留文件可能被误 import、可能干扰测试收集、 可能让你以为某个功能已经实现了。
🔄 一个反直觉的细节(实测) 新文件「add 过」和「没 add 过」,命运完全相反:
  实测
$ git status -s
A  staged_new.py         ← add 过
?? untracked_new.py      ← 没 add

$ git reset --hard HEAD
$ ls
report.py  src  untracked_new.py
>>> staged_new.py 被连文件一起删掉了;untracked_new.py 活下来了

机制:add 一个新文件,它就进了「已跟踪」那一侧。 而 reset --hard 的职责是「让工作区严格等于目标存档」—— 目标存档里没有这个文件,那它就得从工作区消失。
不是 git 在「惩罚」你 add,是 add 把文件搬到了 git 管辖的那一侧。

⚠ 还有一个必须知道的例外(实测) 「reset --hard 不删未跟踪文件」只在回到 HEAD 时成立。

如果你 reset 到另一个存档,而那个存档里恰好有同名文件, 你的未跟踪文件会被静默覆盖。
  实测
$ printf 'MY PRECIOUS UNTRACKED WORK\n' > shared.txt
$ git status -s
?? shared.txt

$ git reset --hard HEAD~1    ← 上一个存档里有 shared.txt
HEAD is now at 7a40b36 c2 adds shared.txt
>>> 你写的内容被存档里的版本静默覆盖了

五、第三件:清掉新文件

规矩:永远先预演 -n 是预演(只说要删什么,不真删),-f 才是真删。
口诀:先 n 后 f。

第一步:预演

cd <你的项目>/myshop && git clean -fdn
  真实输出
Would remove ai_notes.py
Would remove scratch/
(预演之后文件全都还在)

第二步:确认无误再真删

cd <你的项目>/myshop && git clean -fd
  真实输出
Removing ai_notes.py
Removing scratch/

参数含义

参数含义不加会怎样
-n预演直接真删
-f确认执行被拒绝,见下
-d连目录一起整个未跟踪目录及其内容全部跳过 — 见下
-x☢️ 连忽略清单里的也删别加
🔄 关于 -d,经核实修正了一处常见的错误说法 很多教程说「不加 -d 只列文件、不列目录」。机制说得不准,会误导。

真实行为:不加 -d 时,git 根本不会进入未跟踪的目录 —— 那个目录本身和它里面的全部文件都不列、不删。
  实测
$ git clean -n          ← 不加 -d
Would remove ai_notes.py
>>> newdir/sub/deep.txt 完全不出现,连文件都没列

$ git clean -fdn        ← 加了 -d
Would remove ai_notes.py
Would remove newdir/

所以「以为清干净了其实没有」的风险比想象中大 —— 一整个目录连同内容都被跳过了。

三个必须知道的行为

情况结果
忘了加 -f 
fatal: clean.requireForce defaults to true and neither -i, -n, nor -f given; refusing to clean
这是保护机制,不是报错。
-x 是核弹级 它会把忽略清单里的东西一起删光。实测:git clean -fdx 直接蒸发了一个 9MB、569 个文件的虚拟环境,密钥文件也会没。 没有明确理由绝不要加。
嵌套的 git 仓库 如果某个未跟踪目录里面有 .git,单个 -f 删不掉它,需要 -ff。 官方原文:「Git will refuse to modify untracked nested git repositories … unless a second -f is given.」
⚠ clean 删掉的东西没有回收站 不进回收站、不进 git、后悔药也没有,永久消失。

所以必须先 -fdn 预演。预演清单里如果出现你想留的东西 (比如 AI 生成的一份不错的文档),先复制出来或者 git add 保住它。

六、完整还原的标准四步

背下这四步 —— 口诀:先 reset 后 clean;clean 先 n 后 f 
cd <你的项目>/myshop && git status
cd <你的项目>/myshop && git reset --hard HEAD
cd <你的项目>/myshop && git clean -fdn
cd <你的项目>/myshop && git clean -fd

完整实测记录

  AI 改了 2 个文件 + 新建 3 个文件 1 个目录
$ git status -s
 M report.py
 M src/mod.py
?? experiment_final_FINAL.py
?? experiment_v1.py
?? experiment_v2.py
?? tmp_output/

$ git reset --hard HEAD
HEAD is now at 622dcb3 docs: 用 -am 一步提交

$ ls
experiment_final_FINAL.py  experiment_v1.py  experiment_v2.py  report.py  src  tmp_output
↑↑↑ 已跟踪文件的改动没了(对),但新建的 4 个东西一个都没删!

$ git clean -fdn
Would remove experiment_final_FINAL.py
Would remove experiment_v1.py
Would remove experiment_v2.py
Would remove tmp_output/

$ git clean -fd
Removing experiment_final_FINAL.py
Removing experiment_v1.py
Removing experiment_v2.py
Removing tmp_output/

$ ls
report.py  src
$ git status -s
(空 = 彻底回到 AI 动手之前)
前提:让 AI 动手之前,你的工作区必须是干净的 否则这套四步会把你自己没存档的活儿一起抹平。

这就是第 11 页那句「工作区必须干净」的第二个理由 —— 它不只影响看改动,还影响你能不能安全回退。

七、回到某个旧存档

先找到目标存档的编号:

cd <你的项目>/myshop && git log --oneline
方式命令特点
只是去看看 git checkout 编号 历史一点不改。会提示进入「游离」状态 —— 听着吓人,其实就是「你现在站在一次存档上,而不是站在某条分支上」。
回来:git switch -
真的退回去 git reset --hard 编号 危险:后面的存档从这条分支上消失
最安全 git revert 编号 历史不改,只追加一个「反做」的存档。团队协作时用这个
后悔药:找回被 reset 掉的存档 
cd <你的项目>/myshop && git reflog

它记录了 HEAD 的每一次移动,包括被你 reset 掉的那些。 找到编号后 git reset --hard 那个编号 就能回去。

⚠ 但后悔药有明确边界
丢失的东西能找回吗
已存档的内容(被 reset 掉的提交)✅ 能
没存档的改动(被 restore / reset --hard 抹掉的)❌ 不能,永久丢失
被 clean 删掉的新文件❌ 不能

一句话:存过档的救得回,没存过档的救不回。 这又回到了那条最根本的规矩 —— 存得勤一点。

八、忽略清单的最大陷阱

⚠ 忽略清单只对未跟踪文件生效 文件一旦被存档过,后加规则完全无效。

新手 90% 的「忽略清单不管用」都是这个原因。

怎么补救

cd <你的项目>/myshop && git rm -r --cached __pycache__
cd <你的项目>/myshop && git commit -m "chore: 把缓存目录从版本库里移除"
🔥 --cached 这个词千万别漏
写法后果
git rm -r --cached 路径只从 git 里移除,磁盘文件保留
git rm -r 路径磁盘上的文件真删了

对密钥文件漏加 --cached 就是灾难。

💡 调试忽略规则的唯一正解 「为什么我写的规则不生效?」—— 别猜,直接问它: 
cd <你的项目>/myshop && git check-ignore -v 某个文件

它会告诉你这个文件被哪个文件的第几行规则命中。 没有输出就说明没有任何规则匹配它。

两个规则写法细节
  • .venv/ 带尾斜杠 = 只匹配目录;.venv 不带 = 同名的文件和目录都匹配
  • 历史里的旧版本依然存在 —— 如果泄露的是密钥,必须视作已泄露并立刻更换, 光从 git 里移除是不够的

九、新手报错速查

看到什么怎么办
fatal: not a git repository当前目录没有仓库 → git init,或者你 cd 错地方了
Please tell me who you are第一次用,没配名字 → 见第 11 页第二节
refusing to clean忘了加 -f → 先用 git clean -fdn 预演
nothing to commit, working tree clean不是报错,是「干净」的意思 —— 好消息
You are in 'detached HEAD' state不是报错。你切到了一次存档而不是分支 → git switch - 回去
终端卡在一个冒号不动进了分页器 → 按 q
突然进了个奇怪的编辑器退不出来是 vim → 按 Esc,再输入 :wq 回车

🔄 关于「路径不匹配」这类报错 —— 四种措辞都不一样

  实测四种
$ git add nosuchfile.txt
fatal: pathspec 'nosuchfile.txt' did not match any files                (退出码 128)

$ git rm nosuchfile.txt
fatal: pathspec 'nosuchfile.txt' did not match any files                (退出码 128)

$ git restore nosuchfile.txt
error: pathspec 'nosuchfile.txt' did not match any file(s) known to git  (退出码 1)

$ git checkout nosuchbranch
error: pathspec 'nosuchbranch' did not match any file(s) known to git    (退出码 1)

$ git switch nosuchbranch
fatal: invalid reference: nosuchbranch                                  (退出码 128)
最后两行的对比,就是「为什么该用 switch」 git checkout nosuchbranch 报「路径不匹配」对新手极其困惑 —— 我明明在切分支,你跟我说文件路径?

根源是 checkout 职责重载:它先当分支名解释,解释不通就退回去当文件路径解释。
而 switch 只管分支,所以能直接给出人话。
分支切不过去的三个常见原因
  • 分支名拼错了 → git branch 看看有哪些
  • 分支只在远端存在 → 先 git fetch
  • 文件名大小写 → macOS 默认文件系统不区分大小写,但 git 区分,容易出怪事
