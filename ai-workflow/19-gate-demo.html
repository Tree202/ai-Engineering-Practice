一、实验设置

项内容

门禁配置第 18 页第九节那份 ci.yml 的三道检查版,任务名 三道检查

这本身也是一条规矩:让 AI 帮你操作外部服务时, 走已登录的命令行工具,不要把密码贴进对话框。

BLOCKED → CLEAN 这一次状态跳变,是整页最关键的一行输出 它证明了:状态不是人改的,是「把代码改对」这个动作换来的。

中间没有任何人点过「批准」、没有人改过规则、没有人重跑过流水线。 唯一变的是代码本身。

三、怎么配分支保护规则

门禁的「拦」这个动作,不在流水线配置里,而在托管平台的分支保护规则里 —— 这正是第 17 页说的三层拦截中的第 ① 层。

# 用命令行配(以 GitHub 为例)
# 关键点全在 required_status_checks.contexts 这个数组里

gh api -X PUT repos/<账号>/myshop-gate-demo/branches/main/protection \
  --input - <<'JSON'
{
  "required_status_checks": {
    "strict": true,
    "contexts": ["三道检查"]
  },
  "enforce_admins": true,
  "required_pull_request_reviews": null,
  "restrictions": null
}
JSON
字段这里填的含义
contexts["三道检查"] 必须通过的检查名单。这个名字要和流水线里 name: 写的一字不差
stricttrue 要求分支先同步主干最新代码再合。防止「各自都绿,合起来炸」
enforce_adminstrue 管理员也受限。这一项是第 4 节的全部内容
required_pull_request_reviewsnull 本次实验不要求人工评审 —— 为了证明「纯机器判定也能拦住」
🔥 名字对不上,是新手配门禁最常见的翻车点 contexts 里填的必须是任务的名字,不是流水线文件的名字,也不是步骤的名字。

回看第 18 页那份配置: 
jobs:
  gate:                    ← 这是任务的 id,不是它
    name: 三道检查          ← 要填的是这个

填错的后果不是报错,而是永久等待 —— 平台在等一个叫这个名字的检查上报结果,而那个检查根本不存在。 合并请求会一直卡在「等待中」,而且没有任何错误信息告诉你为什么。

这和第 17 页那个 paths 死锁是同一类问题的两个入口: 第 ① 层在等一个第 ② 层永远不会给的答复。

四、🔥 连管理员也绕不过

这是全页最有力的一幕。我是这个仓库的所有者、管理员,拥有全部权限。 我用带「强制」参数的命令去合并那个红着的请求:

  🔥 仓库所有者尝试强制合并
$ gh pr merge 1 --squash --admin

failed to merge pull request: GraphQL: Required status check
"三道检查" is failing (mergePullRequest)

$ echo $?
1
为什么这一幕比前面所有幕加起来都重要 --admin 这个参数的字面意思就是「用管理员权限跳过保护规则」。 它在很多配置下是真的能跳过的。

它这次跳不过,唯一的原因是规则里写了 enforce_admins: true。

enforce_admins结果
false(默认值) 管理员可以强制合并 → 门禁对管理员形同虚设
true 所有人一视同仁 → 这才符合第 17 页「不接受人为通融」的定义

换句话说:一个门禁是不是真门禁,取决于这一个布尔值。 它默认是关的 —— 所以大量团队自以为有门禁,其实管理员一句话就能合。

注意错误信息的来源 报错里的 GraphQL 说明这个拒绝发生在服务端,不是本地工具替你挡的。

这个细节很重要:本地工具的检查可以靠改工具、换工具、直接调接口来绕过; 服务端的拒绝不行 —— 除非你有权限去改规则本身。

这也是「门禁必须在云端」这个结论的技术根据。

我的 Mac云端流水线

Python3.9.63.12.13(差 3 个大版本)
测试运行器8.4.29.1.1(差 1 个大版本)
依赖来源本地虚拟环境,装了半年全新安装,当天最新
坏代码时的结果 8 failed, 9 passed, 1 skipped in 3.66s 8 failed, 9 passed, 1 skipped in 3.66s

注:耗时为 macOS 环境实测值;Linux 环境的红绿计数一致,耗时未逐字核录。

这条数据同时证明了两件相反方向的事
如果两边结果一致如果两边结果不一致
说明这是个真 bug,和环境无关。
→ 老老实实改代码		 说明这是个环境问题。
→ 去查版本、依赖、配置差异,而不是改业务逻辑

这就是流水线最被低估的价值:它不只是「再跑一遍」, 它是一个和你不一样的对照组。

「在我机器上是好的」这句话之所以能被终结, 不是因为云端更权威,而是因为多了一个独立样本。

六、🔥 我诊断错了一次:复盘

这一节保留了我在这次实验里犯的一个真实错误,因为它的排查过程比结论更有价值。

阶段发生了什么
现象 我用接口查这次推送触发的流水线运行记录,连查 12 次全是「找不到」
我的推断 「平台把这次推送事件丢弃了,流水线根本没被触发」
事实 流水线一直都在,而且是绿的,27 秒就跑完了 —— 这条绿的是建仓库时那次推送触发的运行;坏代码那次推送的运行是红的,就是第二节那个 fail。 用浏览器一看就在页面上
真正原因 我查的那个接口路径 / 参数不对,返回「找不到」不等于「东西不存在」
🔥 这个错误的教训,比这一页任何一条门禁知识都通用 「我没查到」和「它不存在」是两件事。

我把观测手段的失败当成了被观测对象的失败。 更糟的是,我重复了 12 次同一个错误的观测 —— 这只增加了我的信心,没有增加任何信息量。

正确的做法是换一种观测方式。换成浏览器直接看页面,三秒钟就发现真相了。
推广成一条排查规则 同一个方法失败两次以上,不要再试第三次 —— 换一个完全不同的观测通道。

通道例子
命令行接口查不到 → 换下面的
网页界面最直观,人眼一看就知道
日志 / 事件流看事件到底有没有到
换个账号 / 换台机器排除权限和缓存问题

这条规则对 AI 尤其重要 —— AI 会非常自信地重复同一个失败的方法,并在每次失败后给出一个更详细的错误解释。 你要做的是打断它,让它换个通道。

七、两个状态字段,别看混了

排查合并请求为什么合不进去时,会看到两个长得很像的状态。它们回答的是不同的问题:

字段回答什么问题 典型取值什么时候看它
mergeable 代码本身能不能合? MERGEABLE / CONFLICTING 只管有没有冲突,完全不管门禁
mergeStateStatus 现在到底让不让合? CLEAN / BLOCKED / BEHIND / UNSTABLE 这才是你要看的那个 —— 它综合了门禁、评审、同步状态
最容易看混的一种情况 
mergeable        = MERGEABLE   ← "能合啊,没冲突"
mergeStateStatus = BLOCKED     ← "但门禁没过,不让合"

只看第一个字段,你会得出「一切正常但按钮是灰的,平台出 bug 了」的结论。 实际上两个字段都对,只是它们回答的问题不同。

mergeStateStatus含义对应第 17 页哪一层
CLEAN全绿,可以合—
BLOCKED被保护规则挡住第 ① 层(可能因为门禁红了,也可能缺评审)
BEHIND落后于主干,要先同步第 ① 层的 strict: true
UNSTABLE有检查红了,但那条检查不是必需的第 ③ 层,失败动作是降级告警
DIRTY有代码冲突—
UNSTABLE 正好是第 17 页「降级告警」的实物 它的意思是:确实有检查是红的,但因为你没把它写进必需名单,所以它拦不住合并。

这就是第 17 页那张「失败动作」表在真实平台上的样子:
想要的失败动作怎么配
阻断把这条检查写进 contexts 名单
降级告警让它跑,但不写进名单 → 红了只显示 UNSTABLE

所以第 17 页那个「三阶段落地路径」在这个平台上的实现极其简单: 先不写进名单(告警),稳定后再写进名单(阻断)。改一个数组而已。
