一、为什么要有个练习项目

因为测试这件事,不动手是学不会的 你可以读一百遍「测试很重要」,但只有当你亲眼看见 「我改了一个字符,屏幕上跳出 8 行红字」的时候,你才真的懂了。

myshop 就是那个让你能亲眼看见的东西。

它做的事情简单到一句话

你告诉它「一杯咖啡 12.5 元,买 2 杯」,它回你「一共 25 元」,并把这笔订单记下来。

没有登录、没有支付;页面也只有「下单成功」那一条最小流程(web.py,专给第 4 层 E2E 点的)。 但它有该有的四样东西:跨模块调用、真数据库、真网络接口、可点的页面 —— 正好能演示金字塔的四层。

三、核心设计:三个文件按依赖排列

这是整个项目最重要的一句话 三个源码文件按「依赖从少到多」排列,而这个顺序,恰好就是测试金字塔的层级。
依赖方向是单向的 —— 注意没有任何反向箭头 price.py 不知道 order.py 存在,order.py 不知道 api.py 存在。

这个约束带来两个好处:
  1. 可以单独测最底层 —— 测 price 不需要数据库、不需要服务器
  2. 爆炸半径可预测 —— 改 api 影响不到别人;但改 price 会波及所有上层

第二条就是第 8、9 页那些事故的根源:一个函数的爆炸半径,和它的代码行数成反比。

四、最底层:纯函数

# 文件:项目根目录/myshop/price.py
"""价格模块:全项目最「纯」的一块。

纯 = 只做计算。不读数据库、不发网络请求、不看时间、不改全局变量。
同样的输入永远得到同样的输出 —— 这种函数是单元测试最好啃的骨头。
"""


def format_price(cents: int) -> str:
    """把「分」换算成人类看的价格字符串。

    1234 -> "¥12.34"
    """
    if cents < 0:
        raise ValueError("价格不能为负数")
    # divmod(1234, 100) 一次返回 (12, 34):12 块、34 分
    yuan, fen = divmod(cents, 100)
    # :02d 表示不足两位就在前面补 0,所以 5 分会变成 "05"
    return f"¥{yuan}.{fen:02d}"

「纯」是什么意思

纯函数pure function最好测
① 定义

一个只做计算的函数:同样的输入,永远得到同样的输出,而且不改变外部世界的任何东西。

② 类比

计算器 vs 自动售货机。

计算器:你按 2+3,它永远显示 5。按一百遍都一样,而且不会因为你按了它就少一瓶饮料。

自动售货机:你按同一个按钮,第一次给你可乐,第二次可能显示「售罄」—— 因为它有状态,而且你的操作改变了它。

③ 位置

它是金字塔最底层的被测对象。因为它不依赖任何外部东西,所以测它不需要任何准备工作 —— 这就是第 5 页说的「准备段重量为零」。

④ 例子
它不做的事如果做了会怎样
不读数据库测试就得先准备一个数据库
不发网络请求测试就得联网,还可能超时
不看当前时间今天跑通了,明天可能挂
不改全局变量跑第二遍结果可能不一样
⑤ 误区

误区 1:「纯函数就是简单函数」。不是。一个几百行的复杂算法也可以是纯的, 只要它不碰外部世界。「纯」说的是有没有副作用,不是复杂度。

误区 2:「抛异常就不纯了」。不影响。抛异常也是一种确定的输出 —— 同样输入 -1,它永远抛同一个异常。

两个值得学的细节

写法为什么这么写
divmod(1234, 100) 一次返回 (12, 34) —— 商和余数一起给你。比写两次 // 和 % 干净
{fen:02d} 02 的意思是「不足两位就在前面补 0」。没有它,5 分会显示成 ¥0.5 而不是 ¥0.05 —— 这是格式化的经典 bug,第 8 页第一个实验就是它

五、中间层:跨模块 + 存数据

这是集成测试的主角。它在一个函数里同时干了两件单元测试盖不住的事:

# 文件:项目根目录/myshop/order.py (节选)——完整代码见配套 myshop 项目
import sqlite3
from contextlib import closing
from typing import Any, Dict, Optional

from myshop.price import format_price     # ← 事件 1:依赖了另一个模块


def create_order(
    item: str,
    unit_cents: int,
    qty: int,
    db_path: Optional[str] = None,
) -> Order:
    """下一单:校验 -> 算钱 -> 写库 -> 返回订单。

    注意顺序:所有可能抛异常的事情都必须发生在写库 **之前**。
    否则订单已经写进数据库了才报错,库里就留下了脏数据。
    """
    # ---- 1. 先把所有校验做完 ----
    if qty <= 0:
        raise ValueError("数量必须大于 0")
    if unit_cents < 0:
        raise ValueError("单价不能为负数")

    total_cents = unit_cents * qty

    # ---- 2. 再把所有可能抛异常的计算做完 ----
    # format_price 对负数会 raise。放在写库前面调用,
    # 保证「要么整单成功,要么库里什么都没有」。
    total_text = format_price(total_cents)

    # ---- 3. 最后才动数据库 ----
    path = _path(db_path)
    init_db(path)

    with closing(sqlite3.connect(path)) as conn:      # ← 事件 2:真的写进数据库
        cur = conn.execute(
            "INSERT INTO orders (item, qty, total_cents) VALUES (?, ?, ?)",
            (item, qty, total_cents),
        )
        # lastrowid 在类型上可能是 None,用 or 0 兜底,类型检查才不会报错
        order_id = cur.lastrowid or 0
        conn.commit()

    return {
        "id": order_id,
        "item": item,
        "qty": qty,
        "total_cents": total_cents,
        "total_text": total_text,
    }

这里的三段式顺序是整个项目最重要的一课

🔥 所有可能抛异常的事情,必须发生在写数据库之前 如果把 format_price 挪到写库之后调用 (这是很自然的写法,毕竟它「只是拼个显示文案」),单价为负时就会: 
写库 ✅  →  算 format_price  →  💥 抛异常
                                     ↑
                          库里已经留下一条脏数据了

这个 bug 有多隐蔽?第 8 页会实测:类型检查完全看不出来,而且如果没人想到写那条测试,全量测试也抓不到。

三个值得学的细节

写法为什么这么写
closing(...) 保证连接一定被关掉,哪怕中间抛了异常。不用它的话,异常路径上会漏连接
cur.lastrowid or 0 这个值在类型上可能是「空」,直接返回类型检查会报错。or 0 兜个底。 这行就是类型检查逼你考虑边界的例子
conn.commit() 确认提交 —— 下面单独讲,它是第 8 页第五个实验的主角

commit 是什么

确认提交commit数据库概念
① 定义

数据库有个规矩:你写进去的东西,要「确认提交」之后才算数。

② 类比

在超市结账。

超市数据库
把商品放进购物车执行写入语句
到收银台付钱conn.commit()

没付钱就走出超市,东西不是你的。数据库也一样 —— 没提交就关闭连接,刚写的东西全部作废。

③ 位置

⚠️ 注意这个词有两个完全不同的含义,别混:

出现在哪意思
数据库(本页)确认提交刚写的数据
存档系统(第 11 页)按一次存档键

两者没有任何关系,只是碰巧同名。

④ 例子

第 8 页会把这一行注释掉,然后看到这一幕:

  真实实验输出
create_order 返回: {'id': 1, 'item': '咖啡', 'total_text': '¥25.00'}
  ↑ 完全正常!有订单号、金额对、文案对

换个连接去数数据库里有几条订单: 0
  ↑ 一条都没有

函数返回「成功」,数据库里什么都没有。这是最阴险的一类 bug。

⑤ 误区

误区:「同一个连接里能读到,说明存进去了」。 错。在同一个连接里,没提交的数据照样能读到 —— 你读的是自己那笔「还没结账的购物车」。
这就是第 5 页那个「换个连接读回来」技巧存在的全部原因。

六、最上层:只做翻译

# 文件:项目根目录/myshop/api.py (节选)——完整代码见配套 myshop 项目

class ShopHandler(BaseHTTPRequestHandler):
    def do_POST(self) -> None:
        if self.path != "/orders":
            self._send(404, {"error": "没有这个接口"})
            return

        length = int(self.headers.get("Content-Length") or 0)
        raw = self.rfile.read(length) if length else b"{}"

        # 解析必须放在 try 里面:客户端发来的东西不一定是合法格式。
        # 放在外面的话,一个畸形请求就会让服务器抛未捕获异常 -> 500,
        # 而设计上这应该是一个规规矩矩的 400。
        try:
            body: Dict[str, Any] = json.loads(raw)
        except json.JSONDecodeError:
            self._send(400, {"error": "请求体不是合法的 JSON"})
            return

        try:
            order = create_order(
                item=str(body["item"]),
                unit_cents=int(body["unit_cents"]),
                qty=int(body["qty"]),
            )
        except KeyError as exc:
            self._send(400, {"error": f"缺少字段 {exc}"})
            return
        except (TypeError, ValueError) as exc:
            self._send(400, {"error": str(exc)})
            return

        self._send(201, order)
它自己不算钱、不写库 它的唯一职责是:把网络请求翻译成函数调用,再把结果翻译回去。

这叫薄接口层,是好的分层设计。判断标准很简单: 把 api.py 整个删掉,业务逻辑一行都不会丢。

三个实用技巧藏在这里

技巧代码为什么
随机端口HTTPServer(("127.0.0.1", 0)) 0 = 让系统挑一个空闲端口。写死端口的话,你本地开着开发服务器时测试就跑不了
中文不乱码json.dumps(..., ensure_ascii=False) 不加这个,「咖啡」会变成一串转义码
静音日志重写空的 log_message 默认每个请求都往终端打一行,跑测试时会淹没结果

八、这个项目里曾经藏着两个真 bug

这个项目最初的版本有两个真实的 bug。它们已经修好了,但值得单独讲 —— 因为它们恰好演示了「全量测试也抓不到你压根没写的用例」。

Bug问题后果
order.py format_price 在写库之后才调用,而且单价从头到尾没校验 单价为负时:先把订单写进数据库,然后才抛异常 —— 库里留下脏数据
api.py 解析请求体写在 try 外面 一个畸形请求 → 未捕获异常 → 客户端拿到 500(设计上该是 400),终端还刷一屏错误

修复的同时补了两条测试

新增的测试它守着什么
test_单价为负数也要被拦下来并且不写库 校验顺序 —— 异常抛出后,库里必须一条记录都没有
test_请求体不是合法_JSON_要返回_400_而不是_500 容错行为 —— 是你请求发错了,不是我崩了
这两个 bug 的教学价值 第 8 页会实测把它们改回去,然后你会看到:
  • 类型检查完全看不出来 —— 报「一切正常」
  • 如果没有那两条新测试,全量测试也是绿的 —— 原版 4 条集成测试全过
  • 只有「你想到要测这个场景」才能发现它
这就是「测试覆盖率」的真正含义 测试只能证明「你想到要检查的东西」是对的,不能证明「代码是对的」。

所以第 4 步(你自己看改动)永远不能省 —— 它是唯一能发现「这里应该还有个用例没写」的环节。机器只会跑你写下的东西。
