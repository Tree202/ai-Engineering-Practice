把下面这条整个复制粘贴进去,回车:

你应该看到类似这样的东西

  真实输出(macOS 15.7.4)

git version 2.39.5 (Apple Git-154)

这一行的意思说明

二、虚拟环境:每个项目自己的一套厨具

虚拟环境virtual environment / venv必须理解
① 定义

一个只属于这一个项目的、独立的 Python。它是项目文件夹里的一个子文件夹, 你往它里面装的任何东西,都只影响这一个项目。

② 类比

公共厨房的锅 vs 这道菜专用的锅碗瓢盆。

系统自带的 Python 是公共厨房那口大锅 —— 所有项目抢着用。 A 项目要 1.0 版的某个工具,B 项目要 2.0 版,两边一打架,两个项目都跑不起来。

虚拟环境是给这道菜单独配一套锅碗瓢盆,全放在项目里的 .venv 文件夹。 不要了就把整个文件夹删掉,不留痕迹,也不影响任何人。

③ 位置

它是所有后续操作的前置。第 3 页的测试工具、第 4 页的检查工具,全装进它里面。

它和「系统 Python」是并列关系 —— 两个互不干扰的 Python,你选择用哪个。

④ 例子

先建项目文件夹并进去(把 <你的项目> 换成你自己放代码的目录):

mkdir -p <你的项目>/myshop
cd <你的项目>/myshop

然后建虚拟环境:

python3 -m venv .venv

这条命令没有任何输出,没输出就是成功了。检查一下:

.venv/bin/python --version
  真实输出
Python 3.9.6

这个 .venv/bin/python 就是本项目专属的那个 Python。

⑤ 误区

误区 1:「我直接装包不行吗」。不建议。往系统 Python 里装东西可能污染系统环境, 迟早和别的项目打架。新版 macOS 甚至会直接拒绝你。

误区 2:「.venv 要提交到存档里」。绝对不要。 它有几千个文件、几十 MB,而且随时能重新生成。第 11 页会教你怎么让存档系统忽略它。

两种用法:激活 vs 写全路径

用法怎么写特点
① 激活 source .venv/bin/activate
之后可直接写 pytest		 命令短。但只在当前这个终端窗口有效,关掉就没了
② 写全路径 .venv/bin/python -m pytest 命令长。但在任何地方、任何情况下都一定对
⭐ 为什么本教程一律用「写全路径」 因为你要和 AI 协作。AI 在执行命令时,不会继承你终端里「已激活」这个状态。

后果:你自己在终端敲 pytest 好好的;你让 AI 跑 pytest, 它那边可能报 command not found,或者用了系统 Python 跑出一堆莫名其妙的错误, 然后开始「修」一个根本不存在的问题。

所以:凡是要告诉 AI 的命令,一律写成 .venv/bin/python -m xxx 这种全路径形式。 这一条会在第 21 页变成一份配置文件里的硬性规定。
Windows 读者对照(全书唯一一处,记住这三条) ① .venv/bin/python → .venv\Scripts\python.exe(全书所有 .venv/bin/ 同理替换)。

② 激活命令:PowerShell 用 .\.venv\Scripts\Activate.ps1,CMD 用 .venv\Scripts\activate.bat —— 但本书原则是写全路径、不依赖激活,Windows 同样适用。

③ touch → New-Item,mkdir -p → mkdir(PowerShell 自动递归)。

另:终端中文乱码时先执行 $env:PYTHONUTF8="1"。

装了却说找不到?一条命令诊断

which python; which pytest
现象原因
两个路径都在 .venv/bin/ 下✅ 正常,已激活
command not found: pytest没激活 —— 用全路径写法,或先 source .venv/bin/activate
路径指向 /usr/bin/用的是系统 Python,不是项目的

这三个工具分别是干什么的

.venv/bin/python -m pytest --version; .venv/bin/python -m mypy --version; .venv/bin/python -m ruff --version
  真实输出

mypy 1.19.1 (compiled: yes)

版本可以不一样 你装的时候版本号可能更高,没关系。本教程只有一处对版本有硬要求: 第五节那个 pythonpath 配置需要 pytest 7.0 或更高。

四、一个和别的语言不同的地方

Python 没有「统一的命令入口」 如果你听过前端的 npm test,那是个统一入口:不管项目内部用什么测试工具, 一律敲 npm test 就行,因为项目里有个文件写明了「test 这个词对应哪条真实命令」。

Python 没有这个东西。
后果具体表现
① AI 每次用的命令可能不一样 这次跑 pytest,下次跑 python -m pytest,再下次跑 .venv/bin/pytest。 三个不完全等价,有时候前者会报「找不到模块」
② 你没法一句话说「跑项目的测试」 你必须每次都把完整命令说出来,否则它就要猜

本教程会用的三条命令(现在先记住形状)

.venv/bin/python -m pytest
.venv/bin/python -m mypy
.venv/bin/python -m ruff check .
正解:让配置文件当那个「统一入口」 Python 虽然没有内置的统一入口,但你可以自己造一个 —— 在项目里放一个说明文件,把这三条命令写死在里面,让 AI 每次自动读到。

第 21 页会完整教这件事。现在只需知道:这不是无法弥补的缺陷,而是需要你手动补上这一环。

五、一个文件配好三个工具

在项目根目录建一个叫 pyproject.toml 的文件。这一个文件同时是三个工具的配置文件。

在 myshop 项目根目录执行:

touch pyproject.toml

用任何编辑器打开它,把下面的内容整个粘进去:

[project]
name = "myshop"
version = "0.1.0"
description = "用来演示测试金字塔四层的迷你商店"
requires-python = ">=3.9"
dependencies = []            # 主代码只用 Python 自带的东西,不装第三方包

# ---------------- pytest:跑测试 ----------------
[tool.pytest.ini_options]
testpaths = ["tests"]        # 只去 tests/ 文件夹里找测试,别扫整个项目
pythonpath = ["."]           # ← 救命的一行,见第六节
addopts = "-v --strict-markers"
python_files = ["test_*.py"]
python_functions = ["test_*"]

# ---------------- mypy:类型检查 ----------------
[tool.mypy]
python_version = "3.9"
files = ["myshop", "tests"]
strict = true                # 严格模式:所有函数都必须写清楚类型

[[tool.mypy.overrides]]
module = "playwright.*"      # 这个包我们没装,别因为找不到它就报错
ignore_missing_imports = true

# ---------------- ruff:代码规范 ----------------
[tool.ruff]
target-version = "py39"      # ← 别漏这一行!见第八节
line-length = 100

[tool.ruff.lint]
# E=风格  F=真错误(未使用变量等)  I=import 排序  B=常见 bug 陷阱
select = ["E", "F", "I", "B"]

逐段解释

配置项作用
requires-python声明本项目最低需要哪个 Python 版本。ruff 会读它,见第八节
testpaths告诉 pytest「只去这个文件夹找测试」,不然它会扫整个项目包括 .venv,很慢
pythonpath本页最重要的一行,下一节专门讲
addopts每次跑测试默认带上的参数。-v = 每条测试单独打一行
python_files / python_functions什么样的文件名/函数名才算测试。第 3 页细讲
files(mypy)mypy 默认检查哪些文件夹,这样你敲 mypy 就不用带参数
strict把 mypy 的严格程度开到最高
overrides对某些包放宽要求。这里是因为后面会写一个用到 playwright 的示例文件但不装它
target-version告诉 ruff「我的代码要在 Python 3.9 上跑」。漏了会出事,第八节讲
select启用哪几组检查规则
⚠ 实测发现的坑:配置写错了它不告诉你 mypy 对拼错的配置键名只打一条 Warning,然后照常报成功。

实测把 strict 拼成 strictt: 
pyproject.toml: [mypy]: Unrecognized option: strictt = True
Success: no issues found in 10 source files

严格模式根本没开,但它报的是 Success。你会以为检查通过了,其实检查压根没开。

习惯:改完配置跑一次,看输出里有没有 Unrecognized option 这行。

🔄 经核实修正:strict = true 已经包含 check_untyped_defs 实测 mypy --help 的原文:--strict 启用的清单里就有 --check-untyped-defs。 所以两个都写是冗余的(但无害,可以保留作教学显式化)。

更重要的一处措辞修正:防「AI 漏写 -> None」靠的是 disallow_untyped_defs,不是 check_untyped_defs。 后者的作用是「连没写标注的函数体也检查」。

还有一个覆盖规则:strict = true 配 check_untyped_defs = false, 无论谁先写,最终都是关闭状态 —— 单项显式值赢过 strict。

六、头号劝退坑:找不到我的包

这是 Python 初学者遇到的第一大障碍,99% 的人会卡在这里。

坑长什么样

假设你的项目结构是这样(第 6 页会真的建起来):

myshop/                  ← 项目根目录
├── myshop/              ← 你的代码放这里
│   └── price.py
└── tests/               ← 测试放这里
    └── test_price.py

你在 tests/test_price.py 里写 from myshop.price import format_price,然后跑测试,得到:

  报错(真实输出)
ModuleNotFoundError: No module named 'myshop'
Interrupted: 1 error during collection

为什么会这样

三种解法,选一个就行

#做法评价
① 在 pyproject.toml 里配
pythonpath = ["."]		 ✅ 本教程用这个。零安装、一行解决、显式可见。需要 pytest ≥ 7.0
② 命令写成
.venv/bin/python -m pytest		 也有效。-m 这种写法会把当前目录加进搜索路径。缺点是必须每次都在项目根目录跑
③ 在项目根目录放一个空文件
conftest.py		 有效但原理绕,而且换个导入模式就失效。见第七节
判定规则,背下来 只要你的测试里出现了 from <你自己的包> import ...,就必须三选一。三个都不做 = 一定报错。
顺带记住这个退出码 这类报错的退出码是 2,不是 5。
退出码含义
0全部通过
1有测试失败了
2被中断 —— 收集阶段就出错了(比如 import 失败)
3内部错误
4命令行用法错误
5一条测试都没收集到 —— 通常是文件名/函数名不符合规则

怎么看退出码:跑完命令后立刻敲 echo $?。

七、五个你一定会撞上的概念

概念 1:__init__.py —— 「这个文件夹是一个包」的标志

位置要不要建理由
myshop/(放代码的)要 它是「这个文件夹是一个 Python 包」的标志,import myshop.price 才成立。可以是完全空的文件
tests/(放测试的)默认不要 只有当两个子文件夹里出现同名的测试文件、pytest 报 import file mismatch 时,才需要加

在 myshop 项目根目录执行 —— 先把目录建出来,touch 才不会报错:

mkdir -p myshop tests/e2e
touch myshop/__init__.py

概念 2:conftest.py —— pytest 自动加载的工具箱

共享配置文件conftest.py会用到
① 定义

一个特殊文件名。pytest 会自动加载它,你不需要 import。 作用范围是「它所在的文件夹,以及所有子文件夹」。

② 类比

办公室里的公共文具柜。

放在整层楼门口的柜子,整层楼的人都能用;放在某个房间里的柜子,只有那个房间和它的隔间能用。 你不需要申请,进来就能拿。

③ 位置

三个用途,按重要性排:

  1. 放共享的「准备工作」(下一个概念讲这是什么)—— 最常见
  2. 放改变 pytest 行为的钩子函数(进阶,本教程只在第 18 页用一次)
  3. 副作用:把自己所在的文件夹加进搜索路径 —— 这就是上一节第 ③ 种解法的原理
④ 例子

实测三种情况的对比:

情况结果
项目根有 conftest.py,跑 pytest✅ 能 import 自己的包
删掉 conftest.py,跑 pytest❌ ModuleNotFoundError
删掉 conftest.py,跑 python -m pytest✅ 又能了
⑤ 误区

🔄 经核实修正 —— 这一条我一开始也说错了: 很多教程说「因为 conftest.py 在项目根目录,所以项目根目录进了搜索路径」。因果关系是反的。

官方文档明确写着,pytest 判定的「项目根目录」这个概念 「不会被用来修改搜索路径,也不影响模块怎么被导入」。

真实机制是:pytest 导入任何一个 conftest.py 或测试文件时, 会把「那个文件所在的文件夹」插到搜索路径最前面。 当它恰好放在项目根目录时,被插入的就正好是项目根目录 —— 结果对,但原因不是「因为它是项目根目录」。

所以本教程推荐 pythonpath = ["."] —— 显式,不依赖这些间接机制。

概念 3:准备工作(fixture)—— 手术前的护士

准备工作fixture很重要
① 定义

一段由 pytest 自动帮你执行的准备代码。你只要在测试函数的参数位置写一个名字, pytest 就会找到对应的准备工作、执行它、把结果塞给你。

② 类比

手术前的护士。

你(医生)只需要在手术单上写「要一套干净的器械台」,护士就在你动手之前把它摆好; 做完之后她负责收拾。你一行代码都不用写,你只是喊了个名字。

③ 位置

它是测试三段式里「准备」那一段的实现方式(三段式在第 3 页讲)。

它和 conftest.py 是配合关系:写在 conftest.py 里的准备工作, 整个文件夹的测试都能用。

④ 例子
名字它准备什么为什么重要
tmp_path一个全新的空文件夹,跑完自动删让每条测试各写各的文件,互不干扰
monkeypatch临时改某个变量,测试结束自动改回来把「真实数据库路径」临时换成临时路径
capsys抓住 print 打印出来的东西测「有没有打印正确的提示」
 
def test_订单落盘了(tmp_path):        # ← 只是写了个参数名
    数据库路径 = str(tmp_path / "test.db")  # ← tmp_path 已经是个准备好的空文件夹了
⑤ 误区

误区 1:「参数名可以随便起」。不行。 参数名必须和准备工作的名字完全一致,pytest 靠名字找。写错就报「找不到这个 fixture」。

误区 2:「它是全局共享的」。tmp_path 恰恰相反 —— 每条测试拿到的是不同的文件夹。这正是它的价值。

概念 4:yield —— 把准备和收尾分开的那条线

@pytest.fixture()
def 服务器():
    服务 = 启动一个服务器()          # ← yield 之前:准备

    yield 服务的地址                  # ← 这一行:把东西交给测试用

    服务.关掉()                      # ← yield 之后:收尾
位置什么时候执行
yield 之前的代码测试开始前
yield 那一行把值交给测试函数
yield 之后的代码测试结束后,不管测试成功还是失败都会执行
「不管成功失败都执行」很关键 否则一条测试失败之后,服务器就一直开着不关,后面的测试全乱。

概念 5:pytest 怎么找到你的测试

规则必须是违反了会怎样
文件名test_*.py 或 *_test.py整个文件被无视,不报错不警告
函数名以 test 开头这个函数被无视
测试类名以 Test 开头整个类被无视
测试类不能有 __init__—⚠ 静默跳过整个类,只给一条很容易被忽略的警告
🔄 经核实修正:是 test 前缀,不是 test_ 前缀 很多教程写「函数名必须以 test_ 开头」。实测不准确。

pytest 的默认配置项 python_functions 的默认值是 ['test'](不带下划线), python_classes 默认值是 ['Test']。所以下面这些也会被收集: 
test_naming.py::test_normal              PASSED
test_naming.py::testnounderscore         PASSED   ← 没下划线也被收集
test_naming.py::Testing::test_inner2     PASSED   ← class Testing 也被收集

注意:上面的演示基于 pytest 的默认配置。你在本页第五节写入的 pyproject.toml 已把规则收窄为 test_* 前缀,照那份配置跑,testnounderscore 不会被收集(Testing 类那行仍成立,因为 python_classes 没有被覆盖)。

⚠ 最阴的一条:文件名不匹配 = 测试静默地完全不运行 实测:一个叫 tests_helper.py 的文件(注意是 tests_ 不是 test_), 里面写了一条必定失败的测试。pytest 从头到尾没有运行它,也没有任何提示。

很多人把辅助文件命名成 tests_xxx.py,然后奇怪为什么测试没跑。 反过来也危险:辅助文件里如果有 test 开头的函数,一旦文件名撞上 test_*.py,就会被误当成测试收集。

防呆:跑完看一眼「收集到几条」(collected N items),数字对不上就说明有东西被吞了。
⚠ AI 协作专属陷阱:带 __init__ 的测试类 AI 有时会生成这样的测试类(它以为需要初始化): 
class TestPrice:
    def __init__(self):        # ← 有了这个,整个类被跳过
        self.data = [1, 2, 3]

    def test_something(self):
        assert self.data[0] == 1

pytest 会一声不吭地跳过整个类,你看到「测试通过」,其实一条都没跑。 正确做法是把初始化放进准备工作里。

八、关于 Python 3.9 的两个提醒

先说一个背景:Python 3.9 已于 2025 年 10 月结束官方支持,新装环境请用当前稳定版。本教程代码按 3.9+ 兼容语法书写,在新版 Python 上同样可跑 —— 下面两个提醒对新版本读者仍然有用。

提醒 1:新语法不能用

写法3.9 能用吗说明
Optional[str]✅ 能本教程一律用这个
str | None❌ 不能3.10 才有。3.9 上运行会报 TypeError
dict[str, Any]✅ 能3.9 就支持了(常被误以为不行)
Dict[str, Any]✅ 能老写法,也能用

提醒 2:那一行 target-version 千万别漏

🔄 这一条经核实后方向完全改了 常见说法是:「Python 3.9 上不要启用 ruff 的 UP 规则,它会催你用 3.10 的语法」。 实测发现这个因果关系是错的。

只要 target-version = "py39" 写对了,启用 UP 是安全的 —— ruff 根本不会建议你用 str | None(相关规则不触发)。
情况会发生什么
正确写了 target-version = "py39" ✅ 安全。ruff 不会提 3.10 的语法
漏写了 target-version,而且 requires-python 也没写 ruff 0.16 默认按 Python 3.10 算。 于是 ruff check --fix 会把你的 Optional[str] 直接改成 str | None, 在 3.9 上一运行就 TypeError
文件里有 from __future__ import annotations ⚠ 即使写对了 target-version 也会被建议改。函数定义能过, 但某些运行时读取类型的场景仍会出错
结论,记这一句就够 关键不是「别加 UP 规则」,而是「别漏 target-version」。

更保险:[project] 段里的 requires-python = ">=3.9" 也写上 —— ruff 会读它作为备用依据。 我们上面的配置两个都写了。

额外保险:即使触发了,相关修复在 py39 目标下被标为 unsafe, ruff check --fix 不会动它,要加 --unsafe-fixes 才改。
想升级 Python 吗? Python 3.9 已过官方维护期。装了 Homebrew 的话升级是一条命令: 
brew install python@3.13

但不升级也完全能走完本教程 —— 所有代码都是 3.9 兼容的。先把流程学会更重要。
