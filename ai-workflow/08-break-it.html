一、为什么要故意改坏

变异测试(手工版)mutation testing核心方法
① 定义

把好代码故意改坏一处,看该响的哨兵有没有响。响了说明这条测试真的在工作,没响说明它是摆设。

② 类比

点根香测烟雾报警器。

你家天花板上的报警器已经安静挂了三年,从来没响过。 它是真的在保护你,还是电池早就没电了?

你没法从「它没响」推断出「它是好的」—— 因为这三年也没着过火。 唯一的办法是:点根香举到它下面,看它会不会叫。

③ 位置

它是「让它自测」这道防线的元检查 —— 检查检查本身是否有效。

一条永远不会失败的测试,和没有这条测试,效果完全一样。 而你还会因为它绿着而放松警惕,这更危险。

④ 例子

标准三步:

  1. 把好代码故意改坏一处
  2. 跑检查,看该响的响了没有
  3. 改回来

第 3 步用一条命令完成(第 12 页会讲这条命令):

cd <你的项目>/myshop && git checkout -- .

意思是「把所有文件恢复成上次存档的样子」—— 就像游戏里读档。

⑤ 误区

误区 1:「改坏代码很危险」。 只要先存过档就一点都不危险。下面五次实验,每次都是一条命令干净还原。

误区 2:「测试全绿就说明测试写得好」。 恰恰相反 —— 全绿只说明「现在的代码通过了现有的检查」, 不说明那些检查有任何鉴别力。

开始之前:确认基线是绿的 
cd <你的项目>/myshop && git status -s && .venv/bin/python -m pytest -q

应该看到:工作区没有输出(干净) + 17 passed, 1 skipped。
基线不绿的话,后面所有红字你都分不清是谁造成的。

二、实验① 去掉补零

改了什么

# 文件:myshop/price.py
- return f"¥{yuan}.{fen:02d}"
+ return f"¥{yuan}.{fen}"

删掉了 :02d —— 就 4 个字符。功能上看起来「还是把分转成元」。

三个工具的反应

  真实输出
$ .venv/bin/python -m ruff check .
All checks passed!

$ .venv/bin/python -m mypy
Success: no issues found in 8 source files

$ .venv/bin/python -m pytest tests/test_price.py
3 failed, 2 passed in 0.04s

失败详情

  真实输出
    def test_不足一角要在前面补零() -> None:
>       assert format_price(5) == "¥0.05"
E       AssertionError: assert '¥0.5' == '¥0.05'
E
E         - ¥0.05
E         ?    -           ← 精确指出:这里少了一个字符
E         + ¥0.5

最值得琢磨的:哪两条活下来了

测试输入结果为什么
test_普通价格1234绿 分位是 34,本来就两位数,不需要补零
test_零元是边界值0红要补成 00
test_不足一角要在前面补零5红要补成 05
test_整数元不能丢掉小数位10000红要补成 00
test_负数要报错-1绿 负数在格式化之前就被拦下了,走不到那行
⭐ 实验① 的结论 如果你只写了「正常情况」那一条测试,这个 bug 会被干干净净地放过去。

而它上线后长这样: 
购物车合计  ¥99.9      ← 用户以为 99 块 9,其实是 99 块 09 分

边界值测试的全部价值,就在这四条里的三条。

三、实验② 换个货币符号

改了什么

- return f"¥{yuan}.{fen:02d}"
+ return f"${yuan}.{fen:02d}"

一个字符。

结果

  真实输出
$ ruff check .   All checks passed!
$ mypy            Success: no issues found in 8 source files

$ pytest
==================== 8 failed, 9 passed, 1 skipped in 3.65s ====================
层红 / 总爆炸原因
① 单元 test_price.py4 / 5直接测这个函数,首当其冲
② 集成 test_order.py2 / 5order.py 用了它 —— 这个文件一个字没动
② 接口 test_api.py2 / 7api.py → order.py → 它 —— 也一个字没动

爆炸半径

⭐ 实验② 的结论 一个函数的爆炸半径,和它的代码行数成反比。

format_price 只有 5 行,但整个项目的价格显示全靠它。

四、实验③ 除数改错

改了什么

- yuan, fen = divmod(cents, 100)
+ yuan, fen = divmod(cents, 10)

这个 bug 让所有金额都错了 10 倍:

  改坏后函数的真实返回值
  format_price(  1234) = ¥123.04   (应该是 ¥12.34)
  format_price(     0) = ¥0.00     ← 巧合对了!
  format_price(     5) = ¥0.05     ← 巧合对了!
  format_price( 10000) = ¥1000.00  (应该是 ¥100.00)
  format_price(  2500) = ¥250.00   (应该是 ¥25.00)

结果:比实验② 还少 2 条

  真实输出
$ ruff check .   All checks passed!
$ mypy            Success: no issues found in 8 source files

$ pytest
tests/test_price.py::test_普通价格 FAILED
tests/test_price.py::test_零元是边界值 PASSED          ← 实验① 里它红了!
tests/test_price.py::test_不足一角要在前面补零 PASSED  ← 实验① 里它也红了!
tests/test_price.py::test_整数元不能丢掉小数位 FAILED
tests/test_price.py::test_负数要报错 PASSED

=================== 6 failed, 11 passed, 1 skipped in 3.65s ====================

为什么 0 和 5 巧合地对了

输入除以 100(正确)除以 10(改坏)结果
0(0, 0) → ¥0.00(0, 0) → ¥0.00 一样
5(0, 5) → ¥0.05(0, 5) → ¥0.05 一样
1234(12, 34) → ¥12.34(123, 4) → ¥123.04 差很远
10000(100, 0) → ¥100.00(1000, 0) → ¥1000.00 差 10 倍

0 和 5 都小于 10,除以 100 和除以 10 得到的商都是 0、余数都是它自己 —— 两条路殊途同归。

⭐ 实验③ 的两个结论

结论 1:红的条数和 bug 的严重程度毫无关系。

实验红了几条实际危害
② 换符号8 条符号难看,钱是对的
③ 除数错6 条每笔钱都差 10 倍

不要用「红了几条」判断问题多大。要看红的内容。

结论 2:不同的用例只挡不同的错。

实验① 靠边界测试(0、5)抓住 bug;实验③ 那两条边界测试完全失效, 靠的是最「平庸」的 test_普通价格。
测试的价值在于「用例的多样性」,不是「用例的数量」。

五、实验④ 边界挪一格

改了什么

- if cents < 0:
+ if cents < -1:
      raise ValueError("价格不能为负数")

-1 < -1 是 假,所以只有 -1 这一个值能溜过去:

  真实输出
  format_price(-3) → ValueError: 价格不能为负数   ✅ 拦住
  format_price(-2) → ValueError: 价格不能为负数   ✅ 拦住
  format_price(-1) = '¥-1.99'                    ❌ 漏了!
  format_price( 0) = '¥0.00'                     ✅ 正常
顺带一个 Python 冷知识 为什么 -1 会变成 ¥-1.99 这么怪的东西? 
divmod(-1, 100) = (-1, 99)     # 不是 (0, -1)!
divmod(-2, 100) = (-1, 98)

Python 的整除是向下取整,不是向零取整。 -1 ÷ 100 得到 -1(不是 0),余数补成 99。
这是 Python 和某些其他语言的一个真实差异,在处理负数金额、时间戳、索引时经常咬人。

结果:只有 1 条红

  真实输出
$ pytest
=================== 1 failed, 16 passed, 1 skipped in 3.68s ====================

    def test_负数要报错() -> None:
        with pytest.raises(ValueError):
>           format_price(-1)
E           Failed: DID NOT RAISE <class 'ValueError'>
一种没见过的失败信息 前三次都是 AssertionError(算错了)。这次是 DID NOT RAISE —— 「你说这里该报错的,结果它没报」。
失败类型含义危险程度
AssertionError算错了值不对
DID NOT RAISE该拦的没拦住一道防线整个失效

后者往往更危险 —— 安全漏洞、越权访问、脏数据入库,大多长这个样子。

上面两层为什么一条都没红

  现场验证
price.py 的关卡已经漏了 -1,那 order 层呢?
✅ 被 order.py 自己的检查挡住了: 单价不能为负数

因为 order.py 有自己独立的校验(第 6 页那段代码里的 if unit_cents < 0)。

⭐ 实验④ 的三个结论

结论 1:纵深防御有用。多设一道关卡真的顶住了。

结论 2(更重要):上层全绿不代表下层没问题。 洞还在 price.py 里。今天有 order.py 兜着; 哪天有人直接调用它做别的用途,¥-1.99 就出现在页面上了。
所以每一层都必须有自己的测试,不能因为「上层测过了」就省掉下层。

结论 3:测边界要用「刚好越界一格」的值。 如果这条测试当初写的是 format_price(-100),这个 bug 就溜过去了 —— 因为 -100 < -1 为真,照样报错,测试全绿。
测负数就用 -1,不要用 -999。

六、实验⑤ 去掉确认提交

改了什么

# 文件:myshop/order.py
        order_id = cur.lastrowid or 0
-       conn.commit()
+       # conn.commit()

先看函数层面发生了什么

  手动实验的真实输出
create_order 返回的字典: {'id': 1, 'item': '咖啡', 'qty': 2,
                          'total_cents': 2500, 'total_text': '¥25.00'}
↑ 完全正常!有订单号、金额对、文案对

换个连接去数数据库里有几条订单: 0
↑ 一条都没有

get_order 结果: LookupError: 订单 1 不存在
🔥 这是最阴险的一类 bug:静默数据丢失 函数返回成功,用户看到「下单成功」,数据库里什么都没有。

前四个 bug 都是「算错了」—— 至少你能看出不对劲。这个是「看起来完全成功,实际什么都没发生」。

上线之后的表现: 
用户:我明明下单了,订单呢?
客服:系统里查不到您的订单。
你  :……可日志显示接口返回成功了啊?

结果:3 条红,三种不同的症状

  真实输出
$ ruff check .   All checks passed!
$ mypy            Success: no issues found in 8 source files

$ pytest
FAILED tests/test_api.py::test_下单之后能用_GET_查回来 - assert 404 == 200
FAILED tests/test_order.py::test_订单真的落盘了_换个连接还读得到 - LookupError
FAILED tests/test_order.py::test_下两单会拿到两个不同的订单号 - assert 1 != 1
=================== 3 failed, 14 passed, 1 skipped in 3.64s ====================
测试报错翻译
test_订单真的落盘了LookupError: 订单 1 不存在 刚存的东西读不回来 —— 最诚实的一条
test_下两单会拿到不同订单号assert 1 != 1 两笔订单拿到了同一个号 —— 因为第一笔被撤销了,连自增计数也退回去了
test_下单之后能用_GET_查回来assert 404 == 200 刚创建成功的东西,立刻查是「不存在」
第三条那个组合是最经典的信号 「创建成功(201)」+「立刻查不到(404)」 —— 任何后端工程师看到这两行放在一起, 第一反应就是「事务没提交」。

⭐ 实验⑤ 最重要的发现

单元测试一条都没红 test_price.py 的 5 条全绿。为什么? 因为这个 bug 根本不在它的地盘上。它只管算数,不管存盘。
能抓什么抓不到什么
单元测试算得对不对存没存进去
集成测试存没存进去网络通不通
接口测试网络那头拿到什么—

这就是为什么要分四层,而不是「把单元测试写足就行了」。

这也证明了「换连接读回来」技巧（第 5 页给结论,第 7 页给代码）的价值 如果那条测试当初图省事,在同一个连接里查询,它会全绿 —— 因为同连接里没提交的数据照样读得到。

这个 bug 就漏了。

四条能读出来的规律

#规律证据
1静态检查五战五败 五次改的都是「行为」,而它只看「形状」。这不是配置问题,是第 4 页讲的结构性盲区
2红的条数 ≠ 危害程度 8 红的只是难看,6 红的会赔钱,1 红的是安全洞,3 红的会丢数据
3每次立功的是不同的测试 五次,五组不同的测试。留任何一组、砍掉其余,都会漏掉四个 bug
4每一层只抓自己那层的错 实验④ 集成/接口层 0 红,实验⑤ 单元层 0 红。少任何一层,都有一整类 bug 溜过去

八、回到 AI 协作

把这五次实验换个身份看:假设改坏代码的不是我,是 AI,而且你不知道它改了什么。

你能依靠什么靠不靠得住为什么
AI 说「我检查过了」❌它在评价自己的作业
静态检查全绿⚠五次全瞎
跑测试✅靠得住,但只挡你写过的用例
你自己看改动✅✅唯一能发现「它偷偷改了测试」的手段

最阴险的场景:实验④

只有 1 条红的时候,最容易被糊弄过去 一条红,看起来太像「小问题」了。AI 很容易顺手把测试改成: 
with pytest.raises(ValueError):
    format_price(-100)      # 从 -1 改成 -100 → 立刻绿

一个字符的改动,一道安全关卡就此永久失效,而且再也不会有测试发现它。

能挡住这一手的只有一件事:你自己打开改动列表,看到 tests/test_price.py 在里面。

三道防线的适用范围

防线实验①②③⑤实验④
提示词写死「不许改测试文件」✅✅
你自己看改动✅✅ 全靠它
跑全量测试兜底✅❌ 没用(在 AI 已篡改测试的场景下,上层全绿)
注意最后一行 实验④ 里（在 AI 已篡改测试的场景下）,全量测试救不了你 —— 因为纵深防御把问题掩盖了,上面两层都是绿的。

唯一能发现的,是你亲眼看见 tests/ 出现在改动列表里。

这就是「第 4 步漏了,你会逐渐失去对代码库的掌控」的最好注脚。

你可以自己再玩几个

cd <你的项目>/myshop
改什么先猜会红几条,再跑
order.py 里 unit_cents * qty 改成 +集成层的算术错误
api.py 里 self._send(201, ...) 改成 200接口层专属:状态码契约
price.py 里把 "¥" 删掉三层同时飘红

每次玩完,一条命令还原:

cd <你的项目>/myshop && git checkout -- . && .venv/bin/python -m pytest -q
