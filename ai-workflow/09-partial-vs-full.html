局部 vs 全量 + 一场真实事故

同一批测试,为什么要跑两次?这一页用一场完整复盘回答: 一个只加了两行的改动,如何把「应付 ¥0.00」变成「应付 免费」,并流进财务系统。

一、两个不同的问题

这不是同一件事做两遍,是两个不同的问题
局部检查全量检查
什么时候每改完一小块(流程步骤 3)准备存档前(流程步骤 5a)
跑什么只跑和刚改的东西相关的全部都跑
命令pytest tests/test_price.pypytest(不带任何参数)
回答什么我刚写的这段,自己立得住吗?这次改动的爆炸半径有多大?
检查半径你手指碰过的文件整个项目
耗时0.00–0.02 秒3.66 秒
一个比喻:换水管 改一个被到处引用的底层函数,像换水管的一节管子。

你在自家水槽下面拧上、放水、不漏,于是宣布搞定 —— 这是局部检查。
楼下邻居的天花板,是第二天才开始滴水的 —— 这是没跑全量的代价。

全量检查就是「整栋楼一起放水」。它只要 3.66 秒。

二、一个只改了两行的下午

产品经理提了个需求,编号 #482,听起来人畜无害:

「订单里 0 元的时候别显示 ¥0.00 了,太冷冰冰。改成显示『免费』,用户看着开心。」

合理吗?非常合理。工作量大吗?看起来就两行。

def format_price(cents: int) -> str:
    """产品需求 #482:0 元时显示「免费」。"""
    if cents == 0:          # ← 新增
        return "免费"        # ← 新增
    return f"¥{cents / 100:.2f}"
说明:这一段的实测输出来自一个独立的精简复现项目 你会发现这里的函数用的是 cents / 100,和前面 myshop 里的写法不同 —— 这不是你看漏了。

为了把这个事故复现得足够干净,我另外搭了一个只有 4 个文件的最小项目来跑。 两个版本的行为完全一样,下面所有绿字红字都是那个项目里真实跑出来的。 事故的道理和用哪种写法无关。

顺带说清楚耗时:本页开头那个「全量 3.66 秒」是 myshop 的 —— 它有 18 条测试,还包含要真启动 HTTP 服务的接口层。 而下面这个复现项目只有 4 个文件、7 条纯函数测试,所以全量只要 0.03 秒。 两个数字都是真的,只是量的不是同一个项目。 后面「算一笔账」用的是 0.03 秒 —— 数字再大十倍,结论也一样。

改完之后,AI(或者你自己)很负责任地想了一件事

「改了行为,得同步改测试啊。」于是打开测试文件,把那条断言改了:

def test_zero_price() -> None:
    # 需求 #482:0 元现在显示「免费」
-   assert format_price(0) == "¥0.00"
+   assert format_price(0) == "免费"

看,多专业。改了代码,顺手把对应的测试也维护了。

三、局部检查:全绿

现在到了流程的步骤 3。你改了价格模块,那就检查价格模块相关的东西,天经地义:

  局部检查(真实输出)
$ .venv/bin/python -m mypy price.py
Success: no issues found in 1 source file

$ .venv/bin/python -m pytest tests/test_price.py -v
tests/test_price.py::test_normal_price PASSED       [ 33%]
tests/test_price.py::test_zero_price PASSED         [ 66%]
tests/test_price.py::test_large_price PASSED        [100%]

========================= 3 passed in 0.01s =========================
⚠ 这时候人的心理状态是最危险的 证据看起来是充分的。你改了 A,你检查了 A,A 是绿的。手指已经放在存档键上了。

四、全量检查:两条红

假设这次你忍住了,按流程走了步骤 5a —— 提交前跑一遍全量:

  全量检查(真实输出)
$ .venv/bin/python -m mypy price.py order.py tests/
Success: no issues found in 4 source files          ← 类型检查依然全绿!

$ .venv/bin/python -m pytest
collected 7 items

tests/test_order.py ..FF                              [ 57%]
tests/test_price.py ...                             [100%]

============================ FAILURES =============================
_____________________ test_full_discount_to_zero ___________________
>       assert order["receipt"] == "应付 ¥0.00"
E       AssertionError: assert '应付 免费' == '应付 ¥0.00'

_______________________ test_gift_line_item _______________________
>       assert order["lines"][1] == "赠品·挂耳包 x2  ¥0.00"
E       AssertionError: assert '赠品·挂耳包 x2  免费' == '赠品·挂耳包 x2  ¥0.00'

==================== 2 failed, 5 passed in 0.03s ==================

炸的是哪两处

引爆点场景后果
① 满减到 0 元 用户拿 88 元券买 88 元咖啡豆,刚好减到 0。系统仍要出一张收款凭证 应付 ¥0.00 → 应付 免费
「应付 免费」这句中文不通。更要命的是这行字要进对账单和财务流水 —— 财务系统那边可能正拿正则匹配 ¥[\d.]+,现在匹配不到了
② 赠品行 账单里单价 0 元的赠品行 赠品·挂耳包 x2 ¥0.00 → 赠品·挂耳包 x2 免费
需求 #482 说的是「订单总价为 0 时」。没有人说过赠品的单价行也要跟着变。
第 ② 处才是这次事故的精髓 format_price 是共用的,它不知道自己这次是在服务「订单总价」还是「某一行的单价」。

改一个底层函数,炸的是所有调用点 —— 包括你脑子里根本没想到的那些。

关键的落差

步骤 3 · 局部检查步骤 5a · 全量
检查范围price.py + 它的测试整个项目
结果3 passed ✅ 2 failed, 5 passed ❌
耗时0.01 秒0.03 秒
复现项目,7 条测试
局部检查没有骗你 它诚实地回答了你问的那个问题:「price.py 现在自洽吗?」答案是自洽。

问题是这个问题本身就问小了。

你真正想知道的是「这次改动会不会弄坏别人的东西」,而这个问题,只有把所有测试都跑一遍才能回答。

五、为什么类型检查完全无能为力

注意上面那个扎心的细节:全量的类型检查也是绿的,而且是在测试已经红了之后。

  同一份代码,两个工具
$ mypy price.py order.py tests/
Success: no issues found in 4 source files      ← 4 个文件全过

$ pytest
2 failed, 5 passed                              ← 同一份代码

不是「局部绿、全量红」,而是类型检查在任何范围下都发现不了这个问题。原因就是第 4 页那个结构性盲区:

def format_price(cents: int) -> str:   # 改前
def format_price(cents: int) -> str:   # 改后 —— 签名一个字符都没变
问题类型类型检查能抓?测试能抓?
改了参数类型 / 数量✅✅
改了返回类型✅✅
拼错属性名、少传参数✅✅
签名不变、返回内容变了❌ ✅(前提:跑全量)
改了边界条件的行为❌ ✅(前提:跑全量)
一句话概括这次事故 类型没变(签名一致),行为变了(返回值内容不同)。
  • 类型系统管的是:调用方能不能安全地把返回值当字符串用?能。
  • 测试管的是:这个字符串的具体内容是不是业务上正确的那个?不是。

这也是为什么步骤 5a 是「类型检查 和 测试」而不是只跑类型检查 —— 这次事故里,前者给了你一个绿灯,后者才是救命的那个。

六、为什么「我知道我改了什么」救不了你

这次事故里,改动者从头到尾都很称职:改了行为,同步改了测试,跑了检查,全绿。

⭐ 漏掉不是因为粗心 你的注意力半径,天然等于你的编辑半径。

你改价格模块的时候,脑子里的画面是「订单总价那一栏」; 你不会自动浮现出「三个月前有人在赠品行也调了这个函数」。

代码库越大、函数越底层,你脑子里的调用点地图就越不完整。 而那种「人畜无害的小工具函数」恰恰是被引用最多的那类。

没有任何一方是不称职的。这就是为什么这类事故特别常见 —— 它不需要谁犯错。
有人会说:我 grep 一下调用点不就行了 可以,但不够。搜索只告诉你「谁调了」,不告诉你「谁的期待被打破了」。

赠品行那个调用点你能搜到,但你得逐个读懂每个调用点期待的是什么格式 —— 而那正是测试已经替你写下来的东西。

七、三条可以直接用的规则

#规则怎么判断
1改底层 = 必跑全量 判断标准很简单:这个函数被别的文件引用了吗?被引用得越多,局部检查越不可信。 工具函数、格式化、序列化、常量、配置 —— 全是重灾区
2「我顺手改了对应的测试」是危险信号 改一个断言意味着你确认了行为变更,而行为变更就一定有波及面。 你改断言的那一刻,恰恰是最该跑全量的时候 —— 因为你亲手确认了旧的期待作废了
3别把类型检查的绿灯当测试的替代品 它只保证「接得上」,不保证「算得对」。这是结构性盲区,不是配置问题
第 2 条值得单独强调 这次事故里,局部检查的那份绿色是改断言换来的,不是代码变正确了。

如果你看到 AI 的改动里包含测试文件,那不是「它很周到」,那是一个需要停下来核对的信号。
