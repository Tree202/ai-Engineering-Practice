git 基础:代码的存档系统

这一页把 git 当游戏存档来讲。它是五道防线里唯一横跨全程的一道, 也是唯一「漏了就全盘皆输」的一道 —— 因为存档必须在事故之前按下。

一、git 是什么

存档系统git绝对不能省
① 定义

一个记录代码历史的工具。你在关键时刻手动按一下「存档」, 之后不管怎么乱改,都能一条命令退回任何一个存过的档。

② 类比

游戏存档。这个类比全书都在用:

游戏里代码里命令
给这个游戏装上存档功能初始化仓库git init
开一条新存档位打 BOSS开一条新分支git switch -c
看看现在进行到哪了看工作区状态git status
看看这段打了什么看改动git diff
按存档键提交git commit
存档列表提交历史git log
读档回退(第 12 页)git restore 等
③ 位置

它是其他所有防线的地基:

  • 没有它,「一键撤销」的死角就没人兜底
  • 没有它,「你自己看改动」根本无从看起 —— 因为你不知道「改之前」是什么样
  • 没有它,第 8 页那五个实验一个都做不了
④ 例子

一天工作的节奏:

开工:  开一条新分支,确认工作区干净
第1步做完 → 检查 → 满意 → 存档
第2步做完 → 检查 → 满意 → 存档
第3步做完 → 检查 → 不满意 → 一条命令退回第2步
再来一次第3步 → 检查 → 满意 → 存档
⑤ 误区

误区 1:「等出事了再学」。来不及。存档必须在事故之前按下 —— 出事之后你已经没有可退回的点了。

误区 2:「git 是团队协作用的,我一个人不需要」。 一个人时它更重要 —— 因为没有别人帮你发现问题,你只能靠「随时能退回去」这个保障。

二、开一条新存档位

第一次用:装上存档系统

cd <你的项目>/myshop && git init
  真实输出
Initialized empty Git repository in <你的项目>/myshop/.git/

用第 0 页 A 路克隆来的仓库已经有 .git, 这里会显示 Reinitialized existing Git repository… —— 也是正常的,继续往下读。

第一次用还要告诉它你是谁 否则提交时会报错。只需要做一次,以后所有项目都用这个: 
git config --global user.name "你的名字"
git config --global user.email "你的邮箱"

开新分支

cd <你的项目>/myshop && git switch -c feat/add-discount
部分含义
switch切换到某条分支
-c--create 的缩写:新建一条分支并立刻切过去
feat/add-discount分支名。feat/ 是社区约定的前缀(新功能),后面写实际功能名
为什么非要新开一条分支 让主干保持绝对干净。AI 在新分支上怎么折腾都行,最坏情况是切回主干把这条分支整个删掉,主干一行都没动过。

这一步把爆炸半径从「整个项目」缩到了「这条分支」。
🔄 关于 switch 和老写法 checkout -b 你会在网上看到大量教程用 git checkout -b。两者效果一样,但推荐用 switch:
命令职责
checkout身兼两职:切分支 + 恢复文件。职责重载 → 容易误操作、报错信息也怪
switch只管切分支
restore只管恢复文件

核实后的两个补充:

  • 这两个新命令从 git 2.51 起已经摘掉「实验性」标签,可以放心用
  • 但如果你本机是较老的版本(比如 2.39),man git-switch 仍然会看到 EXPERIMENTAL 字样 —— 两件事同时成立,不用慌
💡 一个立刻能体会的差别 分支名打错时,两个命令的报错完全不同:
  实测对比
$ git checkout nosuchbranch
error: pathspec 'nosuchbranch' did not match any file(s) known to git
↑ 我明明在切分支,你跟我说「文件路径」?

$ git switch nosuchbranch
fatal: invalid reference: nosuchbranch
↑ 人话:这个分支名无效

前者之所以说「文件路径」,正是因为它职责重载 —— 它先当分支名解释,解释不通就退回去当文件路径解释,于是给出一条看似不相关的错误。
这就是「为什么该用 switch」的最佳实例。

三、看当前进度

cd <你的项目>/myshop && git status

五种状态各自长什么样

  实测五种状态
【状态1:干净】
$ git status
On branch main
nothing to commit, working tree clean

$ git status -s
(完全没有输出 — 没输出就是好消息,不是命令卡住了)

【状态2:有 git 不认识的新文件】
?? README.md
?? app.py

【状态3:改了,已经勾选待存档】
M  README.md

【状态4:改了,还没勾选】
 M app.py

【状态5:勾选之后又改了】
MM both.py
⚠ 简短版 -s 的关键:左右两列 左列 = 暂存区(勾选过的),右列 = 工作区(还没勾选的)。
符号含义
M  改了,已勾选(注意 M 在左边)
 M 改了,没勾选(注意 M 前面有个空格)
MM两种都有:勾选之后又改了
A  新文件,已勾选
??git 完全不认识的新文件 —— 最危险的一类,第 12 页详讲

M 前面那个空格特别容易被忽略,而它恰恰是关键。

💡 不确定该用哪条命令时,照抄它的提示 git status 的完整输出里自带指引,比如: 
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)

它已经把该敲什么写在那儿了。

四、为什么工作区必须干净

这是一条隐藏的因果链,漏了它会让整个流程的步骤 4 悄悄失效:

如果不干净怎么办
做法命令
先存起来(推荐)git add -A 然后 git commit -m "..."
先收进抽屉git stash(之后 git stash pop 拿回来)

还有一件必须在第一次提交前做的事

⚠ 先写忽略清单,再开始存档 Python 项目会自动生成大量垃圾文件。不写忽略清单的话,它们会全部进入存档, 让你的改动列表全是噪音 —— 又一次让步骤 4 失效。

在项目根目录建 .gitignore:

# ---- Python 垃圾 ----
__pycache__/
*.py[codz]
.pytest_cache/
.mypy_cache/
.ruff_cache/

# ---- 虚拟环境(几千个文件、几十 MB)----
.venv/
venv/
env/
ENV/

# ---- 密钥,千万别提交 ----
.env
.env.*
!.env.example
.envrc

# ---- 本地数据库 ----
*.sqlite3
myshop.db          # 本项目跑测试会生成它

# ---- 编辑器 ----
.idea/
🔄 这份清单经核实后做了四处改进
改动原因
*.py[cod] → *.py[codz]上游模板已更新,多覆盖一种扩展名
加了 venv/ env/ ENV/.venv/ 只匹配这一个名字,常见别名要单独列
加了 .env.* 和 !.env.example.env 只匹配精确名字,.env.local 这类会漏网。 感叹号是反向放行,让模板文件能提交
*.db → *.sqlite3*.db 太宽,会连你有意提交的数据文件一起吞掉
💡 .DS_Store 建议放全局,不要放项目里 它是 macOS 自己生成的,不该让每个项目的忽略清单都替你的操作系统擦嘴: 
git config --global core.excludesFile ~/.gitignore_global
echo ".DS_Store" >> ~/.gitignore_global

五、暂存区:超市结账传送带

暂存区staging area / index必须理解
① 定义

一个「待存档清单」。你改了 10 个文件,可以只把其中 3 个放进清单,这次只存这 3 个。

② 类比

超市结账传送带。

超市代码
从货架拿东西改文件
放上传送带git add
收银员扫码打单git commit
看购物车里还没放上去的git diff
看已经放上传送带的git diff --staged

步骤 4 的规矩就是:结账前把传送带上的东西再扫一眼。

③ 位置

它夹在「你的文件」和「存档历史」之间:

工作区(你改的文件)
   ↓  git add
暂存区(待存档清单)
   ↓  git commit
存档历史
④ 例子
cd <你的项目>/myshop && git add -A
命令作用
git add -A把全部改动(含新文件)放上传送带
git add 文件名只放某一个
git restore --staged .从传送带上拿下来,但保留你写的内容
⑤ 误区

误区 1:「add 是添加新文件用的」。不只是。 已存在的文件改了之后也要 add —— 它的意思是「放上传送带」,不是「添加文件」。

误区 2:「add 之后改动就安全了」。没有。 只有 commit 之后才进历史。传送带上的东西,一个粗暴的回退命令照样能清空。

六、看改动

说明:这一节和下一节的终端输出,来自一个更小的练习仓库 下面几个「真实输出」框里你会看到 app.py、report.py, 以及「读取分数 / 计算平均分 / 输出报告」这样的存档说明 —— 那不是 myshop,是我另外建的一个三步小练习。

原因很简单:myshop 的一次改动动辄牵扯几个文件, 贴出来的 diff 长到看不清重点;而这一节要讲的是怎么读一段 diff, 用一个只有一两行改动的小仓库最清楚。 命令的用法、输出的格式完全一样,换个项目不影响任何结论。

三条命令的分工

命令看的是什么
git diff还没 add 的改动(购物车里的)
git diff --staged已经 add 的改动(传送带上的)
git diff HEAD两种全看 —— 步骤 4 推荐用这条
⚠ 头号坑:add 之后 git diff 变成空白 新手会以为改动丢了。其实是跑到传送带上去了,要用 --staged 看。

另外:git 不认识的新文件不会出现在 git diff 里。 所以步骤 4 应该先 git status 再 git diff —— 前者告诉你有哪些新文件,后者告诉你改了什么。

改动怎么读

  真实输出
diff --git a/app.py b/app.py
index 11b15b1..738c813 100644
--- a/app.py          ← a = 改之前
+++ b/app.py          ← b = 改之后
@@ -1 +1,4 @@         ← 改动发生在第 1 行起
-print("hello")       ← 减号红行 = 被删掉的旧内容
+def greet(name):     ← 加号绿行 = 新加的内容
+    return f"Hello, {name}!"
+
+print(greet("world"))
两个新手常撞的小问题
  • 输出很长时会进入分页模式(底部显示一个冒号)—— 按 q 退出,不是死机
  • a/ 和 b/ 不是文件夹,是「改之前 / 改之后」的代号

只看规模

git diff --stat
  真实输出
 report.py | 2 ++
 1 file changed, 2 insertions(+)
💡 步骤 4 的第一眼:先看规模 改动规模和「方案里说的第一步」对得上吗?
说好只改一个文件,结果这里列了 8 个 —— 那就先别看内容,先问它为什么。

七、存档

cd <你的项目>/myshop && git commit -m "feat: 第1步 price 支持满减计算"
  真实输出
[main b27d579] feat: 第1步 price 支持满减计算
 1 file changed, 2 insertions(+)
⚠ 注意开头那个 main 这条输出是在没开分支的情况下跑的 —— 方括号里显示的是当前分支名。

你要是照第二节做过 git switch -c feat/…,这里应该显示你自己的分支名, 比如 [feat/add-discount 9f3c1a2]。 如果你看到的是 [main …],说明分支没开成 —— 停下来先补上。 直接在 main 上攒改动,正是第 12 页那些回退死角最难收拾的场景。

看存档列表

git log --oneline
  真实输出
1a1b5c7 feat: 第3步 输出报告
31db09a feat: 第2步 计算平均分
74412a5 feat: 第1步 读取分数

前面那串字符是存档编号,第 12 页回退时要用它。加个 --stat 能顺便看每次改了多少:

  真实输出
1a1b5c7 feat: 第3步 输出报告
 report.py | 5 +++++
 1 file changed, 5 insertions(+)
31db09a feat: 第2步 计算平均分
 report.py | 4 ++++
 1 file changed, 4 insertions(+)

八、存档说明怎么写

判断标准只有一条 一次存档要能用一句话讲清楚。讲不清就说明该拆成两次。
写法问题 / 好处
❌更新三天后自己也看不懂
❌修改 / fix bug回退时完全抓瞎
❌完成了今天的工作说明这次存档太大了,该拆
✅feat: 第1步 price 支持满减计算一眼知道做了什么
✅fix: 货币符号改回 ¥回退时能精确定位

常用前缀(社区约定)

前缀用于例子
feat:新功能feat: 订单支持备注字段
fix:修 bugfix: 0 元订单显示错误
test:只动测试test: 给 price 补边界用例
docs:只动文档docs: 补充 README 快速开始
chore:杂务chore: 忽略编辑器配置目录
ci:流水线配置ci: 加质量门禁

「小步」到底多小

一个可操作的节奏
步做什么
1git status —— 看现状
2git diff HEAD —— 看 AI/自己改了什么
3git add -A —— 勾选
4git commit -m "feat: 第N步 xxx" —— 存档

四步一循环。循环得越勤,第 12 页那些回退命令的杀伤范围就越小。

💡 别怕提交多 提交是纯本地行为,不需要联网,不会打扰任何人。
新手最常见的问题是「一天只提交一次」,结果出问题时只能整天回滚。
