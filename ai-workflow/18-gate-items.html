二、测试通过率:必须分级

第 17 页的错误 3 已经点过题,这里补上落地细节。

用例分级test priority阈值前提
① 定义

给每条测试用例打上优先级标签,不同级别配不同阈值。

② 类比

飞机起飞前的检查单。

「发动机能不能点火」和「阅读灯亮不亮」不可能用同一个标准。 发动机一项不过就不飞;阅读灯坏两个照飞不误,记一笔下次修。

把两者混成一个「检查通过率 ≥ 95%」,等于允许发动机不点火。

③ 位置

它是阈值门禁的前提工作 —— 没分级就没法定分级阈值。 这件事要在配门禁之前做。

④ 例子

在 myshop 里,用标记给用例分级:

# 文件:<你的项目>/myshop/pyproject.toml
# ↓ 在你已有的 [tool.pytest.ini_options] 块里追加 markers,别整块替换(会丢 testpaths/addopts 等)

[tool.pytest.ini_options]
pythonpath = ["."]
markers = [
    "p0: 核心链路,挂了就是生产事故",
]
# 文件:<你的项目>/myshop/tests/test_order.py

import pytest

@pytest.mark.p0
def test_订单真的落盘了_换个连接还读得到(tmp_path: Path) -> None:
    数据库 = str(tmp_path / "test.db")
    订单 = create_order("键盘", unit_cents=39900, qty=1, db_path=数据库)
    读回来 = get_order(订单["id"], db_path=数据库)
    assert 读回来["item"] == "键盘"
    assert 读回来["total_cents"] == 39900
    assert 读回来["total_text"] == "¥399.00"

(这是 tests/test_order.py 里已有的测试,给它打上标记即可,不需要新写)然后在流水线里跑两遍,配两条门禁:

# 门禁 A:P0 用例,阈值 100%
pytest -m p0 -q

# 门禁 B:全量用例,阈值 ≥ 95%
pytest -q
⑤ 误区

误区 1:「P0 越多越好」。反了。 P0 应该少而精 —— 如果 80% 的用例都是 P0,等于没分级。 经验值:P0 占全部用例的 5%–15%。

误区 2:「全量 95% 就够了,不用单独配 P0」。 危险。那 5% 的余量里正好是支付流程挂了,门禁照样放行。 P0 100% 这条是分级的全部意义所在。

🔄 一个必须配套的动作:通过率的分母 「通过率 ≥ 95%」这句话有个隐藏漏洞:分母是多少?

如果有人把 100 条用例注释掉 90 条,剩下 10 条全过 —— 通过率 100%,门禁绿灯。

注意:被注释/删除的用例不会计入 skipped,「跳过数门禁」抓不住它。注释/删除式作弊由上面清单里新增的「用例总数门禁」(总数不得少于主干)抓住;@skip 式作弊才由下一节的「跳过数门禁」兜底。单独用通过率,等于给自己留了个后门。

三、🔄 被遗漏的两条:跳过数 & 抖动率

这两条是我第一版完全没写的,但它们恰恰堵住了通过率门禁最大的两个漏洞。

3.1 跳过数门禁

四要素内容
① 检查点提合并请求时,和通过率同一时刻
② 度量指标被跳过(skipped)的用例数
③ 阈值绝对值 ≤ 5,或者更好的:相比主干不增长
④ 失败动作阻断。因为它防的是作弊,不是质量波动
为什么这条比它看起来重要得多 「跳过用例」是让门禁变绿的最省事的办法。

一个用例挂了,修它要一小时;在它上面加一行「暂时跳过」只要三秒,而且流水线立刻变绿。 没有跳过数门禁的话,这个操作零成本、零阻力、而且完全合规。

半年后你会发现项目里有 300 条被跳过的用例,而通过率一直是漂亮的 100%。

这就是第 20 页要专门讲的「防作弊」的第一个具体例子。

myshop 里就有一条真实的跳过 —— 你在第 10 页见过:

  真机输出(Windows 重录;本书配置下 -q 输出就是按文件分行,无匿名点串)
$ .venv\Scripts\python.exe -m pytest -q
tests\test_api.py .......                                                [ 41%]
tests\test_order.py .....                                                [ 70%]
tests\test_price.py .....                                                [100%]
17 passed, 1 skipped in 3.90s
                ↑ 这个 1 是端到端用例,因为没装浏览器驱动被跳过
这个 1 是「良性跳过」还是「作弊跳过」? 良性的。它跳过的原因是依赖缺失(没装浏览器驱动),用的是条件跳过, 换到装了驱动的环境上它就会真跑。

作弊跳过长这样:无条件跳过,理由写着「暂时先跳过,后面修」—— 而那个「后面」永远不会来。

门禁分不清这两种。所以现实的做法是:盯住数字不增长, 新增跳过时人工看一眼原因。

3.2 抖动率门禁

四要素内容
① 检查点定时任务(比如每晚),不放在合并请求上
② 度量指标同一份代码重跑 N 次,结果不一致的用例占比
③ 阈值< 1%
④ 失败动作降级告警 + 通知,不阻断合并
为什么抖动率门禁不能挂在合并请求上 要测抖动率,你得把同一份代码跑很多遍(通常 5–10 遍)。

如果每个合并请求都这么干,流水线时间直接乘 10 —— 没人受得了。

所以它的检查点必须是「每晚定时」,失败动作必须是「告警」而不是「阻断」。 这是四要素里 ① 和 ④ 必须联动的一个典型例子: 换了检查点,失败动作也得跟着换。
抖动率和通过率的关系(回看第 10 页 & 第 17 页错误 3) 第 17 页说「全量通过率留 5% 余量给不稳定用例」—— 那是妥协。

抖动率门禁是这个妥协的解药:它盯着「不稳定用例到底有多少」这个数字本身, 不让那 5% 的余量越吃越多。

没有抖动率门禁的话,通过率阈值会一路往下调:95% → 90% → 85% → 关掉。

四、覆盖率:最容易被误解的指标

代码覆盖率code coverage阈值门禁
① 定义

跑完测试后,统计有多少行代码被执行到了,除以总行数。

② 类比

体检的「检查项覆盖率」,不是「健康度」。

你做了全套体检(覆盖率 100%),只能说明每个部位都被看过一眼, 不能说明你健康 —— 医生可能看了但没看出问题。

反过来,覆盖率 30% 一定意味着有 70% 的部位根本没人看过。

覆盖率能告诉你覆盖率不能告诉你
哪些代码肯定没被测到 被测到的代码是不是测对了
测试的盲区在哪 代码有没有 bug

覆盖率是「盲区探测器」,不是「质量分数」。这是理解它的唯一正确姿势。

③ 位置

典型的阈值门禁。必须先测基线才能定阈值,不能第一天就上。

④ 例子

在 myshop 里量一下(先装工具):

cd <你的项目>/myshop
.venv/bin/python -m pip install pytest-cov
.venv/bin/python -m pytest --cov=myshop --cov-report=term-missing -q

term-missing 会直接列出哪几行没被覆盖 —— 那才是这个工具真正有用的地方, 比那个总百分比有价值得多。

⑤ 误区

误区 1:「覆盖率 100% = 没 bug」。 回看第 8 页那五次改坏实验:把 divmod(cents, 100) 改成 divmod(cents, 10), 覆盖率一点没变(那一行照样被执行),但结果全错了。 覆盖率对「行被执行了但断言不够」完全无感。

误区 2:「把阈值定成 100%」。 会逼出为了覆盖而写的空测试 —— 调用一下函数,不写任何断言。 覆盖率满分,防护力为零。这是第 20 页防作弊的第二个例子。

误区 3:「行覆盖率就够了」。 还有一种分支覆盖率,统计的是「每个 if 的真假两条路都走过没有」。 行覆盖 100% 但分支覆盖 50% 是很常见的 —— 因为你只测了 if 成立的情况。分支覆盖率是更严格、也更有意义的指标。

五、🔄 增量优于全量:「新代码干净」原则

核心思想 不要求老代码达标,只要求「你这次新写 / 改动的代码」达标。

这是主流质量平台近年来的默认推荐姿势,通常叫「新代码干净」原则。
全量门禁增量门禁
量什么整个项目的覆盖率 / 问题数只量本次改动涉及的行
老项目上线 基本不可能 —— 十年老项目覆盖率 12%,定 80% 等于永远合不进去 第一天就能上 —— 老代码原样放过
激励方向 「先别管我,那是历史遗留」 「我这次写的必须干净」
长期效果 要么达标要么关掉,没有中间态 代码库自然地越来越干净 —— 改到哪干净到哪
实现难度低,一个总数就行中,要能算出「本次改了哪些行」
🔄 我第一版的第 4 个错误 我原来写的是「覆盖率 ≥ 80%」,没区分增量和全量。

在 myshop 这种 200 行的新项目里,这个区别不明显。 但在任何真实项目上,不区分就等于这条门禁根本上不了线 —— 你不可能让一个存在了五年的代码库突然达到 80%。

正确说法:「本次改动行的覆盖率 ≥ 80%」。多了「本次改动行」五个字,可行性天差地别。

六、静态扫描类指标

第 4 页讲的规范检查和类型检查是「本地能跑的静态检查」。 门禁阶段通常还会接一个更重的扫描平台,量这几样:

指标量什么 建议阈值为什么这么定
严重 / 高危问题确定会出事的问题(注入、越权、空指针) = 0,阻断 这类问题没有「容忍几个」的说法
中低危问题可能有风险的写法 不增长,降级告警 老项目里通常有几千个,一刀切归零不现实
重复代码率大段复制粘贴的比例 < 3%,降级告警 重复本身不是 bug,但改一处漏一处会变成 bug
依赖漏洞你用的第三方库有没有已知漏洞 严重 = 0,阻断 这个和你写的代码质量无关,但危害一样大
🔄 关于「严重问题数 = 0」这个提法的一处修正 我第一版写的是「问题总数 = 0」。这在任何真实项目上都做不到 —— 扫描工具对一个中等规模项目动辄报几百上千条。

正确的做法是按严重程度分档,只对最高档要求归零,其余用「不增长」。 这和测试用例分级是同一个思路:分档,而不是一刀切。

七、阈值怎么定:基线法与棘轮法

基线法baseline定初值
① 做法

先什么都不拦,连续跑两周,把每次的数字记下来。 然后取当前实际水平,略微上浮作为第一版阈值。

两周实测覆盖率:  61%  63%  62%  65%  64%  63%
当前基线:        ~63%
第一版阈值:      65%     ← 略高于基线,踮踮脚够得着
错误做法:        80%     ← 拍脑袋定的行业"标准",团队直接放弃
② 为什么

阈值的作用是「让情况不再变坏,并缓慢变好」,不是「一步到位达到理想状态」。

定得够不着的阈值,唯一的结果是这条门禁被关掉。

棘轮法ratchet往上收
① 做法

阈值只允许往严格的方向走,不允许往回退。

就像棘轮扳手 —— 只能朝一个方向转,松不回去。

第 1 个月   65%
第 2 个月   68%    ← 上个月稳定超过 68 了,把阈值提上来
第 3 个月   72%
第 4 个月   74%
第 5 个月   76%
第 6 个月   77%
第 7 个月   79%
第 8 个月   80%    ← 一年后自然到达,而不是第一天硬定
② 更省事的写法

与其手动调数字,不如直接写成「不得低于主干当前值」 —— 这样阈值自动跟着涨,谁也不用管。

这条规则同时适用于:覆盖率、中低危问题数、跳过数、重复率。

③ 误区

误区:「阈值定了就不能改」。 可以改,但只能朝严格方向改。往松改必须走正式流程并记录原因 —— 否则每次红了都往下调,门禁就名存实亡了。

八、🔥 官方文档自己也会写错(两个实例)

这一节不讲概念,讲一件事:为什么本教程反复说「自己实测,别照抄文档」。 在核实这一页内容时,我在官方文档里发现了两处实打实的错误。

🔥 实例 1:官方示例代码的注释,和它自己的源码相反 某主流质量平台的官方示例里,有一个「门禁不过时怎么办」的参数。 示例代码的注释写着:这个参数为真时,构建会被标记为「不稳定」(降级告警)。

但我去翻了这个插件的源码 —— 它实际做的是把构建标记为「失败」(直接阻断)。

后果:照着注释理解的人以为自己配了个「温和的告警」, 实际上配的是「硬阻断」。上线当天全组合并请求全红。
🔥 实例 2:官方说明文档里用了一个不存在的参数 某覆盖率插件的官方说明文档中,示例配置写了一个参数名。 我在它的源码里找不到这个参数。

更隐蔽的是:这段配置照抄过去不会报错,也能正常工作。 因为配置解析器忽略了这个不认识的键, 而这个参数「本该实现的行为」恰好和默认行为一致 —— 所以看起来一切正常。

后果:你以为自己显式配置了某个行为,实际上只是碰巧命中了默认值。 哪天默认值一变,你的门禁行为就悄悄变了,而你的配置文件看起来一个字没动。
这两个实例给出的三条操作规矩
#规矩怎么做
1配完门禁,先故意让它红一次 改坏一行代码,推上去,亲眼确认它真的拦住了。 第 19 页整页都在做这件事
2版本号以代码仓库为准 不以文档页为准 —— 第 16 页那两个 @v7 就是这么来的
3配置不报错 ≠ 配置生效 大多数配置解析器会静默忽略不认识的键。 唯一的验证方式是看行为,不是看有没有报错
这跟 AI 有什么关系 AI 生成的配置文件,来源就是这些文档和抄了这些文档的博客。

所以当 AI 给你一份门禁配置时,它极有可能原样复现这两类错误 —— 而且写得非常自信,注释也很详细。

唯一可靠的检验是规矩 1:故意让它红一次。 这也是全书那句话的又一个实例 —— 「自己看改动」是唯一不能外包的事。

九、给小项目的最小可用配置

把这一页的结论收成一份可以直接抄的配置(唯一前提:门禁 3 需要你已按第二节打好 p0 标记)。适用于个人项目和小团队:

# 文件:<你的项目>/.github/workflows/ci.yml

name: 质量门禁

on:
  push:
    branches: [main]
  pull_request:

jobs:
  gate:
    name: 三道检查            # 这个名字要和合并保护规则里填的一字不差
                              # (建规则时是三道;后来加到四道,名字故意不改 —— 改名会和已绑定的保护规则脱钩)
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-python@v7
        with:
          python-version: '3.12'
      - run: pip install pytest mypy ruff

      # ===== 硬门禁 1:代码规范(最快,先跑)=====
      - name: 门禁 1 · 代码规范
        run: ruff check .

      # ===== 硬门禁 2:类型检查 =====
      - name: 门禁 2 · 类型检查
        run: mypy

      # ===== 硬门禁 3:P0 用例必须 100% =====
      # 前提:先按本页第二节打好 p0 标记并在 pyproject 注册 markers;
      # 没打标时 pytest 收集 0 条,以退出码 5 直接变红
      - name: 门禁 3 · P0 核心用例
        run: pytest -m p0 -q

      # ===== 硬门禁 4:全量用例 =====
      # 小项目用例少,直接要求全过;
      # 用例上千之后,把这条换成"通过率 ≥ 95%"的阈值门禁
      - name: 门禁 4 · 全量用例
        run: pytest -q
这份配置刻意没有包含什么,以及为什么
没包含为什么
覆盖率门禁 要先测两周基线才知道阈值定多少。先跑起来,一个月后再加
静态扫描平台 要额外接服务、注册账号。小项目投入产出比低
抖动率门禁 要跑 10 遍。用例少的时候抖动本来就少,不划算
paths 过滤 刻意不加 —— 见第 16、17 页那个永久阻塞的死锁
把 action 钉到 SHA
写 @3d3c42e5… 而不是 @v7		 钉 SHA 防的是「标签被改指向别的提交」这一手。本书刻意用 @v7 —— 第 16 页那个真实的过期陷阱教的正是「以代码仓库的最新标签为准」, 两件事都对,只是对不同的人。
你该钉 SHA,如果:流水线里有密钥、能写仓库、或者公司有合规要求。
钉了要付的代价:action 发安全更新时不会自动跟上,得有人定期升 —— 没人升的 SHA 比浮动标签更危险
钉工具版本
pytest==8.4.2 而不是 pytest		 钉版本能让「今天绿、明天红」少发生。本书刻意不钉 —— 第 16、19 页那两张环境对照表靠的就是 「本地虚拟环境装了半年」对「云端每次全新安装」;钉死了两边同版本,那个对照组就没了, 而它恰恰是「云端才是干净环境」最有力的证据。
你该钉版本,如果:这是要交付的生产项目,不是教材。做法是把版本写进 pyproject.toml 或 requirements.txt,让本地和云端读同一份

四条硬门禁,零个阈值需要拍板,十分钟配完。这就是「先上硬门禁」的意思。

另有三样是「加了没代价」的,所以不在上表里 —— permissions: contents: read(令牌只读)、concurrency(同分支新推送自动取消旧的)、 timeout-minutes(卡住的任务默认能跑六小时)。这三样不需要权衡,直接加进配置就行; 本书配套项目的 ci.yml 已经带上了。
