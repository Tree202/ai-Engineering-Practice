步骤 0 · 建安全网

这一步有三件事,一件都不能少

① 确认工作区干净

cd <你的项目>/myshop && git status

要看到 nothing to commit, working tree clean。不干净就先存档或先收进抽屉。

② 开一条新分支

cd <你的项目>/myshop && git switch -c feat/order-note

③ 确认基线是绿的

cd <你的项目>/myshop && .venv/bin/python -m ruff check . && .venv/bin/python -m mypy && .venv/bin/python -m pytest -q
⚠ 第 ③ 件事最容易被跳过,后果最隐蔽 假设开工前就有 2 条测试是红的,而你没记下来。

AI 改完之后你跑检查,看到 2 条红 —— 你会以为是它改坏的, 让它去修。它修不好,开始乱改甚至删测试。

真相:那 2 条在你开工之前就是红的,跟它一点关系没有。

规矩:开工前跑一次,把结果记下来。

步骤 1–2 · 要方案 + 审方案

怎么进

按 Shift + Tab,一直按到状态栏出现 plan mode on(别数按几下,原因见第 13 页)。

提示词(可直接复制)

读一下 @myshop/ 和 @tests/,搞清楚现状,
给我「给订单加一个可选的备注字段」的实施方案,先别写代码。

方案要说清楚:
- 要改哪几个文件,每个文件改什么
- 拆成几步,每步做完能独立验证
- 每一步之后应该跑哪些检查(给出确切命令)
- 有没有会影响到现有功能的地方

审方案看四件事

看什么警惕信号你该说什么
方向它理解的和你想的不是一回事「你理解错了,我要的是 X 不是 Y」
范围「顺便重构一下」「统一优化」「这次只做 X,别碰其他文件」
步子第一步就要改五个文件「第 1 步拆成三步,每步做完我要能验证」
幻觉提到了你没见过的函数名「那个函数在哪个文件?先确认它存在」
方案阶段改十次,比代码阶段改一次便宜 不满意就继续说,让它改方案。满意了再批准,它才开始动手。

嫌来回说话麻烦?按 Ctrl + G 把计划拉进编辑器直接改。
什么时候可以跳过这两步 判断标准:如果你能一句话把要改的东西说清楚,就不需要方案。
比如「把这个报错信息改成中文」—— 直接说就行。

步骤 3 · 做一步 + 自测

先把这句话拆开

半句在管什么
「实施方案第 1 步」管做多少(分量控制)
「改完跑检查,修到干净」管做完怎么验收(质量控制)
🔥 一个关键的时间差:指令下发 ≠ 验证执行 很多人看到这句会以为「还没写代码就要测试了?」不是。 执行顺序是先改代码 → 再跑检查。

但验收标准要在派活的时候就一起给出,原因是:
时机AI 的动机
事前给它带着「最后要过检查」这个约束去写代码,写的时候就在朝这个标准靠
事后追加它已经进入「我做完了」的状态,动机变成「用最小改动让红变绿」 —— 这正是作弊的温床

为什么只做「第一步」

后果说明
改动大到你读不动一步 50 行你会认真看,五步 500 行你只会拉到底说「看着还行」。步骤 4 就这样悄悄失效了
错误会叠加第 1 步的设计错了,后面四步全建在这个错误上。第 5 步才发现 = 前四步全废
回退粒度太粗五步做完才发现问题,只能整个推翻
上下文越长越容易漂连续工作五步,后面它会开始忘掉你最初的约束
「一步」应该多大 判断标准只有一个:这一步做完,能不能独立验证、独立存档?
✅ 好的一步❌ 不好的一步
给数据表加一个 note 字段和迁移 做备注功能
给某个函数加参数并补单元测试 把整个订单模块重构一遍

新手期宁可切得太碎。碎了最多多几轮对话,大了是你彻底失去控制。

提示词模板(核心成品)

实施方案第 1 步。

改完自己跑这三条,修到全绿:
  .venv/bin/python -m ruff check .
  .venv/bin/python -m mypy
  .venv/bin/python -m pytest tests/test_order.py

约束:
- 不许改动任何测试文件;不许跳过、注释掉或放宽断言
- 如果你认为测试本身有问题,停下来告诉我,不要自己改
- 不要改本步骤范围之外的文件
- 把命令的真实输出贴给我,不要只说"通过了"

做完第 1 步就停,等我检查,不要继续做第 2 步。

五条约束各防什么

约束在防什么
不许改测试文件改断言让红变绿 —— 最常见的作弊
有问题先告诉我给它一个诚实的出口,否则它只能硬来
不改范围外文件范围蔓延
贴真实输出它没跑却声称跑过了 —— 比你想的常见
做完就停防止它一路做到第 5 步
💡 注意第一条的措辞 写的是「不许改测试文件」,不是「不许改代码」。 真 bug 该修还是要修,禁止的是「用改断言代替修代码」。

它执行时你会看到什么

  会话里的真实过程
● Bash(.venv/bin/python -m mypy)
  ├ myshop/order.py:52: error: Incompatible types  [assignment]

● 我看到一个类型错误,正在修复...

● Bash(.venv/bin/python -m mypy)
  ├ Success: no issues found in 10 source files

● Bash(.venv/bin/python -m pytest tests/test_order.py)
  ├ 5 passed in 0.02s
为什么这比「你觉得对吗」可靠 输出来自检查工具,不来自模型。类型检查器不会给 AI 面子,测试运行器也不会。

这也解释了对比表里「让它自测」为什么可靠性写「中(会作弊,要盯)」而不是「低」: 输出本身是硬的,作弊发生在「它改了什么」这一侧。 所以你要盯的不是输出,是改动。

两条止损规则

⚠ 防止它在坑里越挖越深
  1. 红得超过五六个 → 停下来自己看一眼。 大面积飘红通常意味着方向性错误(改错文件、依赖没装),让它闷头一个个修是纯浪费,还会塞满上下文
  2. 同一个测试改三轮还不绿 → 人工介入。 它会来回改同两个文件,每轮都说「这次应该好了」。每多一轮,改动越离谱,回退成本越高

步骤 4 · 你自己看改动

!git status
!git diff HEAD
开头那个 ! 是这一步的全部价值 它让命令直接执行、不经过模型,输出直接进你的眼睛。

如果你让 AI 去跑再讲给你听,就等于让它评价自己的作业。

带着这四个问题看

#问自己怎么查
1有没有我没预期的文件?git status --short
2测试文件的断言被改了吗?见下面那条命令
3有没有它新建、我不知道的文件?git status -s 里的 ??
4改动规模和「第一步」对得上吗?git diff --stat;对不上就是超范围

一条专门揪出「测试被动过」的命令

!git diff HEAD --name-only | grep -E '^tests/|_test\.py$'
有输出 = 测试文件被改过了,停下来仔细看 这不一定是坏事(补测试是好事),但它一定值得你多看一眼 —— 因为第 9 页那场事故的引信,正是「顺手改了对应的测试」。

三类只有你能发现的问题

盲区具体表现在改动里怎么发现
① 改测试作弊 改断言值、跳过、注释掉、包个空的异常捕获 改动文件列表里出现 tests/ —— 一眼就能看见
② 范围蔓延 你让它改 A,它顺手「优化」了 B、重命名了 C 出现了你没要求改的文件
③ 写了但没接上 新建了函数但没有任何地方调用 只有新增、没有对应的调用点改动
这三类的共同点 它们都躲在「检查通过」和「做对了」之间的那条缝里。

反直觉但重要:检查越绿越要看改动 —— 因为绿色会让你放松, 而绿色偏偏不覆盖这三类。

步骤 5 · 三层撤销阶梯

看完改动,你要判断:损伤有多大?

5a · 满意 → 全量检查 → 存档

cd <你的项目>/myshop && .venv/bin/python -m ruff check . && .venv/bin/python -m mypy && .venv/bin/python -m pytest
⚠ 注意这次没有指定文件 —— 是全量 为什么步骤 3 已经跑过一次还要再跑? 因为它们回答的是两个不同的问题(第 9 页那场事故就是证据):
步骤 3 · 局部我刚写的这段,自己立得住吗?
步骤 5a · 全量这次改动的爆炸半径有多大?

全量三道加起来也就 4 秒上下(pytest 占 3.66 秒)。

全绿之后存档:

cd <你的项目>/myshop && git add -A && git commit -m "feat: 第1步 订单表加 note 字段"

5b · 小问题 → 直接说

可以,但有两个小问题:
1. 那个字段名 n 改成 note
2. 备注为空时不要写入数据库,保持 NULL

改完还是跑一遍 mypy 和 pytest tests/test_order.py。

这是成本最低的一档,零回退。大部分情况都该走这里。

5c · 方向错了 → 撤销

在空的输入框里连按两次 Esc,选一个之前的提问点,选择「同时恢复代码和对话」。

兜底 · 全烂了 → 用存档系统

cd <你的项目>/myshop && git status
cd <你的项目>/myshop && git reset --hard HEAD
cd <你的项目>/myshop && git clean -fdn
cd <你的项目>/myshop && git clean -fd
🔥 记住:两步缺一不可 reset 管老文件,clean 管新文件。
只做第一步,你会以为「回退失败了」—— 因为 AI 新建的文件还躺在那儿(第 12 页详解)。

三档的选择规则

损伤程度走哪档代价
方向对,细节不满意5b 直接说零回退
这一轮整体跑偏5c 一键撤销退这一轮,但命令的后果不退
好几轮都烂了存档系统兜底退回上一个存档点
规则:从上往下走,能用上面的就别用下面的 不要一看到问题就撤销。大部分情况「直接说」就够了,而且最便宜。

步骤 6 · 循环

  一轮的实际对话
你: 实施方案第 2 步。改完跑 ruff / mypy / pytest tests/test_api.py,
    修到绿。约束同上。做完停。

AI: [改代码 → 跑检查 → 有错自己修 → 全绿 → 停下]

你: !git status
你: !git diff HEAD                 ← 步骤 4,你自己的眼睛

你: 可以。跑一次全量再存档。

AI: [全量检查 → 17 passed → git add -A && git commit]

你: 做第 3 步,同样的要求。
你会发现流程其实很轻 真正花你时间的只有一件事:读改动。其他全是模板化的指令。

而且每一步的改动都很小(因为你只让它做一步),读起来很快。 这就是「小步」的全部意义 —— 它让唯一无法外包的那件事,变得做得动。
💡 什么时候该开新对话 跑到第三四轮,上下文里全是旧改动和旧报错,AI 开始翻旧账。
规矩:一次存档打完 = 一次 /clear。

步骤 7 · 最后总审

① 跑真正的全套(含最贵的那层)

cd <你的项目>/myshop && .venv/bin/python -m ruff check . && .venv/bin/python -m mypy && .venv/bin/python -m pytest

如果项目有端到端测试:

cd <你的项目>/myshop && .venv/bin/python -m pytest tests/e2e/
⚠ 端到端测试为什么只在这里跑一次 它天生时红时绿。人看到偶发失败会说「重跑一下」; AI 会认定「一定是我改坏的」,然后去修一个不存在的问题, 并且很可能用「加等待 / 放宽断言」的方式「修好」它(第 10 页详解)。

所以它绝不进日常循环。

跑它时的提示词要堵死四条歪路:

跑一次 .venv/bin/python -m pytest tests/e2e/。

如果有失败:
- 先原样重跑一遍,确认是偶发还是稳定复现
- 不许用增加等待、加重试、放宽断言、跳过 这四种方式让它变绿
- 稳定复现的话告诉我是哪条、错在哪一步,先别动手改

② 通读完整改动

!git diff main...HEAD

这是从分支起点到现在的全部改动。这一遍看的是「整体」: 有没有互相矛盾的设计、有没有该删没删的临时代码、命名是否一致。

③ 让它自己再审一遍

/review
注意顺序:先你看,再让它看 不要用 /review 代替第 ② 步。

它审的是「代码质量」,你审的是「这是不是我要的东西」 —— 后者它永远不知道。

而且如果你先看它的报告再看改动,你的判断会被它的结论锚定。先形成自己的看法。
⚠ 关于 --fix /code-review --fix 会直接改代码。而这类改动一键撤销救不回来 (官方文档明确点名了后台运行的审查修复任务)。

用它之前先确保你已经存过档。
