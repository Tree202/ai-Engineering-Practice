一、什么是流水线

持续集成流水线CI pipeline云端
① 定义

一台不属于你的机器,在你每次推送代码时自动把它拉下来、装好环境、跑一遍检查,然后告诉大家结果。

② 类比

工厂流水线上的质检工位。

零件做好之后,不是你自己说「我觉得没问题」就能进下一道工序 —— 它要经过一排质检工位,每个工位查一样东西。任何一个工位不放行,零件就停在那儿。

关键在于:那些工位不归你管,你也没法让它们「通融一下」。

③ 位置

它是七步流程的下游:

你在本地走完七步 → 推送 → 流水线接手

它和本地检查不是替代关系,而是同一批检查在两个地方各跑一次 —— 第三节专门解释为什么要这样。

④ 例子

常见的流水线服务有好几家,本教程用 GitHub Actions 举例,因为它免费且配置就是仓库里一个文件。 Jenkins 是另一个常见选择。

你要做的只有一件事:在仓库里放一个配置文件。它会被自动发现,不需要在网页上点任何按钮。

⑤ 误区

误区 1:「有了流水线就不用本地检查了」。 大错。用流水线当调试工具是最慢最贵的开发方式 —— 一个来回 10 分钟,而本地一个来回 3 秒。

误区 2:「流水线红了 = 我的代码有问题」。 不一定 —— 也可能是环境问题、依赖服务挂了、或者别人的改动。第 19 页有一次真实的故障排查实录。

二、8 道关卡

关卡在哪谁触发能不能跳过
①本地你打字(编辑器自动)自动的,想跳也跳不掉
②本地你 / AI 敲命令能,你不跑就不跑
③本地存档时(提交钩子)能 —— 加一个参数就绕过
④本地推送时(推送钩子)能 —— 同上
⑤云端提合并请求不能
⑥云端合并进主干不能
⑦云端部署完成不能
⑧云端上线不能

三、为什么同一层要跑两遍

同一条命令,在两个地方跑,目的完全不同
本地跑云端跑
目的快速反馈强制执行
给谁看你自己团队 / 主干
范围局部(只跑改动相关的)全量
能否绕过✅ 能❌ 不能
环境你的机器(每个人都不一样)统一的干净环境
失败代价你自己再改一次合不进主干

两个理由,缺一不可

理由说明
① 本地可以被绕过 加一个参数,一秒钟就绕过所有本地钩子。赶时间的时候人人都会这么干,包括你。 云端不行 —— 它跑在你控制不了的机器上
②「在我机器上是好的」 你本地一个 Python 版本、同事另一个、生产第三个;你装了某个包、云端没装; 你的配置文件里有个设置别人没有。云端是唯一的权威裁判
本地跑是为了「快」,云端跑是为了「不可绕过」。
同一条命令,两种角色。
对本教程前 15 页的一个推论 那套七步流程覆盖的全是「云端之前」的部分。 它的目标是:让你推上去的代码,在进流水线之前就已经是绿的。

流水线是最后一道保险,不是你的调试工具。

四、本地钩子:能被一个参数绕过

提交钩子pre-commit hook本地
① 定义

一个脚本,放在存档系统的特定位置。你每次存档时它会自动运行, 脚本返回失败就拦下这次存档。

② 类比

自家门口的地垫。

你在门口放了块「进门请擦鞋」的垫子。它确实有用 —— 但它拦不住任何一个决定不擦的人。

③ 位置

它属于关卡 ③。和云端门禁最大的区别在于:它在你自己机器上,归你管。

还有一个结构性局限:钩子文件不会被存档、也不会被推送 —— 别人拉你的仓库,不会自动得到它。

④ 例子

手写一个最简单的(不需要装任何东西),在 myshop 项目根目录执行:

cat > .git/hooks/pre-commit <<'SH'
#!/bin/sh
PY=.venv/bin/python

echo ""
echo "本地检查:提交前跑 3 道"

printf "  [1/3] ruff   ...... "
$PY -m ruff check . > /tmp/g1.log 2>&1 || { echo "未通过"; cat /tmp/g1.log; exit 1; }
echo "通过"

printf "  [2/3] mypy   ...... "
$PY -m mypy > /tmp/g2.log 2>&1 || { echo "未通过"; cat /tmp/g2.log; exit 1; }
echo "通过"

printf "  [3/3] pytest ...... "
$PY -m pytest -q > /tmp/g3.log 2>&1 || { echo "未通过"; tail -18 /tmp/g3.log; exit 1; }
echo "通过"

echo "  全部通过,放行"
exit 0
SH
chmod +x .git/hooks/pre-commit

规则只有一条:脚本返回 0 = 放行,返回非 0 = 拦下。

⑤ 误区

误区 1:「装了钩子就安全了」。 加一个参数就能完全绕过它 —— 下面有真机实测。

误区 2:「钩子会跟着仓库分发给同事」。 不会。它在存档系统的内部目录里,那个目录不进版本控制。 要让全组都有,得用专门的工具(见下)。

真机实测:三个场景

  场景 1:代码是好的
$ git commit -m "docs: 好代码应该被放行"

  本地检查:提交前跑 3 道
  [1/3] ruff   ...... 通过
  [2/3] mypy   ...... 通过
  [3/3] pytest ...... 通过
  全部通过,放行

[main b27d579] docs: 好代码应该被放行
  场景 2:代码坏了(把 ¥ 改成 $)
$ git commit -m "feat: 这次改动有问题"

  [1/3] ruff   ...... 通过
  [2/3] mypy   ...... 通过
  [3/3] pytest ...... 未通过
  ==================== 8 failed, 9 passed, 1 skipped ====================

$ echo $?
1

$ git log --oneline -1
b27d579 docs: 好代码应该被放行     ← 坏代码没进去
  🔥 场景 3:加一个参数
$ git commit --no-verify -m "我绕过了检查,坏代码就这么进来了"

[main 4c5dd7c] 我绕过了检查,坏代码就这么进来了
 4 files changed, 26 insertions(+), 1 deletion(-)

$ echo $?
0

$ .venv/bin/python -m pytest -q
==================== 8 failed, 9 passed, 1 skipped ====================
← 主干上的代码现在是坏的
🔥 场景 3 是本页的核心结论 注意:那个检查的框根本没打印出来 —— --no-verify 让存档系统压根不执行钩子。

多打 12 个字符,一道防线就形同不存在。

这就是为什么本地的检查叫「提醒」,云端的才叫「门禁」。 推送时的钩子同理,也有对应的绕过参数。
🔄 想让全组共享钩子:用 pre-commit 框架 它是一个专门管理钩子的工具,配置文件会进版本控制,所以全组一致。

经核实的一处修正:规范检查工具的钩子标识符现在官方推荐用带 -check 后缀的那个, 老的写法虽然还能用,但已被官方在配置里明确标注为「遗留别名」。 写配置时请去该工具的官方仓库确认当前标识符 —— 这类名字会随版本变。

五、快速失败:便宜的先跑

快速失败fail fast排序原则
① 定义

把又快又便宜的检查排在前面。前面挂了,后面的全都不跑。

② 类比

机场安检的顺序。

先查证件(3 秒),再过安检门(10 秒),最后才开箱细检(3 分钟)。 如果你证件就不对,没人会先花 3 分钟给你开箱。

③ 位置

它是流水线的排序原则,和第 5 页的测试金字塔方向一致 —— 金字塔从下往上跑,流水线也从便宜往贵排。

④ 例子
规范检查(30 秒)→ 单元测试(2 分钟)→ 集成(8 分钟)→ 端到端(25 分钟)
      ↑
   第一道就挡住,后面 35 分钟全省了

规范检查挂了,就没必要花 25 分钟跑端到端才告诉你「你有个变量没用到」。

⑤ 误区

误区:「顺序无所谓,反正都要跑」。 不是。假设 30% 的推送会被规范检查挡下,把它排最后意味着这 30% 的人 每次都白等 35 分钟。

六、真机实证:两个完全不同的环境

这是本页最有说服力的一段。同一份代码,在两个完全不同的环境上跑:

你的 Mac云端流水线
操作系统macOS(darwin)Linux
Python3.9.63.12.13
测试运行器8.4.29.1.1
结果 8 failed, 9 passed, 1 skipped in 3.66s 8 failed, 9 passed, 1 skipped in 3.66s

注:耗时为 macOS 环境实测值;Linux 环境的红绿计数一致,耗时未逐字核录。

完全不同的操作系统、差三个大版本的 Python、差一个大版本的运行器 —— 结论一字不差
这正好验证了第三节那句「在我机器上是好的」: 流水线的价值就在于它是一个和你不一样的干净环境。

如果代码只在你这个版本上能过、在新版本上挂了,流水线会当场抓住; 而这次两边一致,说明那个 bug 是真 bug,不是环境问题。

七、一个最小的流水线配置

在仓库里建一个文件,路径(相对项目根目录)必须是这个:

.github/workflows/ci.yml
name: 检查

on:
  push:
    branches: [main]
  pull_request:            # ← 提合并请求时也跑

jobs:
  check:
    name: 三道检查         # ← 这个名字很重要,第 19 页会用到
    runs-on: ubuntu-latest # 云端提供的一台干净 Linux

    steps:
      - name: 拉取代码
        uses: actions/checkout@v7

      - name: 装 Python
        uses: actions/setup-python@v7
        with:
          python-version: '3.12'

      # 云端机器是一次性的,跑完就销毁,
      # 不存在「污染系统环境」的问题,所以直接装,不用虚拟环境
      - name: 装检查工具
        run: pip install pytest mypy ruff

      # ===== 便宜的先跑 =====
      - name: 规范检查
        run: ruff check .

      - name: 类型检查
        run: mypy

      - name: 测试
        run: pytest -q

三段结构

段关键字说明
什么时候跑on:推送时、提合并请求时
在哪跑runs-on:云端提供的一台干净机器
跑什么steps:一步一步执行,任何一步返回非 0 就整个失败
判定规则和你本地的钩子完全一样 任何一个 run 的命令返回非 0,这个任务就失败。

同样的三条命令、同样的判定逻辑。唯一的区别是它跑在别人的机器上。
🔄 关于那两个 @v7 —— 一个真实的过期陷阱 这里引用了两个现成的动作组件,后面的 @v7 是版本号。

核实时发现:官方教程页上写的还是更老的版本号,比它自己的代码仓库落后了两个大版本。

规矩:版本号以该组件的代码仓库为准,不要以文档页为准。 这也是本教程反复强调「自己实测,别抄博客」的一个具体例子。

(本页版本号核实于 2026-08。你读到时可能又变了 —— 去仓库看最新标签。)
🔄 还有一个和后面直接相关的坑 你可能想加 paths: 过滤来省流水线时间(「只有改了某些文件才跑」)。 这里有一个会导致永久卡死的陷阱:
情况结果
任务因条件判断为假被跳过上报为成功,不阻塞
整个流程因 paths 过滤没被触发 检查根本不上报 → 一直停在「等待中」→ 永久阻塞合并

上面那份配置没有加 paths 过滤 —— 这恰好避开了这个死锁,是个安全的入门默认。 第 17 页讲门禁时会再回到这个问题。
