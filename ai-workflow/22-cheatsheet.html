三、Python 与测试命令

# 全都在项目根目录下执行
cd <你的项目>/myshop

# ---- 建环境(只做一次)----
python3 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install pytest mypy ruff

# ---- 每天用的四条 ----
.venv/bin/python -m ruff check .              # 规范检查(最快)
.venv/bin/python -m ruff check . --fix        # 能自动修的直接修掉
.venv/bin/python -m mypy                      # 类型检查
.venv/bin/python -m pytest -q                 # 全部测试

# ---- 测试的常用参数 ----
.venv/bin/python -m pytest -q                       # 安静模式,只看结果
.venv/bin/python -m pytest -v                       # 每条用例一行
.venv/bin/python -m pytest tests/test_price.py      # 只跑一个文件
.venv/bin/python -m pytest -k "价格"                 # 名字里含"价格"的
.venv/bin/python -m pytest -m p0                    # 只跑 P0 标记的
.venv/bin/python -m pytest -x                       # 第一条挂了就停
.venv/bin/python -m pytest --lf                     # 只重跑上次挂的
.venv/bin/python -m pytest -s                       # 让 print 显示出来

# ---- 覆盖率 ----
.venv/bin/python -m pip install pytest-cov
.venv/bin/python -m pytest --cov=myshop --cov-report=term-missing -q
#                                        ↑ 列出哪几行没被覆盖,比总百分比有用得多
为什么全都写成 .venv/bin/python -m xxx 因为它精确指定了「用哪个 Python」。

直接敲 pytest 时,你用的是系统路径里碰巧排在最前面的那个 —— 很可能不是虚拟环境里那个,于是出现「明明装了却说找不到」。

多打十几个字符,换掉一整类玄学问题。出自 第 2 页。

四、退出码速查

退出码是所有门禁判定的基础 —— 第 17 页说的「隐式硬门禁」,判的就是它。

退出码测试运行器的含义门禁怎么处理
0全部通过放行
1有用例挂了阻断 —— 最常见的一种
2被用户中断(官方口径;实测收集出错如 import 失败也返回 2)阻断
3内部错误阻断
4命令行用法错了阻断 —— 说明你的门禁配置写错了
5一条用例都没找到 阻断。这个最阴险 —— 见下
🔥 退出码 5:「一条用例都没找到」 想象一下:目录写错了、或者所有用例都被删了 ——

如果运行器返回 0(「没有失败啊」),你的门禁会亮绿灯,而实际上一条测试都没跑。

返回 5 就是为了防这个。它明确区分了「跑了都过了」和「压根没跑」。

这也是第 20 页手法 2(删用例)会被自动挡住的原因之一 —— 但只在「删光了」时才挡得住,删一半照样是 0。所以还是需要用例数门禁。
其它退出码含义
127命令找不到 —— 十有八九是工具没装或路径写错
128 + N被信号 N 杀掉的。POSIX(macOS/Linux)环境下,例如 130 = 128+2 是被 Ctrl+C 中断、143 = 128+15 是被 SIGTERM 终止, 不是逻辑失败 —— 排查时别把它当 bug 查

五、存档系统命令

# ---- 看状态(最常用的三条)----
git status              # 现在有哪些改动
git diff                # 改动的具体内容(还没暂存的)
git diff --stat         # 🔥 只看"改了哪几个文件、各改了几行" ← 第 20 页那一步

# ---- 存档 ----
git add -A              # 把所有改动放上传送带
git commit -m "说明"     # 结账,存成一个档
git log --oneline -5    # 看最近 5 个存档

# ---- 分支 ----
git switch -c feat/xxx  # 新建并切到一个新分支
git switch main         # 切回主干
git branch              # 看有哪些分支

# ---- 推送 ----
git push -u origin feat/xxx    # 第一次推这个分支
git push                       # 之后就这样

# ---- 绕过本地钩子(🔥 知道它存在,但尽量别用)----
git commit --no-verify -m "说明"
存档说明怎么写 格式:类型: 做了什么
类型用在什么时候例子
feat加了新功能feat: 下单接口支持折扣
fix修了 bugfix: 单价为负数时不再写库
test只动了测试test: 补上非法 JSON 的用例
docs只动了文档docs: 补 CLAUDE.md 的运行说明
refactor改结构不改行为refactor: 校验逻辑提到函数开头

一条存档说清一件事 —— 如果你的说明里出现了「顺便」「以及」, 说明这次应该拆成两条。出自 第 11 页。

六、撤销阶梯

从轻到重,先试上面的。越往下越危险。

级命令 撤掉什么危险度
0工具自带的一键回退 AI 这一轮做的所有改动 安全,首选
1git restore <文件> 某个文件还没暂存的改动 安全,只影响指定文件
2git restore --staged <文件> 把文件从传送带上拿下来(改动还在) 安全
3git reset --hard HEAD 所有已跟踪文件的改动,回到最近一次存档 危险 —— 改动找不回来
4git clean -fd 所有没被跟踪的新文件和新目录 很危险 —— 会删掉你手写的新文件
用第 3、4 级之前,先跑一遍「预演」 
git status              # 先看清楚现在到底有哪些改动
git clean -nd           # 🔥 -n = 只打印会删哪些,不真删

git clean 删掉的东西没有任何地方能找回来 —— 它删的正是「还没进过存档系统」的文件。先 -nd 看一眼,再 -fd 动手。

出自 第 12 页。

七、门禁四要素 & 阈值参考

四要素回答什么填不满说明什么
① 检查点在流程的哪一步查你还没想清楚它该拦在哪
② 度量指标量什么你其实只是想「跑一下看看」
③ 阈值与判定规则多少算过这条不是门禁,是报告
④ 失败动作不过怎么办这条不是门禁,是装饰

阈值参考值

类指标 建议阈值失败动作备注
硬 代码规范退出码 = 0阻断第一天就上
类型检查退出码 = 0阻断第一天就上
P0 用例100% 阻断这条不能松
严重安全问题= 0 阻断不是「总数 = 0」
阈
值		 全量通过率≥ 95%阻断留 5% 给抖动
增量覆盖率≥ 80% 降级告警「本次改动行」,不是全量
跳过数≤ 5 或不增长阻断 防作弊,不是防质量波动
用例总数不得少于主干阻断 堵住「删用例」(弱门禁,防纯删除;防不住语义替换)
抖动率< 1%告警 检查点必须是定时任务
重复代码率< 3%告警—
定阈值的两条方法 基线法(定初值):先两周不拦只记录,取实际水平略微上浮。 不要拍脑袋抄行业数字。

棘轮法(往上收):阈值只准朝严格方向走。 最省事的写法是「不得低于主干当前值」—— 阈值自动跟着涨,谁也不用管。

出自 第 18 页。

八、云端门禁命令

# ---- 看合并请求的状态 ----
gh pr checks 1                                        # 各项检查的结果
gh pr view 1 --json mergeStateStatus -q .mergeStateStatus   # 🔥 看这个
gh pr view 1 --json mergeable -q .mergeable                 # 这个只管有没有冲突

# ---- 配分支保护 ----
gh api -X PUT repos/<账号>/<仓库>/branches/main/protection --input - <<'JSON'
{
  "required_status_checks": { "strict": true, "contexts": ["三道检查"] },
  "enforce_admins": true,
  "required_pull_request_reviews": null,
  "restrictions": null
}
JSON

# ---- 看当前保护规则 ----
gh api repos/<账号>/<仓库>/branches/main/protection
mergeStateStatus含义该怎么办
CLEAN全绿合
BLOCKED被保护规则挡住看是门禁红了还是缺评审
BEHIND落后主干先同步主干再说
UNSTABLE有检查红了但它不是必需的这就是「降级告警」的实物
DIRTY有代码冲突解冲突
🔥 两个必查的配置项
配置项配错的后果
contexts 里的名字 必须和流水线里 name: 一字不差。 填错 → 永久等待,没有任何错误提示
enforce_admins 默认是 false → 管理员可以强制合并 → 你的门禁对管理员形同虚设

出自 第 19 页,两条都是真机验证过的。

九、排错路径

现象最可能的原因先查这个
「明明装了却说找不到」用的不是虚拟环境里的 Python which python;改用 .venv/bin/python -m
测试跑不起来,说找不到模块项目根目录不在搜索路径里 配置里的 pythonpath = ["."]
本地全绿,云端红环境不一样 比对两边的版本号(第 19 页那张表)
本地红,云端绿本地有残留的缓存 / 数据库文件 删掉缓存目录重跑
合并按钮灰着,但流水线是绿的第 ① 层:保护规则 contexts 里的名字对不对;缺不缺评审
合并请求永久卡在「等待中」名字填错,或 paths 过滤没触发 去看有没有这个名字的检查真的上报过
流水线红了但没跑到测试第 ② 层:前置条件 依赖装没装上、代码拉没拉下来
同一条用例时红时绿抖动用例 看等待逻辑是不是「等 N 秒」而不是「等到出现」
接口查不到东西,查了很多次 你的观测方式错了 换通道 —— 直接打开网页看
排错的元规则(第 19 页亲历) 同一个方法失败两次,不要试第三次 —— 换一个完全不同的观测通道。

重复同一个失败的观测只增加信心,不增加信息。

「我没查到」和「它不存在」是两件事。

十一、二十条硬规矩

全书所有「必须 / 不准」类结论的汇总。抄进你的项目说明文件就能用。

#规矩出处
1命令一律写成 .venv/bin/python -m xxx,不要裸敲工具名02

9不准新增跳过标记;不准删已有用例20
10不准修改门禁配置和阈值20
11同一个方法失败两次就换通道,不要试第三次19
