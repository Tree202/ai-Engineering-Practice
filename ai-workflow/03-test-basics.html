一、测试是代码,不是文档

一句话回答 测试是真实的、可执行的代码文件。不是自然语言,不是文档,也不是让 AI「在心里过一遍」。

一个测试长什么样

假设你有这么一个函数(这是第 6 页那个练习项目里真实的代码):

# 文件:项目根目录下的 myshop/price.py

def format_price(cents: int) -> str:
    """把「分」换算成人类看的价格字符串。1234 -> "¥12.34" """
    if cents < 0:
        raise ValueError("价格不能为负数")
    yuan, fen = divmod(cents, 100)     # divmod(1234,100) -> (12, 34)
    return f"¥{yuan}.{fen:02d}"        # :02d = 不足两位前面补 0

它的测试是另一个真实存在的文件:

# 文件:项目根目录下的 tests/test_price.py

import pytest

from myshop.price import format_price


def test_普通价格() -> None:
    assert format_price(1234) == "¥12.34"


def test_零元是边界值() -> None:
    # 0 很容易被漏掉,专门写一条
    assert format_price(0) == "¥0.00"


def test_不足一角要在前面补零() -> None:
    # 5 分不能显示成 "¥0.5",必须是 "¥0.05"
    assert format_price(5) == "¥0.05"


def test_整数元不能丢掉小数位() -> None:
    assert format_price(10000) == "¥100.00"


def test_负数要报错() -> None:
    # 「该报错的时候有没有报错」也是行为的一部分,同样要测
    with pytest.raises(ValueError):
        format_price(-1)

逐行解剖

部分是什么
test_price.py 文件名里的 test_ 是硬规则。运行器启动时会自动扫描全项目,把符合命名的文件找出来执行
from myshop.price import ...把要测的那个函数真的引进来
def test_普通价格() 一条测试用例。函数名必须以 test 开头,后面可以用中文
assert A == B 断言 —— 整个测试的心脏。意思是「我期望 A 等于 B」,不等就判定失败
pytest.raises(ValueError)断言「这里应该抛异常」。没抛反而算失败
中文测试名真的可以用 def test_零元是边界值() 完全正常,输出里中文照常显示。 唯一前提:函数名必须以 test 开头,中文只能出现在后面。 写成 def 测试_零元() 是不会被找到的。

对初学者来说这个非常值钱 —— 测试名用中文写,你一眼就知道每条在测什么。

二、断言:整个测试的心脏

断言assert核心
① 定义

一句「我打包票这里应该是这样」。是就继续,不是就当场失败。

② 类比

质检员的卡尺。

零件下线,质检员拿卡尺一量:「应该是 10.0 毫米。」量出来 10.0 就放行,量出来 9.7 就当场拦下。 卡尺不商量、不通融、不看你今天心情好不好。

③ 位置

它是 Python 自带的关键字,不是测试工具提供的 —— 你在任何代码里都能用。

它和「测试运行器」是被使用与使用的关系:断言负责判断对错,运行器负责组织执行和汇报。

④ 例子

规则只有一条:

assert 条件        # 条件为真 -> 什么都不发生
                  # 条件为假 -> 抛出 AssertionError

你可以现在就在终端里试(在 myshop 项目根目录执行):

.venv/bin/python -c "assert 1 + 1 == 2; print('通过了')"
  真实输出
通过了

把 2 改成 3 再跑:

  真实输出
Traceback (most recent call last):
  File "<string>", line 1, in <module>
AssertionError

注意这里只有孤零零一行 AssertionError,什么信息都没有。下一节讲为什么在测试里不是这样。

⑤ 误区

误区 1:「assert 是测试专用的」。不是,它是 Python 内置关键字。

误区 2:「断言可以不写具体值」。 assert result 这种只判断「非空」的断言,几乎测不出任何东西。 好断言里一定有一个写死的期望值 —— 第 20 页会用这条标准来识别垃圾测试。

为什么测试里的报错信息这么详细 上面终端里的原生断言只打印一行 AssertionError。而测试里却能打印出两边的值、还标出差在第几个字符。

因为运行器在加载测试文件时,会重写你写的 assert 语句, 让它在失败时把两边的值都抓出来做对比。这个功能叫 断言重写(assertion rewriting)。

这是 pytest 比 Python 自带测试框架好用的最大原因。

三、运行器做的三件事

测试运行器test runner / pytest工具
① 定义

一个程序,负责把你写的测试找出来、挨个执行、汇总报告。它本身不知道你的业务。

② 类比

监考老师 + 阅卷机。

它收卷、批改、报分数。但题目和标准答案是你自己出的 —— 它一道题都不会出。

③ 位置

它和「测试文件」是执行与被执行的关系。很多人把两者混为一谈,记住这个区分:

是什么
pytest工具。你 pip install 装的那个
test_*.py你写的普通 Python 代码
④ 例子

它做的三件事:

第几件做什么怎么做
①找 按四条规则扫描:文件名 test_*.py、函数名 test 开头、类名 Test 开头、类不能有 __init__
②跑 把找到的每个函数当普通函数调用一次。就这么简单,没别的魔法
③报 判定标准只有一条:正常跑完 = 通过;抛出任何异常 = 失败
⑤ 误区

误区 1:「pytest 会自动测我的代码」。不会。它只执行你写下的东西。 你没想到要检查的场景,它一个也不会替你想。

误区 2:「没有红字就是全跑了」。不一定 —— 文件名不匹配的测试会静默地完全不运行(第 2 页讲过)。 要看 collected N items 那个数字。

退出码:给机器看的结果

人看的是绿字红字,机器看的是退出码。这个概念在第 17 页讲质量门禁时是核心。

退出码含义什么时候会遇到
0全部通过正常情况
1有测试失败最常见的失败
2被中断收集阶段就出错,比如 import 失败
3内部错误很少见
4命令行用法错误参数打错了
5一条都没收集到文件名/函数名不符合规则
记住这个「0 与非 0」的规则 几乎所有命令行工具都遵守:0 表示成功,任何非 0 表示失败。

第 16、17 页整套流水线和质量门禁,判定依据就只有这一个数字。

四、所有测试共用的骨架:三段式

不管哪一层测试,骨架都是同一个:

看一个最小的例子 —— 这一层的「准备」是空的:

def test_普通价格() -> None:
    #  ① 准备:这一层不需要准备什么
    #  ② 执行 + ③ 断言 写在了同一行
    assert format_price(1234) == "¥12.34"
    #      └──── 执行 ────┘    └─ 断言 ─┘

五、测「该报错的时候有没有报错」

异常断言pytest.raises特殊
① 定义

一种反过来的断言:我期望这段代码抛异常。抛了才算通过,没抛算失败。

② 类比

测试安全气囊。

你不能只测「正常开车时气囊不弹出来」,还得测「撞上去时气囊必须弹出来」。 该响没响,和不该响乱响,是同样严重的两种故障。

③ 位置

它是运行器提供的,不是 Python 自带的(assert 才是自带的)。

它和普通断言是互补关系:普通断言测「算得对不对」,它测「拦得住拦不住」。

④ 例子
def test_负数要报错() -> None:
    with pytest.raises(ValueError):
        format_price(-1)

如果这段代码没有抛异常,失败信息长这样:

  真实输出
    def test_负数要报错() -> None:
        with pytest.raises(ValueError):
>           format_price(-1)
E           Failed: DID NOT RAISE <class 'ValueError'>

DID NOT RAISE —— 「你说这里该报错的,结果它没报」。

⑤ 误区

误区 1:「with 块里可以放好几行」。能放,但不该放 —— 如果放了三行,你不知道是哪一行抛的异常,测试就失去了精确性。只放期望抛异常的那一句。

🔄 误区 2(经核实修正):「可以在自己的脚本里断言那句 DID NOT RAISE 文案」。 不建议。实测这句话的完整形态是 Failed: DID NOT RAISE <class 'ValueError'>, 后面还跟着期望异常的类型;传异常元组时又变成 DID NOT RAISE any of (...)。 而且这串文字不在官方文档里,是实现细节 —— 版本一变就可能改。要匹配就只匹配 DID NOT RAISE 这个子串。

进阶:还能顺便检查报错信息 
with pytest.raises(ValueError, match=r"不能为负数"):
    format_price(-1)

注意 match= 里面是正则表达式,而且用的是「搜索」语义(不是全匹配)。 所以括号、点号、$ 这些字符要转义 —— 这是最常见的坑。

六、准备工作再讲一遍

第 2 页已经介绍过准备工作(fixture)。这里补一个第 7 页会用到的关键点:它怎么保证测试之间互不干扰。

为什么这件事很重要 假设三条测试都往同一个数据库文件里写数据:

测试 A 写了一条订单 → 测试 B 查询「一共有几条订单」→ 数出来是 1 而不是 0 → B 失败了

而 B 本身的代码完全没问题。 这种「测试互相污染」会让你花几小时排查一个不存在的 bug。

更糟的是:换个执行顺序,失败的可能变成 A。这就是第 10 页要讲的「时红时绿」的成因之一。

七、三种容易混淆的「测试」

形态谁执行 能否重复可靠性
① 自动化测试代码文件机器,秒级 ✅ 无限次高,客观
② 手动测试人的操作你,鼠标键盘 ❌ 每次靠人中,会漏
③ 自然语言验收标准一段话AI 自己判断 ⚠ 结论可能不同低,主观

本教程说的「测试」只指 ①。

③ 确实存在也有用,但它不叫测试。比如你写:

改完自己检查一下:登录失败时应该显示错误提示,不应该跳转。

这是验收标准,AI 会去读代码判断「嗯,看起来是这样」。问题在于:

  • 它是在读自己刚写的代码,倾向于确认自己是对的
  • 结论是「我觉得应该没问题」,不是「我执行了,结果是 X」
  • 同一份代码问两次可能给两个答案
① 和 ③ 的本质区别:证据来自谁 ① 的证据来自运行器和检查工具 —— 它们不会撒谎,也不会给 AI 面子。
③ 的证据来自模型自己的判断 —— 那正是你要防的东西。

AI 在这一步到底做了什么

很多人以为「让它自测」是让它反思一下。不是。你会看到它真的在执行命令:

  会话里的真实过程
● Bash(.venv/bin/python -m mypy)
  ├ myshop/price.py:14: error: Incompatible return value type
     (got "int", expected "str")  [return-value]

● 我看到一个类型错误,正在修复...

● Bash(.venv/bin/python -m mypy)
  ├ Success: no issues found in 10 source files

它调用的是真实的命令,拿到的是真实的程序输出。

八、「几百上千条」是怎么来的

看前面的例子:一个 5 行的小函数就有 5 条测试用例。一条用例 ≈ 一个具体场景。

项目状态测试数量
你刚建的新项目0 条
写了两个月的小项目几十条
一个成熟的开源库几百到几千条
大型商业项目上万条
关键认知 这些不是谁在某一天一口气准备出来的,是几个月几年里一条一条累积的。 每加一个功能加几条,每修一个 bug 加一条。

你现在没有测试,不代表你用不了这套流程 —— 跟着流程走,测试会自己长出来。
